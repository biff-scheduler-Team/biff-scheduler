# PLAN-20260916104514 — 让「登录后十几分钟被踢」这件事**可见**（分诊 401 + 暴露自动续期能力）

## 目标

线上（`https://biff.lcandy.co`）反馈区 / 讨论区无法评论，账号面板一直显示：

> 登录已过期。本机数据已保留，请重新登录继续同步。
> 重新登录后，可继续同步这个账号在本机保存的排片。

用户原话（不要转述）：

> 反馈区为什么一直不让我评论 让我重新登录 说
> 登录已过期。本机数据已保留，请重新登录继续同步。
> 重新登录后，可继续同步这个账号在本机保存的排片。

> 登录后很快就过期 十几分钟内 而且不会自动刷新 这是重新登录后的

> 我的账号访问不了生产的

## 现状（代码事实，含行号）

**1. 前端这条文案的唯一来源**是 `apps/web/src/account-sync.ts:207` 与 `:247`：
`identify()`（`GET /api/account/me`）返回 **401**、且本机 `iffday.workspace.owner.v1` 仍是某个账号时写入。
之后 `syncAccount` 每 20s 重试、每次都 401 → 这条 message 一直挂着（用户感知的「一直」）。

**2. 用户截图证明 cookie 还在**（`__Host-biff.session` 有值），
所以**不是**「cookie 过期/丢失」，而是**「cookie 还在、服务端会话行已经不在」**。

**3. 时间点**：用户说十几分钟。`sessionFor`（`apps/api/src/oauth.ts:105`）只在
access token 剩余 < 30s 时才刷新，而 access token 寿命 15 分钟（`index.ts:223` 的 `expires_in ?? 900`）
→ **登录后约 14.5 分钟的第一次请求触发刷新**，与「十几分钟内」精确吻合。

**4. 401（而非 503）意味着走了「删行」路径**，共三条：

| # | 位置 | 条件 | 现象 |
|---|---|---|---|
| A | `oauth.ts:106-109` | `!tokens.refreshToken`（登录时上游没给长效凭证）→ 删行 | 15 分钟后**必然** 401，不依赖任何上游网络 |
| B | `oauth.ts:157-160` | 刷新被上游判 `invalid_grant` → 条件删行 | 15 分钟后 401，依赖上游 |
| C | `index.ts:250-251` | 上游 `/api/v1/profile` 返回 401 → 删行 | 刷新成功后的第一个请求 401 |

**A 的概率最高**：它**不需要任何上游往返**，是确定性的（「必然在 15 分钟挂」正好解释用户描述的稳定复现）；
B/C 是概率性的，不太可能每次都在 15 分钟整点复发。
本地 E2E（`e2e/account.spec.ts:366-400`）能跑「access token 过期 → 刷新 → 200」，
说明**本地账号系统会下发 refresh token** —— 生产上游是否下发，本仓库现在**无法观察**。

**5. 观察手段全断**：
- 生产 CF 账号是 `62cbe67b…`，本机 wrangler 登的是 `c591765d…` → **查不了生产 D1、tail 不了日志**（用户已确认「访问不了生产的」）；
- 代码里 A/B/C 三条分支**只有 B 的并发子路径有 `console.warn`**，A 与 C 完全静默；
- 9/15 的两次回退（`7468646` / `128331f`，回退到 `45d651c`）恰好撤掉了
  「401 分诊 + 日志 + 会话滑动续期」（`6ab51d7` / `5042f29`），其中 `6ab51d7` 的提交说明**已经指名 A**：
  「没有 refresh token 的会话撑不过第一个 access token 窗口(15 分钟)，之后必然『cookie 还在、行没了』的永久 401」。

## 范围

**做（把病因变可见，零行为变更）：**

1. `oauth.ts::sessionFor` 的返回值加**失败原因分诊**（`SESSION_NO_COOKIE` / `SESSION_NOT_FOUND` /
   `SESSION_NO_REFRESH_TOKEN` / `SESSION_REFRESH_REJECTED`），并给 A、C 两条静默路径补 `console.warn`
   （**只记 subject 与原因，不记 token**）。
2. `index.ts::requireIdentity` 把原因作为 401 的 `error` 字段返回；上游 profile 401 改回独立的
   `IDENTITY_REJECTED`（原来与本地会话失效共用 `UNAUTHENTICATED`，无法区分）。
3. **`GET /api/account/me` 增加 `renewable` 字段**（= 会话里有没有 refresh token）。
   这是本轮的**关键一击**：用户重新登录后**立刻**就能看到它是 `true` 还是 `false`，
   不必等 15 分钟复现 —— A 的结论一次点击即可坐实。
4. 前端 `account-sync.ts`：401 的具体原因拼进那句提示（「登录已过期（登录时没有拿到可自动续期的凭证）」）；
   `account.ts` 账号面板在 `renewable === false` 时给出明确说明。
5. `index.ts::/api/auth/callback` 补 `oidc_token_issued` 日志（记 `expires_in` 与 `有/无 RT`）。

**不做（本轮明确不碰）：**

- **不改任何现有行为**：不「缺 RT 就判登录失败」（那会让用户从「能用 15 分钟」变成「完全登不上」，
  比现状更差，且要等诊断结论才知道值不值）；
- **不做会话滑动续期**（解决的是「7 天被踢」，与本次 15 分钟现象不是一回事）；
- 不动上游账号系统（`IFF-Day/account` 不在本仓库；`prompt=consent` 之类的猜测**等到诊断结论再上**）；
- 不改共享契约 `packages/contracts/src/account.ts`（`renewable` 只在前端私有 schema 里解析）；
- 不碰 `legacy/`（它只 import `accountState` 等既有导出，本轮只增字段，零影响）；
- 不碰工作树里其他人的在途改动（`App.tsx` / `ScreeningDiscussionDialog.tsx` / `PLAN.md` 等）。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 401 分诊 + `renewable` 字段（本轮） | **采纳** | 生产日志不可读、D1 不可查；把诊断搬到**用户可见的响应**里是唯一可行路径 |
| 只加 `console.warn` 靠 `wrangler tail` 查 | 否决 | 本机账号无生产权限（用户已确认），日志没人看得到 |
| 直接按猜测修（缺 RT 就判登录失败 / 加 `prompt=consent`） | 否决 | 猜错会把「15 分钟可用」变成「完全不可用」；且分诊一轮就能定性 |
| 在 `sessionFor` 返回 `null` 前写模块级变量传原因 | 否决 | Worker 同 isolate 并发请求会串扰，错误码不可信 |
| 改 `Account` 共享契约加 `renewable` | 否决 | 会话状态不属于账号资料；前端扩展 schema 即可 |
| 会话滑动续期（1 天窗口）一并做 | 否决 | 与 15 分钟现象无关，混进本轮会掩盖真正的验证信号 |

## 验收标准

1. `apps/api/tests/oauth-session.test.ts` 覆盖 4 类失败原因（先红后绿：改动前跑一次贴失败值）。
2. `npm test -w @biff/api` 全绿；`npm run typecheck` / `npm run lint` 全绿。
3. 手动构造三类 401 时，`/api/account/me` 的 `error` 分别给出
   `SESSION_NOT_FOUND` / `SESSION_NO_REFRESH_TOKEN` / `IDENTITY_REJECTED`。
4. 部署后（**经用户确认再推**）：用户重新登录后立刻 `curl` 或 F12 看 `/api/account/me`，
   能一眼读出 `renewable` 与（若失败）具体 `error` —— 本轮**不以「问题已修复」结案**，
   而是以「病因已坐实 + 下一步修复方向明确」结案。
