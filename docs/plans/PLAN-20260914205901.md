# PLAN-20260914205901 — 修复「我的行程」顺位拖拽在页面滚动后判定错位（CI E2E 红）

## 目标

CI（main push，run 34842131579）E2E 报 `1 failed / 1 flaky`：

> 1 failed: `[desktop-chromium] › e2e/react/desktop.spec.ts:4:1 › hover links a conflict group across the agenda and grid; dragging persists its order`
> `SyntaxError: "undefined" is not valid JSON`（`JSON.parse((await storage(page))["biff.ranks.v1"])`）

本地单文件单浏览器 100% 复现（`1 failed, 3 passed`）。

## 现状（代码事实，非推测）

- 拖拽实现：`apps/web/src/pages/AgendaPage.tsx:85-161`（`RankGroup.startDrag`）。
- 失败点：拖拽结束后 `biff.ranks.v1` 从未写入 → `setRanks()` 没被调用 → `finish()` 里
  `moved && target !== from` 不成立 → **`target` 被判成等于 `from`（没有发生交换）**。
- 探针实测（`e2e/react/zz-probe-a.spec.ts`，跑完即删）：
  ```
  [dst] {"x":56,"y":728.25,"width":284.5,"height":460.5}
  [ev]  ["pointermove:667","pointerdown:667","pointermove:525","pointerup:525"]
  [ranks] undefined
  ```
  即 `dragTo(targetPosition:{x:20,y:4})` 期间，Playwright 为 hover 目标行触发了
  `scrollIntoViewIfNeeded`（目标行从 `y=728.25` 被滚到 `y≈521`），指针最终落在 525。
- 根因：`startDrag()` 在 **pointerdown 时刻**用 `getBoundingClientRect()` 捕获各行的视口 rect
  （`AgendaPage.tsx:99`），而 `paint()` 直接拿后续的 `e.clientY`（`AgendaPage.tsx:114`）与之比较。
  页面一旦在拖拽中途滚动，两者就不是同一坐标系 → 阈值 `centerY + dy` 整体偏移 → 排序判定错位。
  这是**实现缺陷**，不是测试写法问题：真实用户把行拖到视口边缘触发浏览器自动滚动时同样会错位。

## 范围

**做:**

1. `apps/web/src/pages/AgendaPage.tsx`：把顺位拖拽的判定坐标统一到「相对容器顶」的局部坐标系，
   滚动量由每次 `paint()` 重新读取的容器 rect 吸收。
2. `e2e/react/desktop.spec.ts`：在拖拽用例上补注释，说明该用例的 `dragTo` 会触发滚动，
   正是本缺陷的回归覆盖点（防止后续被"优化"成手动 `mouse.move` 而丢掉覆盖）。

**不做:**

- 不改拖拽的交互形态（仍是把手 `pointerdown` + `window` 上的 `pointermove/pointerup`）。
- 不动 `review-schedule.spec.ts:60`（mobile-webkit 的 midnight 边界用例本次是 **flaky**，重试后通过，
  与本缺陷无关，另案观察）。
- 不动 `e2e/react/zz-debug.spec.ts`（未跟踪的临时调试文件；本工作区疑似有并行会话在编辑它）。
- 不改 `biff.ranks.v1` 的数据结构。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 捕获 rect 时统一减去容器 `rect.top`，`paint()` 里再用当前容器 rect 还原 | 采纳 | 改动最小；捕获时刻各行无 transform，rect 干净；滚动量自动被吸收 |
| 改用 `offsetTop` / `offsetHeight` | 否决 | `offsetTop` 相对 offsetParent，而 `.rank-group ol` 未必是定位祖先，基准需额外校正 |
| `paint()` 里重测各行 rect | 否决 | 拖拽中行带 `transform: translateY(...)`，重测会把位移算进去，污染判定 |
| 监听 `scroll` 重新捕获 rect | 否决 | 需要额外注册/注销与去抖，且仍有"滚动与 pointermove 之间"的空窗 |
| 改测试为手动 `mouse.move`（已验证可绿） | 否决 | 掩盖真实缺陷：滚动场景下用户拖拽仍会错位 |

## 修订 1（2026-09-14，收口时）

**触发**：并行的另一个会话把 `e2e/react/desktop.spec.ts` 的 `dragTo` 换成了手动鼠标手势
（理由「落点会过期」），用户已停止该会话并要求由本会话收口。

**测试形态的最终取舍**：保留原 `dragTo` 写法（只补注释），不采用手动手势。理由：

1. `dragTo` 天然覆盖「拖拽中途页面滚动」这条路径 —— 实测「修复前红（`undefined`）/ 修复后绿」，
   即它本身就是一条有效的回归测试；
2. 手动手势需要自己造滚动，而行程页有 `window` + 内部列表两层滚动容器：
   实测 `handle.scrollIntoViewIfNeeded()` 只改内部容器（`scrollY` 仍为 0，而目标行从 728 移到 176），
   `window.scrollBy` 只改 window —— 滚动量无法稳定控制，比 `dragTo` 更脆。

**顺带稳定化 flaky 用例（用户要求本轮一起做）**：`review-schedule.spec.ts:60`（mobile-webkit）
根因是 `page.clock.install({time})` 之后时钟**仍按真实时间流逝**，而用例起点是 `23:59:59`
（距午夜只剩 1 秒）—— 页面加载慢过 1 秒，`todayIsoLocal()` 就已经是 10-11
（10-11 也在 `dates` 里），mobile 默认日期随之漂到 10-11，断言必红。
探针实测（本地 mobile-chromium，fake clock 行为与浏览器无关）：

| 写法 | 默认日期 |
|---|---|
| `install(23:59:59)` 后立刻加载 | `2026-10-11` ❌ |
| `install(23:59:59)` 后等 2.5s 再加载 | `2026-10-11` ❌ |
| `install` + `pauseAt(23:59:59)` 后等 2.5s 再加载 | `2026-10-10` ✅ |

修法：`install` 后立刻 `pauseAt(midnight)` 冻结，跨午夜交给用例原本就有的 `fastForward(2000)`。
