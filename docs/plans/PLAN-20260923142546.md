## 批次 1 详细设计

### 1.1 新表 `stat_daily`（迁移 `0010`，drizzle-kit 生成）

```sql
CREATE TABLE stat_daily (
  edition    TEXT    NOT NULL,
  day        TEXT    NOT NULL,   -- 'YYYY-MM-DD'，**KST 日界**（见 1.3）
  metric     TEXT    NOT NULL,   -- 'want' | 'vote' | 'screening' | 'ticket' | 'telemetry'
  target     TEXT    NOT NULL,   -- film_key / 场次 code / telemetry 的 'kind:target'
  weight_sum TEXT    NOT NULL,   -- 与既有表同款：文本存 '0.75' / '1'，避免浮点漂移
  hits       INTEGER NOT NULL,   -- 只对 telemetry 有意义，其余恒 0
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (edition, day, metric, target)
);
```

**为什么不给现有 5 张 `*_stat` 加 `day` 列**：那会改掉主键与所有读写路径的语义（键从 `(edition, target)`
变成 `(edition, day, target)`），榜单读侧全部要跟着改；新表可以并存、可单独删。

### 1.2 写入点（集成点清单，逐条）

日桶只记**本次的增量**，所以天然落在已有的 diff 上（不是整份写）：

| ping | 增量从哪来 | 备注 |
|---|---|---|
| `want-ping` | `replaceContributorWants` 里的 diff（键集合差异） | 权重 `wantWeightFor(session ? 1 : 0.75)` |
| `film-votes-ping` | `replaceContributorVotes` 的 `diffVotes` → `removed` / `added` | 一人一部一票，无权重 |
| `screening-attendance-ping` | `replaceContributorScreenings` 的 diff | 同 want 权重 |
| `ticket-results-ping` | `replaceContributorTickets` 的 diff | 四项结果各自计数 |
| `telemetry-ping` | 本身就是增量（`deltas`） | 直接累加 `hits` / `weight` |

⚠ 全部**必须并进同一次 `flushStatBatch`**（`stat-batch.ts`），否则 `stat-atomicity.test.ts` 的
往返次数断言会红 —— 那正是它的用途。

### 1.3 日界与时区

`day` 由**服务端**用 `Date.now()` 换算成 **KST（UTC+9）** 的 `YYYY-MM-DD`；**绝不接受客户端传日期**
（可伪造）。与项目既有的「时间口径单一来源」一致：换算写在一处（新 `apps/api/src/day.ts`），
其它地方只 import。

### 1.4 历史数据：**不回填**

现有累计值无法拆到天，硬拆就是**编造数据**。UI 与接口都要显式标注「趋势自 2026-09-23 起」，
由 `stat_daily` 里最早的那一天自动得出（`earliestDay` 字段）。

### 1.5 admin 读接口族（5 条，全部走已上线的 `/api/admin/*` 两层门禁）

| 接口 | 作用 |
|---|---|
| `GET /api/admin/overview?edition=` | 各模块总量 + 去重贡献者数 + 今日增量 + 最早趋势日 + **对账结论**（见 1.6） |
| `GET /api/admin/rows?edition=&metric=&limit=&cursor=&q=` | 通用的「贡献行明细」，`metric` 决定读哪张表；**含 `contributor` 原文**，分页 + 名称筛选 |
| `GET /api/admin/trends?edition=&metric=&days=` | 按天序列（`stat_daily`）+ `earliestDay` |
| `GET /api/admin/content?edition=&kind=discussion\|feedback&limit=&cursor=` | 讨论 / 反馈列表（含作者、反应数） |
| `GET /api/admin/accounts?edition=` | 会话数、同步文档**条数与体积**（**不回片单内容**） |

把 4 张同形的贡献表收进**一条** `rows` 读路径，是为了不让 4 套分页 / 筛选各写一遍（同口径两份 = 红线 5）。

### 1.6 对账（数据质量体检）

`auditContributions(db, edition)`：对每个 metric，`SELECT ... GROUP BY 目标` 从**贡献表**算一遍，
与 `*_stat` 比 → 返回 `ok` 或逐条漂移 `{ target, contribution, stat }`。
这是纯读 + 纯算术，可单测（d1 垫片上人为造一个漂移行，断言能报出来）。

### 1.7 「谁想看」等明细的隐私边界

`rows` 接口会回 `contributor` 原文（subject / `anon:` hash）。它与 `film-vote-contributions` 同级：
**门禁只有 `/api/admin/*` 那一层**，任何新增调用点都要先确认门禁。
**片单内容（`festival_document.records`）永远不进后台** —— 只出条数与字节数。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 给现有 `*_stat` 表加 `day` 列 | 否决 | 改主键与全部读侧语义；新表可并存、可回滚 |
| 用「事件流水表」记每次投票 | 否决 | 体积与隐私都远超收益（要存 contributor × 事件），日桶只要计数 |
| 趋势只在客户端记（localStorage） | 否决 | 管理后台看的是**全体**，客户端看不到别人 |
| 日桶按 contributor 也记一份 | 否决 | 体积爆炸且给「谁在哪天做了什么」留了长期留存，无必要 |
| 通用 `rows` 接口 vs 每 metric 一个接口 | 采纳通用 | 4 张表同形，分页 / 筛选 / DTO 只写一份 |
| 前端抄白名单判断管理员 | 否决 | 第二份口径 + 泄露名单；改由 `whoami` 回 |
| 管理入口进 nav | 否决 | nav 是公开的，等于给所有用户展示管理入口 |

## 明确不做

- ❌ 片单内容（`festival_document.records`）进后台 —— 只出统计量。
- ❌ 登录趋势（`app_session` 没有 `created_at`，要做得再加一次迁移；本轮不做）。
- ❌ 讨论 / 反馈的**趋势**走日桶 —— 它们有 `created_at`，直接 `GROUP BY date` 更准。
- ❌ 内容审核类操作（删帖 / 删反馈）—— 那是新语义（谁能删别人的内容），本轮不碰。
- ❌ 导出走后台任务 / 邮件。

## 「零影响」核对手段

1. 改的是**新增表 + 新增周几行写入 + 新增只读接口**，现有聚合读接口与前端一行不动。
2. `stat-atomicity.test.ts` 的往返次数断言是**守门人**：日桶若另起批次，它会立刻红。
3. 迁移**只 CREATE TABLE**，不 ALTER / 不 DROP，不碰现有表结构。
4. 回滚手段：接口层可单独摘除；`stat_daily` 是纯新增表，删掉不影响任何现有读路径。
5. 部署后核对：`/api/stats/*` 五个读接口返回值与改前一致（`stat_daily` 不该影响它们）。

## 修订 1（2026-09-23，实现期；批 1 落地的三处偏离）

1. **端点从 5 条收敛为 4 条**（`whoami` / `overview` / `rows` / `trends`）：
   - 原计划的 `content` **不做了** —— 「讨论 / 反馈列表」已经有公开读接口（`/api/discussions`、
     `/api/feedback`，都带作者与反应数），管理页直接复用即可。再造一个管理端版本就是
     **同一口径两份实现**（红线 5）。
   - 原计划的 `accounts` **并进 `overview`** —— 它只有四个计数，单开一个接口不值得。
2. **日账本的子类型编进 `metric`，不是原计划写的合成桶**（`vote` / `ticket` / `telemetry`）：
   - `metric` 白名单最终是 `want` / `vote:red` / `vote:black` / `screening` /
     `ticket:{got,transfer,missed,dropped}` / `telemetry:{page,click}`；
   - 理由是 `target` 自己的字符集（路由 `^[a-z0-9\-/:*]+$`）**就含 `:`**，拿它当分隔符迟早撞上；
     而编进 metric 的两段都来自闭合白名单 ⇒ 天然无歧义。`trends` 接受族的裸名
     （`vote` → 红黑相加），由 `dailyMetricFamily()` 展开。
   - 另外红黑票**必须**按颜色分桶：合成一个桶会让「改票（红→黑）」当天 −1/+1 互相抵消，
     趋势图上什么也看不见。
3. **测试基建上收**：`tests/d1-shim.ts` 新增 `createSessionSchema` / `createAdminSchema`
   （会话表与概览会碰到的非统计表），并删掉 `film-vote-admin.test.ts` 里那份重复的会话表 DDL。
   ⚠ 两者**刻意不重叠**建 `app_session` —— 同时用会让测试挂在 `table app_session already exists`。

批 1 已完成**三片**（地基 / 接线 / 接口与对账），全绿后走一个 PR（含生产迁移）。
