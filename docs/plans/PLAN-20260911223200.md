⚠ openapi.yaml **不能当 schema 用**(交接文档 §15.3 已自陈):path 是展开后的样例 ID、
通用参数只有 `apikey/_ts/_sig`、POST 的 requestBody 未恢复、response schema 基本没定义、
弃用条目也进了 paths。它的价值是**路由清单**,不是类型定义。

## 2. 协议要点(来自交接文档,已本机实测)

```
origin   https://frodo.douban.com
path     /api/v2/...
apikey   0dad551ec0f84ed02907ff5c42e8ec70
_sig     Base64(HMAC-SHA1(app_secret, "METHOD&percent_encode(path)&_ts"))
         path 编码后 / → %2F;业务 query 不参与签名;Base64 里的 + 必须再被 urlencode 一次
UA       api-client/1 com.douban.frodo/7.129.0(071290003) iOS/18.2 iPhone14,5
设备参数  os_rom=ios / channel=AppStore / udid=device_id=40 个 f / timezone=Asia/Shanghai
```

**为什么只能离线跑,不能进浏览器**(三条硬约束,缺一不可绕过):

1. `User-Agent` 是浏览器的**禁止头**,JS 设不了 → 服务端按 UA 决定返回 schema;
2. `frodo.douban.com` 不返回 CORS 头 → 跨域必被拦;
3. `app_secret` 随前端产物下发 = 公开。

→ 接入点只能是**离线管线**(与本站「零后端、纯静态」的既定架构一致,不改 D2/D6)。

## 3. 关键发现:三个接口的可用性并不一样

| 接口 | 匿名可用 | 实测结论 |
|---|---|---|
| `GET /api/v2/movie/{id}` | ✅ | 详情,给 `title/original_title/aka/directors/year/rating/pic` —— **匹配的权威依据** |
| `GET /api/v2/search/suggestion` | ✅ | `cards[]`,subject 卡带 `target{id,title,year,rating}` |
| `GET /api/v2/search/mix_suggest_subjects` | ✅ | `items[]`,字段平铺,年份藏在 `card_subtitle` 开头 |
| `GET /api/v2/subject_collection/{slug}/items` | ✅ | 榜单(与本次需求无关,仅验证可用) |
| `GET /api/v2/search/subjects` | ❌ | **跑约 100 次后 `HTTP 403 code=103 need_login`** |

**结论:交接文档推荐的 `search/subjects` 在长跑里不可用**,而交接文档 §16.3 又明确记录
「豆瓣用户登录与刷新流程**未恢复**」→ 拿不到 access token。故检索改用
`suggestion`(主)+ `mix_suggest_subjects`(备)两个匿名口。

### 3.1 详情口也有 IP 级风控(踩坑记录)

跑完 `search/subjects` 被封后改走匿名口,**跑约 120 部后详情口开始返回**:

```json
HTTP 400 {"code": 1309, "msg": "subject_ip_rate_limit",
          "localized_message": "您所在的网络存在异常，请登录后重试。"}
```

危险点:此时 `search` 仍返回 200(只是候选为空或照常),**很容易被当成「这部片豆瓣没有」而写进
`miss`** —— 一张表 246 部,后 100 部全被写成「未命中」,而且看起来「跑完了」。
故 `douban_match.py` 把 `{103, 1005, 1309}` 定为**风控码**,命中即抛 `DoubanUnavailableError`,
调用方**立即停轮**、保留已落盘进度(绝不写 miss)。

## 4. 落地:三个模块

```
tools/frodo_client.py      协议层:签名 / 设备参数 / HTTP / 错误码(纯标准库,零依赖)
tools/douban_match.py      业务层:检索 → 挑候选 → 详情确认 → 置信度(两个产物脚本同源)
tools/build_douban_map.py  产物层:films.json → public/douban.json(前端消费的那份)
tools/enrich_douban.py     产物层:影片表 → data/enriched_douban.json(海报管线用)
```

### 4.1 匹配口径(宁可缺,不可错)

```
候选     = search/suggestion(+ mix_suggest 兜底)的 movie 条目
确认     = /api/v2/movie/{id} 详情的 title ∪ original_title ∪ aka[] 与本片片名归一后相交
high     = 片名命中 且 年份不矛盾        ← 唯一会写进 douban.json 的档
medium   = 片名命中但年份不符 / 只靠导演命中   ← 默认不写,只计数
miss     = 都没命中 → 不写(前端本来就有豆瓣搜索兜底)
```

只靠「年份 + 国家」这类弱证据**永不**判命中(与 `tools/film_match.py` 同一条纪律:
错配比配不上危害大得多 —— 静默挂错中文名 / 海报)。

### 4.2 `public/douban.json` 的键

键 = **影片 id(`f###`)与它各场次的 `code`**,两条都写:

* 网格 / 行程 / 资料弹层按**场次 code** 查表(`grid.ts::mappingOf`、`modal.ts::buildDoubanBlock`);
* 「无排期目录片」按**影片 id** 查(`library.ts`)。

条目一律带 `title_en` —— 它是 `tools/prune_douban.py` 判「跨届撞号」的自证签名
(键是现编号,换届会撞号)。新增 `year/rating/rating_count/confidence` 为**审计字段**,
前端 `data.ts::loadDoubanMappings` 只取 `subject_id/title_cn/douban_url`,多出来的字段无害。
