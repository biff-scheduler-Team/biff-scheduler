# PLAN-20260910122007 · 接入 2025 真实排期（29 厅 / 699 场）+ 造一份 2025 影片目录

## 1. 现象 / 需求

用户看图（2025 第 30 届 BIFF 排期册）后问：「明明有很多个厅，为什么现在展示的只有四五个？」
拍板：**把 2025 真实排期接进 `public/`**（按「厅」建 29 馆），影片目录（films.json）「造一点」——即由 AI 合成一份与 2025 排期对得上的片单。

## 2. 根因

页面渲染没问题：`src/data.ts` 的 `screeningsByVenue()` 是按「当天有场次的 `venue_id`」逐厅分泳道，无截断逻辑。
问题在数据源——`public/schedule.json` + `public/venues.json` 仍是 **2026 第 31 届 MOCK 演示数据**：

| | 现状（mock） | 目标（2025 真实） |
|---|---|---|
| 场次 | 24 | **699** |
| 场馆 | **5 个「楼」**（bcc-1/bcc-2/cgv-centum/lotte-centum/mega-haeundae） | **29 个「厅」**（bt/b1…/l10/m1…/kt/sh/bcm/bd） |
| 日期 | 3 天 | 10 天（09-17~09-26） |

2025 解析产物早已存在（`tools/extract_schedule.py`，PLAN-20260910111844），但默认输出到 `/tmp`，**从未写进 `public/`**——这正是记忆里记下的阻塞项：「venue_id 两套口径并存（按楼 5 个 vs 按厅 29 个），上真数据前必须先统一」。

## 3. 方案

### 3.1 数据层：`public/`

重跑解析器（`~/Downloads/2025_BIFF_Ticket_Catalogue_web.pdf`），产物落 `public/`：

```
python tools/extract_schedule.py --pdf ~/Downloads/2025_BIFF_Ticket_Catalogue_web.pdf \
    --year 2025 --month 9 --out /tmp/biff2025/schedule.json --venues-out /tmp/biff2025/venues.json
```

后处理（一次性脚本 `tools/import_schedule_2025.py`，读 /tmp 产物 → 写 `public/`）：

- **venues.json**：29 厅，`id` = 官方代码小写、`code` = 官方代码大写、`group` = 影院（bcc/cgv/lotte/megabox/kofic/sohyang/bcm）、`region` = 分区（centum/nampo）；**泳道顺序按「分区 → 影院 → 厅号」重排**（centum：bcc→cgv→lotte→kofic；nampo：megabox→sohyang→bcm），让相邻厅挨着；`lat/lng` 保持 `null`（前端不消费，见下）。
- **schedule.json**：`festival` 改真实口径（30th BIFF / 2025 / 10 天 / note 去掉 mock 字样），`screenings` 原样落盘。
- 数据口径修正：41 场（M1–M4 南浦，原册只印韩文名）`title_en` 为空 → **不在这里补**，交前端兜底（见 3.2）。

### 3.2 前端：让 29 厅 / 699 场能正常渲染

- `src/data.ts`：
  - `loadCatalog()` 里对 `screenings` 做一次**规范化**：`title_en` 为空时用 `title_kr` 兜底（41 场南浦场次，否则卡片标题空白）。单一入口，不动 util/library。
  - 其余逻辑（`screeningsByVenue` / `dates` 派生）天然支持 29 厅 10 天，无需改。
- `src/types.ts`：`Venue` 补 `region?: string`（与 venues.json 契约对齐）。
- `src/legend.ts`：
  - `GROUP_AREA` 的 key 从旧 mock 口径（bcc/centum/haeundae）换成新 group 值（bcc/cgv/lotte/megabox/kofic/sohyang/bcm），否则图例「分区」列全部显示 `—`；
  - 去掉「mock 演示 / 2026 以官网为准」措辞（现在是 2025 真实数据，代码即官方 Catalogue 代码）。
- `src/main.ts`：`toast("排片为 MOCK 数据 …")` 改为真实口径提示（仅此一行，避免与其他会话的在途改动冲突）。

### 3.3 影片目录：`public/films.json`（「造一点」）

2026 目录（246 部）与 2025 排期对不上（`filmNodeKey` 全走 `sched:` 分支，影片库「未关联」）。改为**从 2025 册子造一份真实片单**：

- 片名来源 = 排期里抽取的**唯一影片**（236 个 `title_en` + 41 个仅韩文 ≈ 277 条），保证 `title_orig == s.title_en` → `filmNodeKey` 精确命中 `cat:f###`。
- 元数据（unit / country / year / director）来源 = 册子**影片介绍页**（p22–p101）：用排期的 `page` 字段定位页，取该页页眉的**单元名**、`국가 | 연도 | nmin | 포맷 | 색` 元数据行、`Director …` 行，按页内坐标就近配对；配对不到则留空（`title_zh` 全空，中文名交后续 `enrich_douban.py`）。
- `unit` 空值时影片库单元筛选只剩「全部」——可接受（用户明确「造一点」，不追求完整）。

### 3.4 不改的东西

- 渲染层（grid / agenda / modal / engine / pick / state）一行不动——它们本来就与场馆口径解耦。
- `store.picks` 数据契约、D1 表结构不动。
- `public/films.json` 的 2026 原文件先备份到 `data/films-2026.json`（不删，将来换届还能用）。

## 4. 验收

1. `npm run typecheck` 通过。
2. `public/venues.json` = 29 厅；`public/schedule.json` = 699 场 / 10 天；`code` 全局唯一。
3. 甘特图某一天（如 09-20，95 场）能正常渲染出该日全部厅的泳道（当天有场次的厅全部出现，不再是 4–5 条）。
4. 图例「影院代码 / 分区」表列出 29 厅且分区列有值。
5. 41 场南浦场次卡片标题不空白（显示韩文名）。
6. 影片库能列出 2025 片单，且与排期关联（点开某片能看到它的场次）。
7. `git push` + `npm run deploy`（**走隔离 worktree**——工作区有其他会话的在途改动）；`curl -sL https://biff-scheduler.pages.dev/venues.json` 核对线上 29 厅。

## 5. 已知遗留（不在本次范围）

- 韩文片名的空格在 PDF 文本层已丢（`어쩔수가없다` 应为 `어쩔 수가 없다`）——需按字符 x 间距回填，本次不做。
- `lat/lng` 未补（前端不消费，转场用全局 `transitMin` 常数）。
- 影片目录的 `title_zh` 全空 → 显示英文/韩文原名；中文名后续走豆瓣 enrich。
