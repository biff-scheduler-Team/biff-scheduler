# PLAN-20260910140904 — 加入场次强制定档（「未设档位」状态下线）

## 背景 / 用户诉求

> 「我的行程」里面还是会显示既没有选必看 / 备选 / 随缘的电影，请你排查下问题。

排查结论（读代码 + 线上 `GET /api/pick` 核对）：

1. 行程行**完全不看档位** —— `agenda.ts::buildAgenda` 只按 `slot.group === ctx.group` 过滤，
   凡属当前方案的场次一律出行程行。
2. 档位为 `null` 时行程行照常渲染，只是三段 seg 全灰 + 左侧一枚「未设」小字（`agenda.ts:211-213`）。
   这是 `6a3c9de`（新加入场次不再默认「备选」）的**有意设计**，但它没阻止「未设」进入行程。
3. 线上 17 条记录里，**唯一带场次的**是
   `sched:115, 160, 163, 164 midnight passion 3` → `priority: null`、`picks: [{"code":"164","group":"A"}]`
   —— 即午夜联映块第 164 场（块名 `title_en` 匹配不到目录 → 落 `sched:` 孤儿 key）。
   其余 16 条有档位但 `picks: []`（未排场，不进行程）。
4. 根因：网格里点选了一部**没在影片库打标**的片 → 记录被建出来但档位未设 → 行程不筛档位 → 显示「未设」。
   **不是同步 bug，也不是档位丢失。**

`AskUserQuestion` 澄清口径（用户选定）：

- **① 点选时强制定档** —— 网格里点选未打标的片时，先要求选一个档位（必看 / 备选 / 随缘）才加入，
  从根上消灭「未设」；行程照旧显示全部（不做档位过滤）。
- **② 顺手清掉存量** —— 已存在的「未设档位 + 只点了场次」记录（本地 + 云端）一并清理。

## 设计决策

**「未设档位」= 非法状态，彻底下线。** 档位成为「入选片单」的必要条件：

| 状态 | 语义 |
|---|---|
| 有档位 + 无场次 | 选片意向（未排场）—— 合法，`picks: []` |
| 有档位 + 有场次 | 行程成员 —— 合法 |
| 无档位 + 无场次 | 空壳 —— 现状即删除，不变 |
| **无档位 + 有场次** | **非法** —— 本次要消灭的状态 |

消灭手段（两条路径，互为兜底）：

1. **入口强制定档**（新数据）：所有「加入场次」入口在目标片无档位时，先弹「选择档位」小弹层，
   选定后才落场次。不选（Esc / 取消）= 不加入。
2. **清空档位 = 整片移出**（运行期）：`setWish(key, null)` 不再保留记录，直接删整条
   （含其全部场次）。因为「无档位 + 有场次」非法，「只取消档位却留着场次」不可能存在。
   该语义同时覆盖行程行 seg、影片库三选、我的选片三选、详情弹层档位行（四处都走 `setWish`）。
3. **载入清理**（存量数据）：`pruneUnsetPicks()` 在 `loadPicks()` 与 `syncFromCloud()` 之后各跑一次，
   删掉「档位未设 + 有场次」的脏记录（本地 + 云端 DELETE）。幂等，无需迁移脚本。

**不做的事**：

- 不给行程加档位过滤（用户明确选了「行程照旧显示全部」）。
- 不删 `agenda.ts` 的「未设」兜底分支 —— 清理是**载入时**做的，运行期理论上不会再有 null，
  保留分支作为防御（真出现时用户能看出来，而不是静默全灰）。
- 不动 `library.ts`（并行会话在途改动 481 行）。其「未设」chip 是 `if (unset)` 条件渲染，
  `unset === 0` 时本就不出现。

## 边界与风险

- **并行会话热点文件**：`main.ts`（AI 排片 Key 分组，只动 `openSettings`）/ `library.ts`（481 行在途）
  / `legend.ts` / `grid.ts` / `types.ts` / `public/venues.json`。本轮改动点与 `main.ts` 的在途 hunk
  **不重叠**（`openSettings` vs 事件委托区 + `filmModalCtx`）；`legend.ts` 的图例文案**本轮不同步**
  （并行在途，避免交织）。提交按 SKILL `parallel-agent-safe-commit` **只带本需求的 6 个文件**。
- **部署必须走隔离 worktree** —— 工作区有并行在途改动，`npm run deploy` 会把它们一起上线。
- **Tailwind v4 只生成完整字面量类**：新弹层复用 `PRI_BG_ON`（常量表在 `pick.ts`）、
  `hover:brightness-110` / `active:translate-y-px` / `border-line-strong` / `bg-hover`（均已在产物 CSS 里），
  构建后仍要 `grep` 产物核对。
- **`pruneUnsetPicks` 会删用户数据** —— 但删的正是用户要求清理的非法记录，且删前有 `priority == null`
  且 `picks.length > 0` 双条件；有档位 / 无场次的记录一律不动。

## 验收标准

1. `npm run typecheck` 通过。
2. `vite build` 后 `grep` 产物 CSS / JS：新文案与类名命中。
3. 无头 DOM 断言（playwright-core + 缓存 chromium + 临时 `python -m http.server` 对隔离 worktree 的 `dist/`，
   用完 `pkill`；见 SKILL `web-ui-headless-interaction-qa`）：
   - 全新 localStorage：点一张**未打标**的网格卡 → 弹出「选择档位」弹层、**场次未加入**（`biff.picks.v2` 为空）；
     点「备选」→ 弹层关闭、场次加入、档位 `maybe`；行程行 seg 亮「备选」、**无「未设」标签**；
   - 点一张**已打标**的片（影片库标「必看」）→ 直接加入、不弹层、档位 `must`；
   - 已加入的场次再点 → 直接移出、**不弹层**；
   - 行程行 seg 点当前档（取消）→ 该片**整条消失**（`picks` 里查不到该 key），行程行同步消失；
   - 存量脏数据：预置 `biff.picks.v2` 含 `{priority: null, picks: [{code, group}]}` → 刷新后该记录被清理，
     云端收到 DELETE。
4. 线上核对带 cache-buster：`curl -sL "https://biff-scheduler.pages.dev/?cb=$(date +%s)"`；
   `GET /api/pick` 复核那条 `sched:115, 160, 163, 164 …` 记录已消失。
