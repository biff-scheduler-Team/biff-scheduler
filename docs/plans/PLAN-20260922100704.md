# PLAN-20260922100704 — 发版后顶部提示「有新版本」并一键刷新

## 目标

用户原话：

> 现在发版一定要用户 ctrl shift R 才能看到新版本吗
>
> A + 加个 reload 防抖 检测到新版 → 顶部「有新版本，点击刷新」

（A = 走 PWA 更新链路检测新版；「防抖」= 重复事件只提示一次、刷新只触发一次。）

**先还原症状的成因**（2026-09-22 实测线上 `biff.lcandy.co`，避免把结论建在推测上）：

1. HTTP 层**没有**陈旧问题 —— 首页响应头是
   `cache-control: public, max-age=0, must-revalidate`（配 `cf-cache-status: HIT`），
   浏览器每次都得回源校验。静态资源还是内容 hash 名（`/assets/main-Dh1VPkog.js`），不会串版本。
2. 真正拦住新版的是 **PWA 的 Service Worker 预缓存**：线上 `sw.js` 里 `index.html`
   带 revision 进了预缓存清单 —— `{url:"index.html",revision:"dec70d21e29d6fa0768ec0ea4cc17f0c"}`，
   而 `vite.config.ts:144` 的 `navigateFallback: "index.html"` 让**导航请求由 SW 直接吐缓存**。
   **这一层完全绕过上面那个 `must-revalidate`**（HTTP 头管不到 CacheStorage）。
3. 线上 `registerSW.js` 全文只有一句注册：
   `if('serviceWorker' in navigator) {window.addEventListener('load', () => {navigator.serviceWorker.register('/sw.js', { scope: '/' })})}`
   —— **没有任何「新版接管后刷新」的代码**。

合起来就是：发版后**首次打开仍是旧版**，要再刷新一次才更新；而 SPA 的站内跳转是 `pushState`、
不构成导航请求，所以**一直开着的标签页永远等不到新版**。这才是「必须 Ctrl+Shift+R」的真实成因，
与 `docs/plans/PLAN-20260916135942.md:18` / `:47` 记的现场一致。

## 范围

**做：**

1. **检测**：新 SW 接管本页（`controllerchange`，且**页面加载时就已被 SW 控制**）→ 置「有新版本」。
2. **提示**：顶部（`.app-header` 之上）出一条提示：文案 +「刷新」+「稍后」。
3. **防抖**（三道，都是用户明确要的）：
   - 同一实例重复 `controllerchange` 只置位、只通知一次；
   - 点「刷新」只 `reload()` 一次（连点 / 重复回调不再触发）；
   - 更新检查按最小间隔节流（切回前台很频繁，不能变成对 `sw.js` 的轮询）。
4. **长时间挂着的标签页也能发现新版**：`visibilitychange` → visible 与 30 分钟定时器触发
   `registration.update()`。**这条不可省** —— 只靠导航触发的自动检查，SPA 挂一天也不会检查。
5. 单测（纯逻辑，先红后绿）+ E2E（接线与防误报）。

**不做：**

- 不改 `registerType: "autoUpdate"`（`sw.js` 仍自带 `skipWaiting()` + `clientsClaim()`）；
- 不引入 `workbox-window` / `virtual:pwa-register`（理由见「方案取舍」）；
- **不做静默自动 reload** —— 用户明确要「点击刷新」；排片排到一半被强刷会打断上下文；
- 不改注册方式、不改 workbox 预缓存清单（**离线能力零影响**，`e2e/react/offline.spec.ts` 必须继续绿）；
- 不碰 `legacy/`（只读回退件，且它没有 SW 更新问题）；
- 不做「同一会话里第二次发版再提示一次」（同一实例只置位一次；被忽略或被点掉之后就等下次自然加载）。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| `virtual:pwa-register/react` + `onNeedReload`（插件官方路径） | **否决** | 它在 autoUpdate 模式下的行为确实正是我们要的（`activated` 且 `isUpdate` → 调 `onNeedReload` 而**不是**直接 `window.location.reload()`，见 `node_modules/vite-plugin-pwa/dist/client/build/register.js:39-47`）。但代价是拉进 `workbox-window`（实测 gzip **1358 B**，虽是动态 import 的独立 chunk，也是每次加载多一个请求），而它的其余能力（`waiting` 提示、`messageSkipWaiting`）我们用不上 —— `sw.js` 已自带 `skipWaiting()`。更要紧的是**可测性**：走虚拟模块，单测只能 mock 打包器模块，测的是 mock 不是逻辑。 |
| 手写 `controllerchange` 监听 | **采纳** | 原生 API，0 新依赖、0 新增 chunk；检测 / 节流 / 一次性三道逻辑都能抽成纯函数单测。 |
| 只在组件 `useEffect` 里挂监听 | **否决** | 注入的 `registerSW.js` 在 `window.load` 就注册（`dist/index.html:32` 是 `<head>` 里的普通阻塞 `<script>`），新版 SW 的下载 + 安装 + 接管**理论上有机会早于** React 首个 effect —— 那一次 `controllerchange` 会被漏掉，而那正是我们要修的场景。改为在 `main.tsx` 顶层挂：模块脚本（`type="module"`）执行早于 `window.load`，**零竞态**。 |
| 只靠导航触发的 SW 自动更新检查 | **否决**（单独用不够） | SPA 站内跳转是 `pushState`，不构成导航 → 挂一天的标签页永远不检查。必须补 `visibilitychange` + 定时 `registration.update()`。 |
| 检测到就静默 reload | **否决** | 用户明确要「点击刷新」；静默刷新会在排片中途把人打断。 |
| 拿一个构建号 / `version.json` 比对 | **否决** | 要多一个构建产物 + 多一次 fetch；而 `controllerchange` 已经是「本页跑的不是最新代码」的**确定性**信号，不需要自己造版本口径（§8 红线 5：同一口径不写第二份实现）。 |
| 顶栏改用 Tailwind 工具类（免得动 `style.css`） | **否决** | React 侧的既有写法是 `style.css` 里的语义类名（`.skip-link` / `.app-header` / `.nav-item`）；Tailwind 在那侧只有 `components/account-ui.css:1-2` 一处 `source(none)` + `@source "../account.ts"` 的窄口子。跟着既有写法走，不为省一次 `style.css` 改动而另立体系。 |

**提示条文案**：用户原话是「有新版本，点击刷新」。落地为文案 `有新版本可用` + 按钮 `刷新` + 按钮 `稍后`
—— 按钮本身就表达了「点击刷新」，同一行里再写一遍「点击刷新」是重复。若用户想要逐字文案，改一处字符串即可。

## 验收标准

1. `apps/web/tests/pwa-update.test.ts` 全绿；**先红后绿** —— 红的那次要贴出失败值。
2. `e2e/react/pwa-update.spec.ts`：
   - SW 已接管本页时，一次 `controllerchange` → 顶部出现提示条；点「刷新」→ 页面确实重新加载；
   - **没有被 SW 接管时**（默认工程 `serviceWorkers: "block"`）派发同样的事件 → **不出现**提示条
     （这是「首次安装的 claim 不算新版」的防误报回归）；
   - `e2e/react/offline.spec.ts` 不回归（离线能力没动，但要跑一遍确认）。
3. `npm run build`（typecheck → lint → 单测 → 各 workspace 构建）本地跑通；云端 Cloudflare 构建 + CI 全绿。
4. 线上：push 后，用**已经被旧 SW 控制**的浏览器（不清缓存）等一次再发版 → 顶部出现提示，
   点「刷新」即切到新版，**不需要 Ctrl+Shift+R**。
