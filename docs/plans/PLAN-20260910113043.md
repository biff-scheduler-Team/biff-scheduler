## 1. 需求

承接 `PLAN-20260910111844`(PDF 解析器)的遗留问题盘点,用户选定先修两件:

1. **修 `subs` 多值丢失** — 解析器把「官方同时印多个字幕标识」的第二值丢掉,静默丢数据。
2. **注册 `talk` / `commentary` / `event` 三个徽章** — 解析器已产出这三个 tag,但前端徽章注册表里没有,渲染时被静默忽略。

## 2. 问题定位(已核实)

### 2.1 subs 多值丢失

2025 册子里 4 场同时印两个标识(实测单元格):

| 页 | code | 场馆 | 原文 |
|---|---|---|---|
| p9 | 028 | c3 | `10:30~11:48 028 15 KE KK  78’ 126` |
| p9 | 029 | c3 | `… KE KK …` |
| p10 | 109 | c3 | `… KE KK …` |
| p12 | 268 | c3 | `… KE KK …` |

`extract_schedule.py` 的 `parse_meta()` 原写法:

```python
if out["subs"] is None and RE_SUBS.match(t):
    out["subs"] = t
    continue
```

只有第一个值被接走,第二个 `KK` 落进 `extra`,而 `extra` 在写 JSON 前被剥掉(只喂给 `notes` 参与打 tag)
→ **静默丢数据**。旁证:自检里 `cells_with_extra: 4`,这 4 个格子恰好就是上面这 4 场。

p8 官方图例:`KE` = 韩字 + 英字/英配 · `KN` = 韩字 + 非英外语 · `KK` = 韩字 + 韩配 · `NO` = 无对白。
`KE KK` 的语义 = 「有韩字 + 有英字,且配韩语对白」——**两个标识是叠加关系,不是二选一**,所以正确模型是数组。

### 2.2 三个 tag 未注册

`src/badges.ts` 的 `screeningBadgeKeys()` 里:

```ts
if (!defByKey.has(k)) return; // 未注册的键忽略,向前兼容
```

解析器产出 `tags` 分布 `{opening:1, closing:1, talk:6, commentary:3, event:1}`,
但 `BADGE_DEFS` 只有 `gv / masterclass / premiere / open_talk / batch`
→ `talk` / `commentary` / `event` 被全部静默吞掉(共 10 场),`opening` / `closing` 也没注册。

官方语义(取自册子 p101–p102 Community BIFF 页):
- `Talk` = **토크** — 对谈 / 分享场(2025 例:커비북스 / 잇츠시네마 的 book & food talk)
- `Commentary` = **실시간 양방향 코멘터리 픽쳐 쇼** — 实时双向评论音轨场
- `Event` = **연계이벤트** — 联动活动场(2025 例:907 라이브 드로잉 现场作画)

## 3. 方案

### 3.1 `subs` 改数组(三层贯通)

| 层 | 文件 | 改动 |
|---|---|---|
| 类型 | `src/types.ts` | `subs?: SubsKey` → `subs?: SubsKey[]` |
| 解析 | `tools/extract_schedule.py` | `parse_meta` 里 `subs` 初始化 `[]`,命中 `RE_SUBS` 就 append(去重);写行时 `meta["subs"] or None`(空数组落 `null`,与 `subs?` 可选语义一致);自检输出改多值统计 |
| 渲染 | `src/legend.ts` | `appendMetaRow` 里单值 chip → 循环;新增 `subsKeys()` 归一化 helper,**兼容旧数据**(demo `public/schedule.json` 里 `subs` 是标量字符串) |
| 判空 | `src/grid.ts` | `s.subs` → `s.subs?.length`(避免 `[]` 真值导致渲染空 chips 行) |

### 3.2 注册三个徽章

`src/badges.ts`:

- `BADGE_DEFS` 追加 `talk` / `commentary` / `event` 三条(label + 中文 hover 说明 + cls)。
- `ABBR_LINES` 追加三条 → `abbrTooltip()`(图例「ⓘ 缩写说明」)自动收录。
- 顺带把 `字幕 KE / KN / KK / NO` 那行补上「可同时标注多个(如 KE KK)」。

**配色**:档位色(`--pri-*` 蓝/紫/灰蓝)、红绿灯(`--status-*` 红/黄/绿)、等级色(`--rate-*` 绿/橙/深红)
都已被占语义,不复用。新增一族**青绿**(teal,`--ev-teal`),用「实心 → 实线描边 → 虚线描边」三种视觉权重区分:

| key | 语义 | 样式 |
|---|---|---|
| `talk` | 对谈 / 分享场 | 实心青绿底 + 白字(与 `gv` 的实心黑同族,表达「有人到场」) |
| `commentary` | 实时双向评论音轨场 | 青绿实线描边 + 青绿字(表达「额外音轨」) |
| `event` | 联动活动场 | 青绿虚线描边 + 浅青底(表达「非正式活动」) |

token 加在 `src/style.css` 的 `:root` + `@theme`(遵守「颜色唯一色源 = :root」约定)。

> 注:`opening` / `closing` 两个 tag 本次**不注册**(开闭幕式各只有 1 场,已在标题行标注
> 「개막식+개막작」/「폐막식」,加徽章是重复信息)—— 留作后续判断。

### 6.5 过程记录(踩坑)

1. **`git commit` 会被并行会话的暂存区污染**:提交时发现对方已把 `src/engine.ts` / `src/library.ts` /
   `src/pick.ts` / 其 PLAN **放进同一个 index**。直接用 `git add` + `git commit` 会把对方在途改动
   卷进本提交 → 改用**独立临时 index**(`GIT_INDEX_FILE=/tmp/biff_my_index` + `git read-tree HEAD`
   + `update-index --add`)提交;并**先**把本改动同步进真实 index,避免对方随后提交时把本改动
   「回退」(index 里旧 blob 会盖掉新 HEAD)。
2. **blob 精确暂存 `src/style.css`**:对方在同文件里改 `--pri-*-soft`,用
   `git show HEAD:src/style.css` → 打上本改动 → `hash-object -w` → `update-index --cacheinfo`。
   核对方式:`git diff` 暂存区 vs 工作区,差异应**恰好只剩对方那 7 行**。
3. **首次 staging 脚本写错**:替换块里重复带上了锚点行 `--rate-19: #6e1522;` → 暂存 blob 出现重复行。
   已加「相对 HEAD 只增不删 + 关键声明各出现 1 次」的自检,修正后 +8 行 / -0 行。
4. **1Password SSH 签名被拒**:沙箱内报 `1Password: failed to fill whole buffer`、沙箱外报
   `agent refused operation` → 解锁 1Password 后恢复。签名 key 指纹
   `SHA256:DgzR1G74W7u7O4LAs7rfj5L30bOnnps/pPFQvna4U7s` 与 agent 内 `id_ed25519` 一致
   (`ssh-add -l` 能列 key 但签名被拒,是「已锁」而非「缺 key」的典型表现)。
   → 结论:**提交 / 推送要在沙箱外跑**,且 1Password 需处于解锁态。
5. **对方在等待期间两次推进 HEAD**(`18829d7 test` → 改写为 `10c6c39`)。因当时**未推送**,
   改写没有污染远程 —— 验证了「提交前先确认 HEAD 是否在自己操作期间变过」这条纪律的价值。
   若当时贸然 push,对方的改写就会变成一次 force-push 事故。

### 6.8 关于「厅和楼能不能都要」

用户提问:`厅和楼不能都要吗 这两个能定位到唯一的影厅?` —— 结论:**厅级 id 本身就唯一,再单独存一个
楼级 id 是冗余**,理由:

1. `venue_id` 取官方影院代码小写(`b1` / `c2` / `l10` / `cx` / `bt`),**已经唯一确定一个影厅**;
   「楼」是它的前缀集合,属于**可派生信息**,不是第二个键。
2. 前端 `Venue` 已有 `code`(官方代码,如 `B1`)与 `group`(建筑分组 `bcc` / `cgv` / `lotte`…),
   「楼」这一层其实**已经存在** —— 只是字段名叫 `group` 而不叫 `building`。
3. 真正的冲突不是「要不要楼」,而是**两套口径并存**:
   - `public/venues.json`(2026 demo)= **楼级** 5 条,id 是 `bcc-1` / `cgv-centum` 这类**自造 slug**,
     官方代码塞在 `code` 字段,分区叫 `group: haeundae`;
   - 解析器产物 = **厅级** 29 条,id = 官方代码小写,分区叫 `region: centum / nampo`。
   两者混用会让 `data.ts` 的 `venueById` **全部 miss**。
4. 建议(待确认后执行):统一到**厅级 id**;`group` 承载建筑(`bcc` / `cgv` / `lotte` / `kofic` /
   `sohyang` / `bcm` / `megabox`);把解析器的 `region` 合进来(或统一改名);并补 `GROUP_AREA`
   的 7 个建筑映射(现在只有 `bcc` / `centum` / `haeundae`,其余会渲染成 `—`)。
   即:**「楼」用 `group` 表达,不新造第二个 id**。
