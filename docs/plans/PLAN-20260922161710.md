# PLAN-20260922161710 — 红黑榜：默认档「按总数」在首屏要名副其实

## 目标

用户 2026-09-22 提问：

> 默认页面的排序 和总数 红数 黑树 只看我的 这四个筛选里面 默认排序是按什么排的 好像既不是总数 也不是红数 也不是黑数 也不是只看我的

**复盘结论（已实测，非推测）**：默认档位**确实是「总数」**（`mode ?? "total"`，chip 也是 `aria-pressed=true`），
判据是**全量票数（红 + 黑，含我自己那一票）**降序、并列时按目录序稳定排。三档判据都没错，
「只看我贴过」是**筛选**（`only=mine`，与 `sort` 正交），本来就不是第四档排序。

问题出在**时机**：排序发生在**票数到达之前**。

- 首屏时 `votes` 是空表（`peekFilmVotes()` 在硬刷新后为空）→ `crowd` 为空 → `sortByCounts` 把每部都判成 0 分
  → 并列规则 `|| a.index - b.index` 是稳定排序 → **原样返回 `boardFilms(films)` 的顺序 = 影片库目录序**。
- 票数到了**不会重排** —— 这是 2026-09-16 用户要的「顺序冻结」（原话「跳动很频繁」）。

实测（本机 mock，卡片 chip 上的数是全量票数）：

| | 前 10 张（key = 总数） |
|---|---|
| 首屏 | `f001=101 f002=92 f003=0 f004=46 f005=27 f006=8 f007=123 f008=138 f009=119 f010=0` —— **不降序**；且这几部在 `films.json` 里的下标正好是 **0..10**（= 目录序） |
| 点「重新排序」后 | `160 159 159 159 157 156 155 154 154 150` —— **严格降序** |

**用户拍板（2026-09-22）**：

> 默认按总数排就行了吧

**本期要达成的结果**：默认档「按总数从高到低」在首屏就是真的。

## 范围

**做：**

1. **票数落定后自动补排一次**（仅一次）：`loadFilmVotes()` 结算（成功或失败都算结算）之后触发一次
   `setSortTick(n => n + 1)`，让首屏那次「全部并列 0」的排序被真正的总数排序覆盖。之后照旧冻结。
2. **用户已经动过手就不补排**：`scroll` / `pointerdown` 任一发生过就跳过这次补排 ——
   否则在读的人会被整页重排顶走（这正是当年「跳动很频繁」的痛点）。
   用户没等到补排时，界面上那条「有新贴纸 · 重新排序」照旧亮着，手动排一次即可。
3. **测试**：E2E 补两条（票数落定后第一张就是票最多的那一部；票数落下前用户已滚动 → 不补排、提示亮着），
   并订正既有的首屏断言（原来断言首屏**亮着**「有新贴纸」，补排之后它不该亮）。

**不做：**

- **不改三档判据本身**（总数 / 红 / 黑仍按 `sortByCounts` 的 `crowd` 口径），也不动「只看我贴过」的筛选语义。
- **不做骨架屏等首屏闸门**（方案 C）：那会削弱现在「接口没上线也能用」的优雅降级。
- **不把默认档改名成「目录序」**（方案 B）：用户已明确「默认按总数排就行」。
- **不动顺序冻结机制**：补排只有**一次**，之后票数变化仍不重排，提示机制原样保留。
- **不动 canvas / 贴纸交互 / 持久化契约**。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| A 票数落定后无条件补排一次 | 否决 | 慢网下用户可能已经在读，整页重排会把他顶走 |
| **A′ 票数落定后补排一次，但用户已滚 / 已点过就跳过** | **采纳** | 默认档名副其实，又不会在用户眼皮底下重排；跳过时界面上的「有新贴纸 · 重新排序」本来就是给这种情况准备的 |
| B 不改行为，把默认档改叫「目录序」+ 加一句说明 | 否决（用户已选 A′） | 零跳动，但要用户读文案；且榜单第一印象仍然没有信息量 |
| C 等票数再渲染列表（骨架屏） | 否决 | 首屏被接口往返挡住，削弱「接口没上线也能用」的降级 |
| 把 `crowd` 并进 `sorted` 的依赖，让它跟着票数随时重排 | 否决 | 就是 2026-09-16 被否掉的「跳动很频繁」 |

## 验收标准

1. 打开榜单 → 票数落定后**自动**排成总数降序：第一张卡就是票数最多的那一部（`data-film-key` 可断言）。
2. **只补排这一次**：之后再贴一枚 / 票数变化，顺序不动，且「有新贴纸 · 重新排序」按既有口径亮起。
3. 票数**落下之前**用户已经滚动 → **不补排**（顺序仍是目录序），「有新贴纸 · 重新排序」亮着。
4. 票数接口失败 / 空表 → 不产生任何重排，页面照常可用。
5. 收口命令：`npm run verify:quick` + 三浏览器跑 `e2e/react/redblack.spec.ts` 与 `smoke.spec.ts` 全绿。

## 验收结果（2026-09-22）

- `apps/web/src/pages/RedBlackPage.tsx`：`votesSettled` 状态 + `resortedRef`（只补一次）+ `touchedRef`
  （`scroll`（capture，覆盖任意滚动容器）/ `pointerdown` / `keydown` 任一即置位）+ 补排 effect；
  `sortTick` 的声明上移到 `crowd` 之后（补排要用它）。
- E2E 新增两条、订正一条（`e2e/react/redblack.spec.ts`）：
  - 新增「默认档『按总数』在首屏就是真的」：票最多的那一部要跑到第一张，且不留下「有新贴纸」提示。
  - 新增「票数落下之前用户已经在滚 → 不补排」：读接口用 Promise **扣住**模拟慢网，先滚再放行；
    ⚠ 这条踩到一个跨引擎差异 —— **WebKit 不支持 `page.mouse.wheel`**（仓库 `vertical-schedule.spec.ts`
    也为它分过支），改用 `window.scrollBy`（同样会派发 `scroll` 事件）。
  - 订正「重拉同一份票数不算『有新贴纸』」：首屏不再亮提示（补排之后顺序已经是按最新票数排的），
    把原来「先断言亮着、点掉它」那三步删掉。
- **先红后绿**：把补排的 `if (touchedRef.current) return;` 门槛去掉后，「不补排」那条立刻变红；
  恢复即绿。
- `npm run verify:quick` 全绿；`e2e/react/redblack.spec.ts` 三浏览器 **51 passed**。
- 口径已同步 `docs/CONVENTIONS.md`「红黑榜榜单排序口径」。
