## 现状事实（代码 + 官网核实）

### 1. 已保存方案里「顺位」恒为 1 —— 所以必须带备选

方案快照 = 每个冲突组第 1 顺位 + 共同场次：

```ts
// apps/web/src/app/agenda-model.ts:6-9
export function topPlanCodes(plans: Pick<PlanSet, "common" | "groups">): string[] {
  return [...plans.common, ...plans.groups.map((group) => group[0])];
}
```

只给方案内的场次打顺位，每场都印「顺位 1」，朋友无法分工；而备选场次在快照里已被丢掉，
只能从**当前行程**的冲突组取（`plans.groups` 组内已按顺位排好 + `plans.rankOf` 归一化 1..n）。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 顺位取方案快照内的次序 | 否决 | 方案每组只留第 1 顺位，恒为「顺位 1」，朋友无法分工 |
| 顺位 + 备选取当前行程的冲突组（`plans.groups` / `plans.rankOf`） | **采纳** | 备选本来就活在行程里；不另算一套顺位 |
| Open Cinema 按影片 `unit` 判 | 否决 | 实测两头错（漏 3 场、多算 4 场室内重映），见现状事实 §2 |
| Open Cinema 按 `venue_id === "bt"` 判 | **采纳** | 与官方公布的 8 部片单逐部吻合；且官方定义就是 outdoor screenings |
| 不确定的场次单列「批次待确认」 | 否决 | 官网 1 批品类是穷举的，其余必然第 2 批；多一个分组只会让页面更难读 |
| Community BIFF「不在排期里、无需判别」（初稿结论） | 推翻 | 见「修订 1」—— 它其实是官方编号 901–942 的 42 场，且官网 1 批品类里就点名了它 |
| 批次规则做成可覆盖的映射数据文件 | 否决 | 判据已能逐场对上官方 8 部片单，先落纯函数；真出现对不上的场次再加覆盖层 |
| 「抢票」挂在我的行程页顶部 | 否决 | 用户明确选「新增导航页」，且它是独立任务视图（抢票当天看的就是它） |
| 抢票页自己算倒计时 / 票价 / 票种 | 否决 | 复用 `ticketOpens()` / `countdownText()` / `priceOf()`，避免第二套口径 |
