# 第一部分：评审结论（分级清单）

## 🔴 阻断（6 条）

### R1. D1 聚合计数「读-改-写」非原子 → 并发永久丢更新

位置：`apps/api/src/want-store.ts:46-95`、`film-vote-store.ts:26-41`、`screening-stats-store.ts:96-113`、
`telemetry-store.ts:46-74`、`ticket-stats-store.ts:31-64`

```ts
// want-store.ts:52-63
const nextSum = Math.max(0, parseWeight(row.weight_sum) - previousWeight);
if (nextSum <= 1e-9) { await db.delete(filmWantStat)...run(); }
else { await db.update(filmWantStat).set({ weight_sum: String(nextSum), updated_at: now })...run(); }
```

机制：先 `SELECT` 旧值 → JS 加减 → 写回。D1 无跨语句事务（仅 `db.batch` 原子），并发时双方各读到同一旧值 → 丢更新。
放大因素：`replaceContributorWants` 只在「贡献行有差分」时修正聚合，若贡献者已在集合内则**永不再修正** → 聚合永久偏低、不自愈。

### R2. 每个 ping 在请求路径上串行 3×N 次 D1 写 → 超时 / 超 D1 额度

位置：`apps/api/src/want-store.ts:67-95`（screening / ticket / telemetry 同构）；上限声明 `apps/api/src/index.ts:719-723`

```ts
// want-store.ts:67-95
for (const filmKey of added) {
  await db.insert(filmWantContribution).values({...}).onConflictDoNothing().run();
  const row = await db.select().from(filmWantStat).where(...).get();
  if (row) await db.update(filmWantStat).set({ weight_sum: ... })...run();
  else await db.insert(filmWantStat).values({...}).run();
}
```

机制：`MAX_*_PER_PING = 500` → 首次上报约 1500 次串行 D1 子请求，必然超时或触发每 invocation 查询上限；
且不在 `waitUntil` 内，用户在请求路径上等待。

### R3. 无限流；仅靠 `Origin` 校验，脚本可伪造 → 统计/遥测可被刷

位置：`apps/api/src/index.ts:142-143`、`475-509`、`734-767`（另 532 / 589 / 657 三个 ping）

```ts
// index.ts:142-143
if (!["GET", "HEAD"].includes(c.req.method) && c.req.header("origin") !== origin)
  return c.json({ error: "FORBIDDEN_ORIGIN" }, 403);
```

机制：`Origin` 客户端可控，只挡浏览器跨站（CSRF），挡不住脚本；5 个 `*-ping` 对匿名开放，身份是可无限铸造的匿名 cookie。

### R4. telemetry 同一 target 累加无总上限（可一次灌 200×100）

位置：`apps/api/src/telemetry-stats.ts:130-137`；契约常量 `packages/contracts/src/telemetry.ts:34,37`

```ts
const count = Math.min(raw, MAX_HITS_PER_TARGET);   // 单条封顶 100
const existing = out.get(key);
if (existing) existing.hits += count;               // 200 条同 key → 20000
```

### R5. 冲突提示手拼时间区间，把 24+ 时制原值印给用户

位置：`apps/web/src/grid.ts:191`

```ts
return `${c}《${title}》${o.start_time.slice(0, 5)}–${o.end_time.slice(0, 5)} · ${vTxt}`;
```

午夜场会显示 `23:59–29:35`（应为「次日 05:35」）。同文件顶部已 import `fmtMinRangeMin`，
`types.ts:12-16` 明确要求显示走 `fmtEndClock` / `fmtMinRange` —— 这是「场次行区间」的第二份实现。

### R6. 账号缓存损坏 → 同步永久失效；离线无法登出 → 共享设备残留他人数据

位置：`apps/web/src/account-sync.ts:51-53`、`237-242`、`460-473`

```ts
// :51-53 无容错
function cacheFor(owner: string): Cache {
  const raw = localStorage.getItem(cacheKey(owner));
  return raw ? cacheSchema.parse(JSON.parse(raw)) : emptyCache();
}
// :240 在 try(243) 之前
cache = cacheFor(owner);
```

```ts
// :460-473 登出与网络强耦合
export async function signOutAccount() {
  remember();
  try { await api("/api/account/logout", { method: "POST", ... }); }
  catch (error) { if (!(error instanceof ApiFailure && error.status === 401)) throw error; }
  activate(null);   // ← 上面抛错就到不了这里
  setStatus("guest");

```

机制 ①：脏 JSON 抛错会冲出 `initAccountSync`，此时 `iffday:workspace-change` / `online` / `focus` / `storage`
监听与 20s 定时同步**全都还没挂上** → 此后任何改动都不再同步，须手动清 localStorage。
机制 ②：断网/超时（12s）时 `activate(null)` 不执行 → `owner` 与 `biff.*` 仍是 A 的数据。

## 关键代码结构

计数聚合的唯一写入口（API 侧各 store 统一形态）：

```ts
// 原子增减：避免 SELECT → JS 加减 → UPDATE 的丢更新
const stmts = [
  db.insert(contribution).values({ ...row, weight }).onConflictDoNothing(),
  db.update(stat)
    .set({ weight_sum: sql`max(0, ${stat.weight_sum} + ${delta})`, updated_at: now })
    .where(and(eq(stat.edition, edition), eq(stat.film_key, filmKey))),
];
await db.batch(stmts as [typeof stmts[0], ...typeof stmts]);
```

（`max(0, ...)` 仅作兜底，仍须在批次结果里检测负漂移并打点告警；具体列名以各 store 现表为准。）

1. **B1**：单次 ping 上报数十条条目时 D1 调用次数为**常数级**（批次数可数），且结果与逐条等价；
   并发（或模拟交替）增减同一 contributor 后聚合值等于期望；贡献行无差分时聚合仍正确。

   mock 网络失败后登出仍清空本地 owner 与 `biff.*` 归属。
5. **B5**：性能改动给出**可比对数字**（hover 一次的全树渲染次数 / `setOption` 调用次数 / `derive` 重算次数），
   前后对比写明测量口径；不接受「应该更快了」。
6. **B6**：`text-[Npx]` 与任意值类名清单清零（除仍有正当理由并写明注释者）；
   `javascript:` 协议的外链不可达；非法 `createdAt` 不再整页崩；死组件删除后 `RushAnalysisPage` 正常。

## 修订 2（2026-09-23，B1 实现中）

**触发原因**：B1 原写「单次上报上限从 500 降到几十条量级」。

**改动**：**不降 API 层的 `MAX_*_PER_PING`（保持 500，行为零变化）**，
把「几十条量级」落在**批量粒度**上（`apps/api/src/stat-batch.ts::STAT_BATCH_SIZE = 40`）。
验收标准第 1 条随之改为「往返次数常数级 + 块内原子」，不再要求降上限。

**理由（代码事实，非推测）**：这几个 ping 的语义是**整份替换**——
`replaceContributorWants` / `replaceContributorScreenings` / `replaceContributorVotes` /
`replaceContributorTickets` 都拿客户端发来的**全集**与库里已有贡献行做差分，多出来的当「移除」。
而客户端自己就在截断：`apps/web/src/want-counts.ts:50`（`.slice(0, 500)`）、
`apps/web/src/screening-counts.ts:76`（`.slice(0, 500)`），
`apps/web/src/film-votes.ts:19` / `ticket-stats.ts:28` 与 API 侧常量逐字对齐 500。
若服务端上限降到几十条，用户行程 / 想看超过该阈值时，服务端会把「客户端截掉的那部分」当成主动移除而
**静默删贡献** —— 这比写放大更严重，且专砸最活跃的用户。
所以只改「怎么写」（分块 batch：往返从 3N → N/40 + 1），不改「收多少」。

**验证**：`apps/api/tests/stat-atomicity.test.ts` 的「一次 200 条上报」用例同时钉住了
`outsideRuns === 0`（写全在批次内）与 `outsideRaws === 1`（只有一次读往返）。

## 修订 3（2026-09-23，B2 实现中）—— 必须让用户知道的一条**未完全关闭**的风险

**改动**：限流落在 `apps/api/src/rate-limit.ts` 的 **isolate 内存固定窗口计数器**上
（`PING_RATE_LIMIT` 60 次/分、`LOOKUP_RATE_LIMIT` 30 次/分），**没有**新增 KV / Durable Object 绑定
（那份 `wrangler.jsonc` 变更按原计划留给用户先确认）。

**必须明说的后果**：因此 🔴 R3（无限流 → 统计/遥测可被脚本刷）**只被部分缓解**：

- 已挡住：单个来源对同一 isolate 的暴力刷（成本从「零」变成「要跨 isolate」）。
- **仍未挡住**：攻击者跨 isolate（或等冷启动）时计数重置；`Origin` 头仍可伪造。
- **真正关掉这条风险需要在 Cloudflare 控制台配 Rate Limiting Rules / WAF**（针对
  `/api/stats/*-ping` 与 `/api/eats/lookup`）—— 这件事**仓库里做不到**，需要人工执行或授权新增绑定。

**待用户裁决**（本 PLAN 第 4 节「待确认」之外的新增项）：

| 选项 | 代价 | 效果 |
|---|---|---|
| A. 只保留内存限流 + 人工在 CF 控制台配规则 | 需要一次人工操作，仓库零改动 | 推荐：CF 层才是权威闸门 |
| B. 新增 KV 命名空间做跨 isolate 计数 | `wrangler.jsonc` + 绑定 + 每次写 KV（有小额费用） | 中等幅度提升，但仍弱于 CF 规则 |
| C. 新增 Durable Object 做精确计数 | 新增 DO 类与绑定，成本最高 | 最精确，但为这个体量过度 |

**在用户裁决前，本 PLAN 把 R3 记为「已缓解，未关闭」**，并在 `rate-limit.ts` 文件头写明边界。

**验证**：`apps/api/tests/rate-limit.test.ts`（固定窗口行为 4 例 + edition 白名单 1 例）；
`apps/api/tests/telemetry-stats.test.ts` 新增「累加后总量封顶」用例 —— 先红（实测 `hits: 20000`，
期望 `100`，用 `git stash` 临时退回未修实现取得），后绿。
