# PLAN-20260916154255 — 讨论区直接按场次 code 发帖

## 目标

用户原话（逐字保留）：

> 讨论区也能直接通过 Code发帖

澄清后的口径（用户在本轮问答中选定）：**在全站讨论区页面上直接输入 / 选择「场次 code」发帖**，
不必先进某一场的行程卡弹层。

还原成机制：`/discussions` 目前有**两个**发帖入口，两个都要求场次已知 ——

1. 方格墙里某个**已存在的帖子**格子上点「进入讨论」（`DiscussionsPage.tsx:86-103`）；
2. `/discussions?focus=<code>` 定位条上的「发帖」（`DiscussionsPage.tsx:224-242`）。

也就是说：**无 `focus` 的 `/discussions` 上没有任何发帖入口**。用户想在讨论区这一页上直接把帖子
发到某一场 —— 手上知道场次编号（比如「0412」），不想先绕去行程页点卡片、也不依赖那一场是否已有帖子。

## 范围

**做：**

1. `apps/web/src/app/schedule-search.ts`（新）：把 `TransferAddDialog.tsx:24-40` 的 `matchScreenings`
   **原样提出来**成为唯一实现（按官方场次编号 / 英文名 / 韩文名 / 中文名模糊匹配，按日期 + 开场时间排序，
   上限 20）。`TransferAddDialog` 改为 import —— 同一口径不允许存在第二份实现（红线 5）。
2. `DiscussionsPage.tsx`：`panel-heading` 增加常驻的**「发帖」**按钮（无 `focus` 也在场）。
   点击后在该位置**内联展开**一个场次选择区（不新开弹层，避免与讨论弹层叠加）：
   - `SearchField`（label「场次编号或片名」，placeholder 沿用既有说法「如 419 / 峡湾 / Fjord」）；
   - 候选列表复用 `matchScreenings`，每行显示「片名 · 场次 code · 日期 开场时间 · 影院」，行尾「发帖」；
   - 输入非空但无命中 → 沿用既有文案「没找到这一场。编号要写官方 3 位（如 001），片名中英文都可以。」；
   - 「收起」按钮复位。
3. 选中场次 → 关闭选择区、打开**既有的** `ScreeningDiscussionDialog`（发帖 / 反应 / 删除 / 社区提醒的
   唯一实现），`onPosted` 接讨论区既有的 `prependPost`，让新帖立刻出现在方格墙首位。
4. 样式落 `apps/web/src/components/screening-social.css`（新增 `.discussion-picker*`），不碰 `style.css`。
5. `e2e/react/screening-social.spec.ts`：新增一条用例 —— 无 `focus` 打开 `/discussions`，点「发帖」、
   按场次编号搜到那一场、直接发布，断言新帖出现在方格墙首位且定位条/计数口径不变。
6. `scripts/test-map.json`：把新文件 `apps/web/src/app/schedule-search.ts` 补进 `screening-social` 规则的
   paths，并 `node scripts/affected-specs.mjs --write-doc` 同步 `docs/TEST-MAP.md`。

**不做：**

- **不改接口 / 表结构 / 分页口径 / 鉴权** —— 发帖仍是 `POST /api/screenings/:code/discussion` + 登录门闸。
- **不引入第二份 composer** —— 分类白名单、正文长度、社区提醒、登录门闸全部留在 `ScreeningDiscussionDialog`。
- **不做嵌套弹层**（选择器不是 `Dialog`）—— 两层级 modal 的焦点归还风险不值得换那点版面。
- **不新增 `biff.*` 键**，不动 `biff.discussionprivacy.v1`。
- **不做自由文本发帖 / 无场次帖子** —— 帖子必须挂场次，这是接口与表的既有契约。
- **不做「场次不在当前排期也能发帖」**（`cat.byCode` 无此项就不给发，与定位条的既有判据一致）。
- **不动 `style.css`**（命中 TEST-MAP `allOn` → 三浏览器全量 E2E）。
- **不动 `legacy/`、不动 `TransferAddDialog` 的行为**（只换 import 来源，UI / 文案 / 断言零变化）。
- **本轮不推送** —— 本地跑通 + 起 dev server 交用户验收，用户确认后才推。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 把 `matchScreenings` 提取为 `app/schedule-search.ts` 共用 | **采纳** | 转票补入与讨论区发帖是同一个问题（「按编号/片名找到那一场」），抄第二份必然漂移（红线 5） |
| 「发帖」按钮 → **内联展开**场次搜索区 → 选中后开讨论弹层 | **采纳** | 任意时刻只有一个 modal；页面默认仍是干净的方格墙；最贴合「直接输入/选择 code 发帖」 |
| 「发帖」按钮 → 先开一个**场次选择弹层**，选中后再开讨论弹层 | **否决** | 两层 modal 交接（关闭选择器 + 打开讨论层同帧发生）的焦点归还无可靠保证；换来只是省一行版面 |
| 页面常驻一个搜索框（不折叠） | **否决** | 方格墙是这个页面的主体，常驻搜索框会把它挤成次要内容 |
| 在讨论区**再写一份**行内 composer | **否决** | 分类 / 正文上限 / 登录门闸 / 社区提醒会立刻出现第二套口径（红线 5） |
| 支持「场次不在当前排期也发帖」 | **否决** | 弹层要渲染片名与时间（`ScreeningDiscussionDialog` 依赖 `Screening`），无场次对象渲染不出来 |
| 用 `DialogContainer` 承载讨论弹层以便选择器也做成弹层 | **否决** | 能跑通但引入跨 modal 的隐式时序，收益为零 |
| 同时把定位条上的「发帖」入口也搬过来统一 | **否决** | 定位条那个入口是上一轮 `PLAN-20260916102631` 的成果，语义是「已定位到某场就发这一场」，与本轮「自己挑一场」是两个场景，都保留 |

## 验收标准

1. 无 `focus` 的 `/discussions` 上，「发帖」按钮可见；点击后出现场次搜索框与候选列表。
2. 输入场次编号（如 `001`）或片名都能命中；输入 `zzz` 之类的无命中串时显示「没找到这一场」提示。
3. 点某一行的「发帖」→ 打开 `<code> 场次讨论` 弹层，社区提醒 / 分类 / 正文 / 登录门闸与格子上进的**完全一致**。
4. 登录后成功发布 → 关掉弹层，方格墙**首位**立即出现该帖（`prependPost` 同一口径）。
5. 「转票补入」弹层的搜索行为与文案零变化（只换 import 来源）。
6. `npm run typecheck` / `npm run lint` / `npm test` 全绿；`npm run check:repo`、`npm run check:test-map` 通过；
   `screening-social` spec 通过（贴出计数与断言）。
7. 本地 dev server 可交互，交用户本地验收；**未获用户确认前不推送**。
