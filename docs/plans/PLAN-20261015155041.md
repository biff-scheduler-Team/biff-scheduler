# PLAN-20261015155041 — 红黑榜：午夜联映块（Midnight Passion）也拆成成员片

## 目标

> 用户原话：「还有个问题是刚刚有刷到一部 midnight passion 3 但是我记得 jim queen 在
> mid night passion 2 里有场次 但是可以单独打分 这种打分也要拆下」

口径确认（2026-10-15，用户单选）：

- **拆的落点** = 红黑榜：「联映块不再单独成卡计票（和 Asian Short Film Competition 那次一样，
  块卡 `sched:midnight passion 3` 从红黑榜 / 排行榜下架，只留成员片各自成卡、各自贴票）+
  会补「搜 269」落到成员片」。
- **「打分」** = 红黑榜的红 / 黑票（不是豆瓣评分）。

现状（代码事实，用 2026 版真实产物核过）：

- `PLAN-20261014112444` 已把 8 个「短片竞赛 / 双片连映」合集拆成成员片，但**明确排除了**
  `Midnight Passion 1/2/3`（code `075` / `168` / `269`）—— 判据是「成员片在榜上别无落脚点才拆」，
  而 MP 的 9 部成员**自己就有场次**（实测：Sapiens `040/232/539`、The Chain of Roses `037/205/685`、
  The Spiral `163`、Spirit Guardians `161/316/419/641`、The Scar-Faced Cat `153/462`、
  `L’Autre` `385/697`、Jim Queen `414/555`、Welcome to Dolly′s House `093/196/376/711`、
  Angel′s Egg `009`），所以在榜上**已经**各有一张卡。
- 于是榜上同时存在 `sched:midnight passion 3`（块）与 `cat:f211`（Jim Queen）两张卡 ——
  用户要的是**块卡不再单独计票**。
- 现有拆法靠 `FilmNode.block.code` 倒排，而 MP 成员是**排期节点**（`buildFilms` 只在「纯目录片」
  那一支挂 `block`），倒排**天然查不到**它们。
- `films.json` 的 `block_code` **不可靠**：`168` 的成员在官网已由 `Red Thread` 换成
  `Spirit Guardians…`（`PLAN-20261015142133`），而 `films.json` 里 `f113`（Spirit Guardians）
  **没有** `block_code`，按 `block_code` 倒排只能解出 2 / 3 → 会被保守判据挡下、拆不掉。
  → 所以本轮改用**联映块自己的官方成员名单** `screening.midnight_members`（它就是「谁在这个块里」
  的唯一来源）按**片名**解析。

## 范围

**做：**

- `apps/web/src/redblack.ts`：在 `boardFilms` 的拆解里加**第二支**判据 —— 块节点（
  `shows[].midnight_members` 非空）的成员先按既有 `block.code` 倒排，倒排不齐时再按官方成员名
  与榜单里 `FilmNode.en` / `names` 做归一匹配；**两支护斥**、都要求「解析出的成员卡数 == 官方成员名数」，
  否则原样保留（宁可少拆，也不拆出一张空洞）。
- `apps/web/src/redblack.ts`：新增 `boardCards(films) → { films, blocks }`，`boardFilms` 保留为
  薄封装（分享图 / 排行榜只要 `films`）；`blocks` = 卡片 key → 该卡所属的联映块场次，供搜索认块编号 / 块名。
- `apps/web/src/redblack.ts::searchBoardFilm(film, query, blocks?)`：多接一个「这张卡所属的块」入参 ——
  拆掉块卡之后，「搜 269」必须落到 3 部成员片上，否则会从「搜到 1 张块卡」变成「一张都不剩」。
- `apps/web/src/pages/RedBlackPage.tsx`：榜单那一份改取 `boardCards(films)`，搜索把 `blocks` 传下去。
- 单测：`apps/web/tests/redblack.test.ts`（合成夹具：MP 块拆开、成员名解析不全时原样保留、
  `searchBoardFilm` 认块编号）+ `apps/web/tests/model-parity.test.ts`（真实产物：三张 MP 块卡不在榜上、
  9 部成员片都在、搜 `269` 命中它们）。
- E2E：`e2e/react/redblack.spec.ts` 一条（搜 `269` → 成员片卡可见、块卡不在）。
- 回写 `docs/CONVENTIONS.md` 的「红黑榜榜单口径」那一条（判据由「别无落脚点才拆」改成两支护斥）。

**不做：**

- 不动影片库 / 排片表 / 我的选片 / 我的行程：`app/model.ts`（`buildFilms`）与
  `library.ts::searchFilm` **一行不改** —— 影片库里 `Midnight Passion 3` 那张节点照旧。
- 不动分享图与排行榜的**排序 / 门槛**口径：它们仍然走 `boardFilms`，只是候选集合少了 3 张块卡。
- 不做「旧块票搬到成员片」的一次性迁移（本地 `biff.redblack.v2` 与服务端 `film_vote_*` 里的
  `sched:midnight passion *` 留在库里、只是不再有卡片显示）—— 与 `PLAN-20261014112444` 同一处置。
- 不动豆瓣评分 / 影片资料弹层的联映成员列表（`ScreeningMemberList`）—— 用户没选那一档。
- 不碰工作区里在途的「排行榜」「窄屏 hero」未提交改动之外的任何文件。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 按 `FilmItem.block_code` 倒排（与现有 8 个合集同一支） | 否决 | `f113`（Spirit Guardians）在 `films.json` 里**没有** `block_code`（Red Thread 换片只同步了 `schedule.json`），倒排只能解出 2 / 3 |
| 在 `buildFilms` 里给 MP 成员补 `block` 指针 | 否决 | `FilmNode.block` 的契约是「**仅合集成员**（该片没有独立场次）」；给有独立场次的片挂上会让影片资料弹层对 9 部片多印一句「收录于合集」，属于超范围的行为变更 |
| 只删块卡、不补搜索 | 否决 | 「搜 269」会一张都不剩，比原问题更糟（`PLAN-20261014112444` 已经踩过一次同样的坑） |
| 块卡与成员片并存、只把块卡上的票「借」给成员 | 否决 | 违反「一部片一张卡、一部一枚票」的既有口径，且票的归属会变得没法解释 |
| 两支护斥：先 `block.code` 倒排，不齐再按官方成员名匹配 | **采纳** | 既保住 8 个合集的既有行为（逐字不变），又能覆盖 `midnight_members` 这一份官网口径；两支护斥 = 不会互相污染计数 |

## 已知代价（写清楚，不偷偷改口径）

- 榜单卡片数 **317 → 314**（-3 张块卡；9 部成员片本来就在榜上）。三张块卡上的历史贴纸
  （`sched:midnight passion 1/2/3`）在榜上不再有卡片，本地 / 服务端数据都不删；hero 的「全站」小计
  因此少掉这部分票 —— 与 `PLAN-20261014112444` 的处置一致。
- 红黑榜分享图的候选集合同样少 3 行（它读同一支 `boardFilms`）；`Midnight Passion` 这个**单元**
  在分享图的单元筛选里照旧有 9 部成员片，不会变空。
