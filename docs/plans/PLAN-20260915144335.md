# PLAN-20260915144335 — 影片库「午夜单元」成员补齐（主单元 ∪ 联映块单元）

## 目标

用户原话：

> 排片网站的午夜单元只有五部 https://www.biff.kr/eng/html/program/prog_list.asp?c_idx=438

截图证据：影片库单元下拉显示「Midnight Passion，午夜激情，**5 部**」。

官网同一单元页列出的是 **9 部**（见「现状事实」第 2 条），我们的影片库少数了 4 部。
本需求让「午夜单元」的成员与官网一致，且不破坏其它单元的计数。

## 现状事实（均为实测，非推测）

1. **下拉计数口径**：`apps/web/src/app/model.ts::libraryUnits()` 对 `public/films.json` 每部片的**单值** `unit` 做 `unitKey()` 归并计数；筛选 `filmInUnit()` 同样只看 `item.unit`。`5 部` 就是这么来的。
2. **官网成员 = 9 部**：`prog_list.asp?c_idx=438` 英文页与韩文页各抓一次，各列 8 条且**各缺一条不同**——
   英文页缺 `Welcome to Dolly′s House`，韩文页缺 `Angel′s Egg`；**两者并集 = 9 部**。
   该并集与我们 `public/schedule.json` 里 3 个联映块的成员表**逐字吻合**，且成员片长之和与块时长完全相等：
   | 块 | code | 成员 | 时长校验 |
   |---|---|---|---|
   | Midnight Passion 1 | 075 | Sapiens / The Chain of Roses / The Spiral | 101+83+115 = 299 ✓ |
   | Midnight Passion 2 | 168 | Red Thread / The Scar-Faced Cat / L'Autre | 126+108+98 = 332 ✓ |
   | Midnight Passion 3 | 269 | Jim Queen / Welcome to Dolly′s House / Angel′s Egg | 86+88+72 = 246 ✓ |
   → 官网 section 页 = 联映块成员并集 = **9 部**（不是 8 部；单页缺的那条是页面渲染问题）。
3. **我们为什么只有 5 部**：`films.json` 里 `unit == "Midnight Passion"` 的正好 5 部（Chain of Roses / Welcome to Dolly′s House / Scar-Faced Cat / L'Autre / Red Thread）。
   另外 4 部的主单元在别处：Sapiens = `Korean Cinema Today – Special Premiere`、Jim Queen = `Korean Cinema Today`、Angel′s Egg = `日本动画特别企划`、The Spiral = `Open Cinema`。
   `unit` 是单值字段，表达不了「主单元 A + 同时属于午夜联映块 B」。
4. 该坑在管线里已有记录（`tools/build_films_2026.py::find_catalog` 头注：xlsx 把同一部片登记在两个单元，实测 4 组含《不速之母》《天使之卵》），且**刻意**只保留非午夜那条以避免同一部片出现两张卡片。故不能靠「把 unit 改成 Midnight Passion」来修。
5. `FilmItem.block_code` 已存在（`types.ts:128`），块成员片已被管线标记；但**块的单元名没被记录**，前端无从得知 `block_code` 属于哪个单元。

## 范围

**做：**

1. **A（管线）** `tools/build_films_2026.py`：给「联映块成员」的目录条目登记块单元 —— 新增 `also_units: ["Midnight Passion"]`，并给「只在块里出现」的新建条目补上块单元。
2. **B（前端）** 单元归属收敛成**唯一口径** `app/model.ts::unitsOfFilm(film)` = 主单元 ∪ `also_units`；`libraryUnits()`（计数）与 `filmInUnit()`（筛选）都改走它。卡片在「另属某单元」时补一行可见提示。
3. **产物**：按 A 重新生成 `apps/web/public/films.json`（离线，输入用 `/tmp/biff2026/films-web.json`），并核对与提交版只差新字段。
4. **回归测试**：`apps/web/tests/model-parity.test.ts` 加一条断言（午夜单元 9 部 + 其它单元计数不被扣减），先红后绿。
5. 口径变更写进 `docs/CONVENTIONS.md`。

**不做：**

- 不改 `unit` 字段本身（`unit` 仍是唯一身份：卡片副标题、排期匹配都认它）。
- 不新增重复的目录条目（同一部片仍是**一张卡片**）。
- 不动 3 个联映块场次自身（`Midnight Passion 1/2/3` 是场次不是影片；把它们计进单元会让计数虚增到 12）。
- 不改 `unitKey()` 的归并规则、不改 `units.ts` 对照表。
- 不做「按块筛选场次」这类新功能。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| A：管线登记块单元（`also_units`） | **采纳** | 块单元名是**官网数据的确定性事实**，应由管线一次算好；前端去解析块名（`"Midnight Passion 3"` 去掉尾号）等于把口径抄第二份，违反「口径单一来源」 |
| B：前端 `unitsOfFilm()` 统一并集 | **采纳** | 计数与筛选必须同源，否则会出现「下拉说 9 部、点进去 5 张卡」 |
| C：把 4 部片的 `unit` 改成 Midnight Passion | **否决** | 它们会从原单元消失；且与管线「消灭重复对」的既有口径冲突 |
| D：像 `data/films-catalog-2026.json` 那样造重复条目 | **否决** | 同一部片会出现两张卡片 |
| E：只改前端（从 `schedule.json` 的块成员表现推） | **否决** | 需在前端解析块名 → 第二份口径；且 `libraryUnits()` 吃的是 `FilmItem[]`，拿不到 schedule 上下文 |
| 块成员片是否连**块场次**一起进 `shows` | **不做** | 块的 `title_en` 是「Midnight Passion N」，按片名匹配本就对不上；成员片各自的场次已足够，强行挂块会污染行程/冲突计算 |

## 验收标准

1. 单元下拉「Midnight Passion，午夜激情」显示 **9 部**；选中后列表能筛出 9 张卡（含 Sapiens / Jim Queen / Angel′s Egg / The Spiral）。
2. `Open Cinema`（5 部）、`Korean Cinema Today – Special Premiere`、`日本动画特别企划` 的计数**不被扣减**（同一部片在两个单元各计一次，属预期）。
3. 「亚洲电影人奖 4 部」等既有断言仍绿（`libraryUnits` 计数与 `filmInUnit` 命中数保持相等的不变量）。
4. 新增回归测试先红（5 部）后绿（9 部），失败值贴进提交 body。
5. `npm run verify` 全绿 + 受影响 spec 全绿（`public/films.json` 命中 TEST-MAP `allOn` → 需跑全量 E2E）。
6. 部署后线上核对：单元下拉出现「9 部」，且 asset hash 与本地构建一致。
