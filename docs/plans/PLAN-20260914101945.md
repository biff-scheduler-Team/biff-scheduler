# PLAN-20260914101945 — 把「PR 流程」与「大重构前 checkpoint」写进规范

用户原话：

> 请你改一下我的 PLAN 和 RULE 对齐他的开发规范 "反过来，citron 有两点值得保留
> PR 流程：Verified 签名 + Review 记录，比直接 push 到 main 更有可追溯性。
> 大重构前打 checkpoint：4feda07 chore: checkpoint before integrating React scheduler —— 大规模改造前留一个干净的落点，这个习惯是对的，只是它没把这条规矩用在后续的粒度上。"

即：上一轮提交复盘（对比 `gaaiyeoi` 121 条 vs `citron` 14 条）得出的**两条值得从 citron 侧吸收**的做法，
当前三层规范（`AGENTS.md` / `docs/DEVELOPMENT-STANDARDS.md` / `RULE.mdc`）**都没有写**，需要补成可执行条款。

## 范围

**做：**

  §6 补一条「PR 分支不部署」；§9.3 大重构档位补「先打 checkpoint」这一启动动作；§10 变更记录加 v7。
- `AGENTS.md` §4：加两条 bullet（PR 流程 / checkpoint），并同步 §9.1 表格下方的 checkpoint 说明。
- `.codebuddy/rules/biff-development-standards/RULE.mdc`：与 `AGENTS.md` 等价同步。
- `PLAN.md` §0：回写本轮状态。
- **顺带订正**：`AGENTS.md` / `RULE.mdc` 里「绕过它只能用 `--no-verify`，而那是**红线 12**」的编号错误
  —— `--no-verify` 根本不在 §8 红线清单里，红线 12 是 `wrangler pages deploy`。改为指向 §4 禁止项。

**不做：**

- **不改任何 `*.ts` / `*.tsx` / `*.json`** —— 纯文档改动。
- **不改 `.github/workflows/ci.yml`** —— `on: pull_request` 早已存在，本轮只是把「什么时候该走 PR」写进规范。
- **不把 PR 设为强制** —— 默认仍是直接 `push main`；只有三类改动必须走 PR（见 §4.5）。
- **不新增红线** —— 红线已 15 条；这两条靠 §4 / §9 约束，不靠红线膨胀。
- 不引入 GitHub 分支保护规则 / 签名强校验（属仓库设置，不在本仓库文件范围内）。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| PR 设为**强制**（所有改动都走 PR） | 否决 | 与 §0 / §2「push 即部署、推的时候直接推」冲突；小改动（单文件修复 / 文案）走 PR 是纯开销。且这是两人协作的自用工具，不是团队仓库 |
| PR 只在 §9.3 大重构档位提一句 | 否决 | 依赖升级（Dependabot 自动开 PR）、D1 迁移这两类也需要 PR，散落两处必漏 |
| 新增 §4.5 / §4.6 两个小节 | 采纳 | 与 §4 提交规范同域；编号接在 §4.4（会话草稿落点）之后，不打断既有编号 |
| checkpoint 写进 §8 红线 | 否决 | 红线是「违反即返工」的硬约束；「没打 checkpoint」不会直接产生错误提交，它的代价是**出问题时回退成本高**，属纪律而非红线 |
| checkpoint 只写「先提交一次」 | 否决 | 必须强调**checkpoint 自身必须全绿** —— 否则别人 `git pull` 到的是坏 HEAD（§7）；且必须写明它**不能替代原子提交** |

## 验收标准

1. 三层规范都能搜到「PR 流程」与「checkpoint」两节，且口径一致（`AGENTS.md` / `RULE.mdc` 为摘要，
   `DEVELOPMENT-STANDARDS.md` 为完整版）。
2. `npm run verify:quick` 全绿（check:repo · check:test-map · typecheck · lint · 单测）。
3. `git diff --stat` **只含 `*.md`**（无 `*.ts` / `*.tsx` / `*.json`）。
4. `PLAN.md` §0 有本轮条目。
