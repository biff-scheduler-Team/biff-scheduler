# PLAN-20260924141442 — 我的行程：日程表上的「票」标注（张数 / 座位 / 账号）

## 目标

在**我的行程 → 日程表**上给每一场标注自己手填的票务明细，并把这信息纳入行程概览。

> 用户原话（2026-09-24）：
> 「我的行程中加一个显示自己有几张票的组件」
> 「自己标记即可 就是在日程表上标注一下张数 自己输入就行」
> 「是在日程表上可以右键编辑 然后显示在日程表上 能填上座位号 在设置中配置 biff 的官方网站的账号密码
>  能提供快速跳转对应的票务 然后每一张票也能单独设置账号 因为可能票在不同账号里面」
> 「票里面能单独设置账号 否则默认按设置中的账号来」

拆成 6 条可验收的行为：

- **B1 张数**：每一场可手工填「几张票」（默认不填 = 1 张）。
- **B2 座位号**：每一场可填座位号（一场可能多张 → 每张一个座位号）。
- **B3 账号覆盖**：每一场可指定「这张票属于哪个账号」；**不指定 = 用设置里的默认账号**。
- **B4 账号表**：设置弹层里维护 BIFF 官网票务账号（名称 / 用户名 / 密码）+ 指定默认账号。
- **B5 快速跳转**：从票务明细一键打开 BIFF 票务站，并一键复制该账号的用户名 / 密码。
- **B6 标注显示**：日程表格子上标出「N 张」；行程概览条给出「共 N 张票」。

## 范围

**做：**

- `我的行程`（`AgendaPage`）的**日程表档**（`GanttScope = "agenda"`）上的右键编辑入口 + 格子票数标注。
- 行程概览条（`.agenda-overview`）新增一枚「共 N 张票」tag。
- 设置弹层新增「BIFF 票务账号」区（账号增删改 + 默认账号）。
- 新增两个 localStorage 键（见下「数据契约」）与对应纯逻辑模块、单测、E2E。

**不做（写清楚，防范围蔓延）：**

- **排片表档不做右键**（`GanttScope = "schedule"`）。用户说的是「我的行程中」；
  排片表上右键还叠着浏览器原生菜单的使用习惯，先不动。
- **不做密码自动填充**。`ticket.biff.kr` 是跨域站点，本站没有任何合法手段往它的登录框里写值。
  能做到的是「打开站点 + 把用户名 / 密码复制到剪贴板」，UI 文案必须这么说，不能暗示会自动登录。
- **不把账号 / 密码写进 `biff.*`**。理由见「方案取舍 D2」，这是本 PLAN 的硬约束。
- **不改 `biff.tickets.v1` 的结构与语义**（三态 / 转票口径原样）。
- **不动 `legacy/`**（只读回退件）。
- 不做「票的备注 / 价格 / 订单号」等用户没提的字段。
- 不做服务端任何改动（`apps/api` 不碰）。

## 数据契约

### 1. `biff.ticketinfo.v1`（随账号云同步，与 `biff.tickets.v1` 同性质）

```jsonc
{
  "008": { "count": 2, "seats": ["F12", "F13"], "accountId": "a2" },
  "033": { "count": 1 }                          // 座位 / 账号都可缺省
}
```

- 键 = 场次 `code`；`count` 为正整数（未填 = 1）；`seats` 长度 ≤ `count`；
- `accountId` 缺省 = 用设置里的默认账号。
- **只增不改**：将来再加字段走同一个新 key 的字段级兼容（读取时逐字段归一）。

### 2. `iffday.workspace.ticketaccounts.v1`（**本地专属：不上云、不进备份**）

```jsonc
{
  "accounts": [
    { "id": "a1", "label": "主号", "username": "me@example.com", "password": "..." },
    { "id": "a2", "label": "朋友号", "username": "friend@example.com", "password": "" }
  ],
  "defaultId": "a1"
}
```

- `password` 允许为空串 = 「不保存密码」；
- `id` 用 `crypto.randomUUID()`，只在本机有意义。

## 验收标准

1. **单测**（新增 `apps/web/tests/ticket-info.test.ts`，node 环境）：

   - `accountFor(code)`：有覆盖 → 覆盖；覆盖 id 不存在 → 回落默认；无默认 → `null`；
   - prune：场次移出行程后明细同步消失。
2. **E2E**（新增 `e2e/react/ticket-info.spec.ts`，desktop-chromium）：
   - 行程日程表上右键某场 → 弹层 → 填 2 张 + 座位 → 保存 → 格子上出现「2 张」；
   - 概览条出现「共 N 张票」；
   - 刷新后仍在（落盘）；
   - **阴性对照**：`storage(page)` 里**出现** `biff.ticketinfo.v1`，**不出现**任何 `iffday.` 前缀键。
3. **既有 spec 不回归**：`compatibility`（全键等值那两条）、`screening-social`、`parity-agenda`、`agenda-gantt` 全绿。
4. **门禁**：`npm run verify:quick`（含 `check:repo` / `check:test-map`）通过。
5. **人工**：设置里加两个账号（其中一个密码留空）→ 某场指定第二个账号 → 点「打开票务」能跳 `ticket.biff.kr`；
   点「复制密码」剪贴板拿到的是第二个账号的密码。

## 风险与已知取舍

1. **明文密码**：存的是本机 localStorage 明文，同源脚本 / 拿到该设备的人可读。
   → 缓解：只在 `iffday.workspace.*`（不上云、不进备份）；UI 明示「只存这台设备，请勿在公用设备保存」；
   密码留空即「不保存」；不进任何 E2E 存储快照。
2. **跨域无法自动填充**：能做的只有「打开站点 + 复制凭据」。文案不得写成「自动登录」。
3. **`biff.ticketinfo.v1` 上云、账号表不上云**：换设备后 `accountId` 会失配 → 由 D5 兜底回落默认账号。
4. **新键与「载入路径不写盘」约束**：一旦实现里顺手在载入时写了默认值，`compatibility.spec.ts:228` 会红。
   写的时机只有一个：用户点「保存」。
5. **票数 ≠ 场次数**：`实际 N 场` 与 `共 N 张票` 两个 tag 并存，UI 上必须能一眼分得清口径。

## 修订 1（2026-09-24，实现期）

需求没变，实现时在 PLAN 未展开的三处细节上做了取舍，记在这里免得下次重猜：

1. **座位数组「保位对齐」**：下标 = 第几张票，故归一化只收**尾部**空项、保留中间空项。
   「丢掉所有空值」的常规写法会把「第 3 张是 14」读成「第 2 张是 14」。
   （`ticket-info.ts::normalizeSeats`，单测 `★ 座位数组保位对齐` 钉住。）
2. **填了「1 张 + 没座位 + 跟随默认」= 不记明细**：保存时等价于清掉这一条
   （`TicketEditDialog.tsx::save`）。否则「打开看一眼就保存」会给每一场留一个 `{count:1}`，把格子徽章糊满。
   代价写明：这一档下「显式填 1 张」无法与「没填」区分 —— 但两者在概览里的计数结果本来就一样。
3. **账号用户名必填、密码可留空**：读取归一（`normalizeAccountsFile`）会丢掉没有用户名的账号，
   若不在保存时显式挡下，就会表现成「保存后账号凭空消失」。故设置弹层保存前校验一次并提示。
   「恢复默认设置」**刻意不动账号** —— 那是用户录入的数据，不是偏好。

另外：`tickets.ts::staleTicketCodes` 放宽成泛型（`<T>`）供三态与明细共用 ——
prune 判据完全相同，不该写第二份实现；既有断言不受影响。

## 修订 3（2026-09-24，撤销账号方案 + 票数改为座位行数派生）

触发原因（用户原话）：

> 「有账号密码之后 能做到直接跳转订单页吗? 不行的话还是不要存账号密码了 直接留一个备注区域吧」
> 「不需要备注了 直接通过操作去添加座位表吧 这样比较简单 比较好 用添加的座位数作为票数」

### 3.1 先答那个技术问题（撤销的依据，**实测**）

| 查到的事实 | 结论 |
|---|---|
| `https://ticket.biff.kr/` → 302 → `https://biff.maketicket.co.kr/` | 真正售票的是**第三方域** |
| 登录入口 `/BIFF/en/mypageLogin`；官方退票原文 `biff.kr → Login → My page → Details → Select the ticket` | 订单页在登录态后面，而这个登录态由**另一个域**掌管 |

跨域 ⇒ 本站①写不进它的登录框、②建不了它的会话。所以「跳订单页」**不依赖我们存任何东西**
（用户自己在那边登录过就能进 My page），存密码只换到「手动复制再粘贴」——
收益≈0，代价是明文密码躺在本地磁盘（`backup.ts` 还会把它写进**可以随手发给朋友**的导出备份）。
**决定：账号 / 密码方案整体撤销，不留任何键、任何字段。**

### 3.2 最终形态：座位表 = 票数

- 字段：`biff.ticketinfo.v2` = `Record<场次 code, {seats: string[]}>`。
  **票数一律由行数派生**（`ticket-info.ts::ticketCountOf`），`count` 字段删除 ——
  用户口径是「加一张座位 = 多一张票」，两个来源必然打架，只留一个。
- 交互：弹层里一张票一行（`第 N 张 [座位号] [删除]`）+「＋ 添加一张」+ 实时「N 张票」。
  空行**也是**一张票 ⇒ 归一化**不许收尾部空项**（修订 2 时为了「不留空壳」收过，现在反过来）。
- 备注：用户先提出、随后自己否掉（「不需要备注了」）—— 不做，`TicketInfo` 里没有这个字段。
- 迁移：按 AGENTS §5「改结构必须新 key + 一次性迁移 + 删旧 key」——
  `migrateTicketInfoV1` 把 v1 的 `count` 折算成「补齐到那么长的座位行」，`accountId` 直接丢弃，迁完删 v1。
  只有本机**没有** v2 时才走迁移（v2 存在即权威，绝不被 v1 覆盖）。
