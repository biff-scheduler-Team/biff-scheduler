# PLAN-20260917120454 — 修红:`eats.spec.ts` 分区筛选断言抢跑,CI 连续 4 轮挂同一条

用户贴回的 CI 结果:`2 failed / 2 skipped / 397 passed`,`eats.spec.ts:94 搜索与分区筛选`
在 `desktop-chromium` 与 `mobile-webkit` 两个 project 上失败(各重试一次仍失败)。

## 现状(代码事实,非推测)

**失败点**(`gh run view 35178246251 --log`):

```
Error: expect(received).toBeLessThan(expected)
Expected: < 38
Received:   38
  112 |   const east = await shuffled.count();
  113 |   expect(east).toBeGreaterThan(0);
> 114 |   expect(east).toBeLessThan(total);
```

**不是本轮引入的**:同一断言自「吃喝」页落地起就红,行号随文件增长漂移(84 → 114)——
`35121283980`(feat eats)、`35123813041`、`35172824078`、`35178246251` 四轮 CI 全挂同一条。

**根因:测试抢跑,应用无 bug。** 本地起 `vite preview` + 探针脚本
(`.scratch/probe-eats.mjs`,临时,已删)实测时间线:

```
option clicked, immediate  n=38  search=?district=donggu   ← URL 已更新,DOM 还没提交
+366ms                     n=38  search=?district=donggu
+393ms                     n=1   search=?district=donggu   ← 过滤生效
```

即:点 `东区` 后 URL **同步**变成 `?district=donggu`,但 React 的重渲染要 ~30ms 才提交 DOM;
而 `await locator.count()` 是**一次性取数**断言,不重试 —— 读到的是过滤前的 38。
本地机器快,刚好卡在提交之后;CI runner 慢且 3 project 并发,两次重试都输掉这场竞速
(mobile-chromium 同轮通过,正是「快慢差」的旁证)。

数据侧也确认 `东区`(= `donggu`)只有 1 家(`halmae-gukbab`),过滤正确时 `east` 必然 < 38,
所以断言本身是**对的、有牙的** —— 只是读得太早。

## 范围

**做:**
- `e2e/react/eats.spec.ts:112` 的「先行取数 → 即时比较」改成**会重试的 web-first 断言**,
  口径与同仓库先例 `e2e/react/redblack.spec.ts:47`(`expect.poll(() => cards.count()).toBeLessThan(total)`)逐字一致。

**不做:**
- 不改 `EatsPage.tsx` / `query-search.ts` / `QuerySearchField.tsx` —— 应用行为正确,改实现就是「为测试变绿改实现」(红线 4)。
- 不动 `eats.spec.ts` 里其余断言(它们的 matcher 本身就会重试)。
- 不动其它 spec:全仓扫过 `= await …count();` 只有 eats 这两处,`total` 那处取数前已 `toBeVisible` 等到清单渲染。
- 不借机重构 / 不顺手改搜索框。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| `await expect.poll(() => shuffled.count()).toBeLessThan(total)` | **采纳** | 重试到过滤生效为止;断了 filter 照样红(有牙),口径与 redblack 先例一致 |
| `await expect(shuffled).toHaveCount(1)` | 否决 | 把 `eats.json` 里 `donggu` 的家数写死 —— 表格一改就假红(本文件已刻意不写死 40 家) |
| 加 `await page.waitForTimeout(300)` | 否决 | 靠睡等,慢机器照样翻车,且掩盖真实回归 |
| 改 `query-search.ts` 让导航同步提交 | 否决 | 应用行为正确(URL 即时、DOM 下一拍),为此改实现是红线 4 |
