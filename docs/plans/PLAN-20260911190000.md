# PLAN 2026-09-11 19:00 — 档位降级为「冲突顺位」+ 抢票视图

> 需求(用户原话):「选排片的时候不需要选想看等级 然后只有冲突的时候才需要选想看等级怎么样 然后加上方案 3?」

## 1. 核心转向:档位从「主数据」降级为「冲突组的排序键」

现状:`Priority`(must/maybe/wild)是**影片级主数据**,被 8 处消费(`score` / `library` 排序与筛选 /
`ai::buildPayload` / `ai::planMerge` / `picklist` / `ics` / `agenda` / `grid`)。

问题:用户挑场次时被迫先回答「这部片多想看」,但档位**真正有决策价值的场景只有一个 —— 冲突二选一**
(两场时间重叠,必须保一场)。其余场景里它只是一个"排序依据",而排序可以退化为添加顺序。

新定位:

* **挑场次 = 纯几何操作**:点一下加入 / 移出,不弹档位、不要求打标。
* **档位 = 冲突组内的顺位**:只在冲突出现时让用户回答「保哪场」。
* **影片库 ★ 保留但不再强制**(仍是「我想看什么」的入口,可选;不打标也能正常排片)。

## 2. 关键决策

### D1. 顺位保持**影片级**,不改成场次级

冲突绝大多数是**不同影片**争同一时段(真实痛点);同片多场互相冲突是边缘情况,取消一场即可。
改场次级会破坏 `PickEntry.priority`「档位只有一份且在影片级」的核心设计(`state.ts` 文件头)+ 需数据迁移,收益小。

### D2. `must / maybe / wild` 的 key 与文案**不变**

数据结构与现有文案(必看 / 备选 / 随缘)保留 —— 本轮只改它**出现的位置**(从「挑场次时」移到「冲突时」),
不引入新枚举、不改 localStorage 结构、零迁移。

### D3. 档位 UI 的出现条件 = 冲突场次

* 网格卡 ★:常显 → **仅冲突卡显示**(未设时显示空心 ☆,点开即设顺位)。
* 行程行 ★:**仅冲突行显示**。
* 影片库卡 ★:保留(可选入口),但**不再是排片前置条件**。
* 「我的选片」档位筛选 chips:改为 **「全部 / 有冲突 / 无冲突」**。

### D4. 下游口径调整(**必须**,否则功能被拆掉)

| 消费者 | 现状 | 新口径 |
|---|---|---|
| `ai.ts::buildPayload` | **只送 `priority ≠ null` 的片** | 改为送 **`store.picks` 里有记录的片**(否则不打标就没片单,AI 排片直接空转) |
| `score.ts::scorePlanRows` | must×3 / maybe×2 / wild×1,unset 不计分 | unset 按 **wild×1** 计(「排了就算数」),避免全站分数塌成 0 |
| `library.ts::pickNodes` | 按档位 `rankOf` 排序 | 未设排最后;全未设时退化为稳定添加序 |
| `picklist.ts` | 按档位排序 | 改为**按冲突组聚簇**排序(见 §3) |
| `agenda.ts` / `grid.ts` ★ | 常显 | 仅冲突场次 |

### D5. 新增「抢票」tab(方案 3)

选片抽屉第 4 个 tab,**按时间带(冲突组)聚合**,而非按日平铺:

```
9/17 周三
┌ 18:00–20:40 · 3 场重叠 ──────────────────────┐
│ ① 001 片A  18:00–20:39  BCC1   [必看]          │  ← 顺位 1
│ ② 042 片B  18:20–21:00  CGV3   [备选]          │
│ ③ 098 片C  19:00–21:30  Lotte  [未设] ⚠        │  ← 未设 → 提示就地设顺位
│   结果: [① 已抢到] [② 售罄] [③ 待抢]            │
└───────────────────────────────────────────────┘
```

* 组内按顺位排序,未设排最后。
* 每场一枚**抢票结果**三态:`won`(已抢到)/ `lost`(售罄)/ `pending`(待抢)。
* 点「已抢到」→ 该场成为实际行程;同组其余场次**灰显保留**(不删除,用于记录"没抢到")。
* 售罄 / 已抢到的同组落选场次:**不进 `.ics` / 复制清单**(口径见 §5 待确认 3)。

### D6. 冲突组(并查集)

`conflict.ts` 现只有 `conflictGroupFor`(一跳)。新增 `conflictGroups(result): string[][]` ——
按 `pairs` 建图做**传递闭包**,供抢票 tab 按组聚合、供行程折叠择一卡。

### D7. 移除 A/B 方案(`Group`)

A/B 的**原始用途就是「冲突隔离」**(PLAN.md §5:「冲突只针对同一方案内部;A/B 互不干扰」)——
而这正是「冲突组 + 顺位」要接管的事。两套机制解决同一个问题,合并成一套。

**收益**:

* 顶栏少一个常驻切换控件,概念少一个(用户不必理解「方案」);
* 修掉一个现存的坑:把冲突的两场分到 A / B,冲突就**看不见了**,但导出也分成两份(用户得手动合并)——
  去掉 A/B 后,分属两处 = 同一套里成冲突组,红标 + 顺位直接管到。

**唯一真实损失**(需用户确认):

* AI 排片的**多候选对比**(现在可「候选 1 → A、候选 2 → B」):改为「逐个预览、挑一个采纳 / 追加」——
  候选间的差异在新模型里由**冲突组的不同选法**表达;
* 「两套完整对比计划」的用法(如雨天 / 晴天):改为「一套计划 + 冲突组的 `won` / `lost` 结果」。

**做法(零迁移)**:UI 入口全删,数据字段 `PickSlot.group` **保留但不再读取** —— 旧数据里的 B 直接并入同一套。

### 再迭代(同日):删掉三态抢票结果

用户反馈「不需要已抢到和售罄这个选项吧,感觉这个组件有点多余」。**理由成立**:抢票在票务系统里完成,
在排片工具里追踪「已抢到 / 售罄」是多余的中间态(抢完就知道了,不需要工具记账)。

**删除**:`types.ts::TicketStatus`、`state.ts::ticketStatus` / `loadTicketStatus` / `setTicketStatus` /
`ticketStatusOf` 与 `biff.ticket.v1` 键、`agenda.ts::ticketRowEl`、`main.ts` 的 `[data-ticket]` 委托与
boot 里的 `loadTicketStatus()`;`buildRow()` 的 `opts` 收敛为 `{ inConflictGroup?: boolean }`。

**保留**:冲突组聚合 + 组内顺位排序 —— 择一卡仍有独立价值(把散落在时间轴上的几场聚到一起,
按抢票顺位排好),它解决的是「隔着几十行找不到冲突对方」,与三态结果无关。
