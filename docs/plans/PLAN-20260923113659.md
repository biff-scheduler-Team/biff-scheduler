### 一、T4 渲染次数量化（补齐验收标准第 5 条）

测量脚本：`.scratch/measure/measure.mjs`（会话草稿，不检入）。Playwright + 注入计量钩子：

- **React 提交次数**：注入 `__REACT_DEVTOOLS_GLOBAL_HOOK__.onCommitFiberRoot`（dev 构建每次提交都会回调）。
- **本次提交真正重渲染的组件实例数**：遍历 fiber，取 `actualStartTime > 上次提交结束时刻` 的节点。
  ⚠ 只看 `actualDuration > 0` 是**错的**：没参与本次提交的 fiber 会保留上次的时长，数出来恒等于「树里的组件总数」——
  静置与 hover 一样大（这是本脚本第一版踩过的坑，已在脚本注释里写明）。
- 页面 = `/schedule`，日期 = **2026-10-11（115 张场次槽位卡）**，fiber 总数 ≈8818。
- 协议 = **逐次 hover、逐次读数**，并做同样次数的「不动鼠标」等长基线相减：
  顶栏倒计时每秒都会全树重渲染一次（静置 1s 就有 1 次提交 / ~1800 个组件），不隔离它会把 hover 信号淹掉。

| 指标（20 次换卡 hover，观测窗 140ms） | 改动前（Context） | 改动后（模块 store） |
|---|---|---|
| hover 时间窗内的提交次数 | 30 | **5 ~ 13**（两次独立运行） |
| 窗内重渲染组件数合计 | 37638 | **266 ~ 767** |
| **单次提交重渲染组件数（典型值）** | **~1500–2100**（全树） | **~55–69**（只有受影响的卡） |
| 单次提交最长组件耗时 | 53–169 ms | **0.1–3.6 ms** |
| 净增 / 每次 hover（重渲染组件数） | 1876 | **14 ~ 36** |
| DOM 属性写入（基线 → hover） | 0 → 101 | 0 → 99 / 145（同一量级） |
| 静置基线（20×140ms） | commits=2, rendered=114 | commits=3, rendered=171 |

**结论**：单次提交重渲染组件数约 **−97%**、单次提交最长组件耗时从**数十毫秒降到毫秒级**。

### 四、T7 两条口径（✅ 都有结论；**T7-1 的结论与预期相反**）
