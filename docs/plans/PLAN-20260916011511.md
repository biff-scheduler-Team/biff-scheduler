# PLAN-20260916011511 — 备选按自己的开票批次归节(分享文案 / 分享图片)

## 目标

> 「我觉得抢票批次很重要 你看一下怎么去解决这个问题吧」

开票批次是**抢票当天唯一的时间轴**:第 1 批 9/17 开票时,人只扫「第 1 批」那一节去官网报 CODE。
而旧版排版把**备选块永远紧跟主选**,于是出现:

- 主选 `349`(一般放映,第 2 批)的备选 `806` 是 Actors' House(**第 1 批**)——
  `806` 被印在【第 2 批】节里,**第 1 批开票那天按节扫根本扫不到它**;
- 分享图片同口径(`buildPosterModel` 直接复用 `matesOf`),图上的备选行待在同一处错误的节里。

即:批次分节的粒度是「主选行」,而备选是场次级信息,两者不同粒度 ⇒ 抢票当天漏项。

## 范围

**做:**

- `share.ts`:新增 `shareUnits()`(打印单元:主选 / 被抬出来的备选),**与海报共用**;
  与主选不同批次的备选 → 抬成独立块(行首 `↳ `,顺位印「349 的备选②」),归自己的批次节。
- `share.ts::buildShareText` 改走 `shareUnits`;概要「共 N 场」仍只数主选行。
- `poster.ts`:`PosterRow.altOf`(脱离主选的备选行)+ 单独一行绘制(不画卡片),
  `buildPosterModel` 走同一份 `shareUnits`;`PosterDay.count` 不计这类行。
- 单测:文案 2 条(不同批次抬出来 / 同批次仍紧跟)+ 海报 2 条。

**不做:**

- 不动画布版式 / 配色 / 批次判据(`batch.ts::ticketBatchOf` 不变)。
- 不改「备选紧跟主选」这个默认形态 —— **只在开批次分节时**抬不同批次的那几条。
- 不动 `.ics` / 「查看场次」弹层(后者不传 `ranking`,本来就没有备选行)。
- 不给主选块补「你的备选在第 2 批」提示(先不加噪声)。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 备选按**自己的批次**归节(不同批次抬成独立块) | 采纳 | 抢票当天按节扫是唯一用法;备选行自带「349 的备选②」,不丢归属 |
| 备选**同时**在主选下面 + 自己批次节里各印一次 | 否决 | 清单翻倍;同一条 CODE 出现两次,群里报号会重复 |
| 不分批次(取消批次分节) | 否决 | 批次是抢票当天的时间轴,用户明确说「很重要」 |
| 所有备选一律抬成独立行(含同批次的) | 否决 | 同批次的备选紧跟主选正是「主选 + 备选同框」的意义,抬开反而难分工 |
| 海报上把抬出来的备选画成完整卡片行 | 否决 | 一张卡片 = 一张海报缩略图,会把备选抬到与主选同等的视觉重量;一行文字足够(它是备选) |
| 备选计入「共 N 场 / N 场」 | 否决 | 备选不是「要去看的那一场」,计进去场次行与概要会对不上 |

## 验收标准

1. 主选 004(第 2 批)+ 备选 003(露天场,第 1 批)→ 文案里 `↳ 003` 落在**【第 1 批】**节、
   印「004 的备选②」,004 落在【第 2 批】;同批次(003 + 005,都露天)的备选仍紧跟主选。
2. 海报模型:不同批次的备选 → `rows[0].altOf === "004"` 且在第 1 批节里、当天 `count` 不计数;
   同批次 → 仍是主选行的 `alts`。
3. 单测:`apps/web` 的 `share.test.ts` 24 条 / `poster.test.ts` 19 条全绿(本地实测 43 passed)。
4. 不勾 `batching` 时输出与旧版**逐字一致**(基线测试未改)。
