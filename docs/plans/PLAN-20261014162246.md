# PLAN-20261014162246 — 「热门影片」编辑式排行榜（Editorial Film Ranking）

## 目标

把榜单页的「热门榜」从「海报 + 想看条 + 角标」的排名列表，做成**编辑式编排的排行榜**：
榜首 #01 用大型海报 + 完整影片信息占据主视觉，第 2 名起是整齐的海报墙网格，
海报带**轻量 hover 动效**（缩放 1.03 + 渐变遮罩 + 信息淡入），并支持三个榜单切换。

用户原话（需求全文见对话）：

> 请在现有 BIFF Scheduler 项目中实现一个「编辑式热门影片排行榜」（Editorial Film Ranking），
> 整体参考 Letterboxd 的电影榜单，并融合独立电影杂志的编辑式排版。
> …不要直接重构整个页面，也不要修改与本功能无关的 UI 结构和业务逻辑。

## 前置勘查结论（动手前必须知道的三件事）

### 1. 技术栈不是「无框架」

需求写的是「Vite + TypeScript，不使用 React / Vue」。**实测不成立**：

| 事实 | 证据 |
|---|---|
| 主应用是 React 18 + React Router + React Spectrum S2 | `apps/web/src/**/*.tsx`（`main.tsx` 的路由表、`components/spectrum.ts`） |
| 旧的 Vanilla 实现仍在仓库里，但是**只读回退件** | `apps/web/legacy/`；AGENTS §5：「只接 P0 修复，**不接新功能**」；且 `apps/web/tests/legacy-snapshot.test.ts` 会在它变动时变红 |

⇒ 本功能用 **React + 项目既有 CSS 体系**实现。用 Vanilla 写等于往冻结件里塞新功能，违反 §5。

### 2. 位置：不是新页面，是「热门榜」这一档的呈现层重做

「热门榜」已经存在于榜单页（`/redblack`，页内 tab 热门榜 / 红榜 / 黑榜），数据源就是本需求要的
「想看人数」。所以**不新增路由、不动导航**：重做 `HotBoardPanel` 的呈现层 +
`hot-board.css` 的榜单样式，排序逻辑继续住在 `hot-board.ts`（纯逻辑、可单测）。

### 3. 数据口径（本需求最要紧的一节）

需求里的三项，实测**两项能真做、一项必须改名**：

| 榜单 | 需求口径 | 实测 | 结论 |
|---|---|---|---|
| 最受关注 | 「加入个人行程的去重用户数」 | 行程是 **per 场次**记录的（`screening_attendance_stat`，主键 `(场次, contributor)`），**没有 per 影片的去重用户数**。按影片把场次数加起来会把「同一人给同一部片排了 3 场」算成 3 —— 正是需求禁止的重复计数 | 改用**服务端 per 影片去重的「想看人数」**（`film_want_stat`，主键含 `contributor`，匿名 0.75 / 登录 1.0 加权）。它就是全站唯一「按人去重的影片级关注数」 |
| 正在升温 | 「最近 24 小时新增关注」 | 服务端有**逐日账本** `stat_daily`（`metric='want'`，`(metric, target, day)` 一行，只在增量上报时写差分）✔ 但**按 KST 日分桶**，滚动 24h 不可表达 | 做**「今日（KST）新增想看」**，并在界面上写明是「今日新增」而非 24 小时。需要**新增一个只读接口**把日账本按影片聚合出来 |
| 全部影片 | 「当前可用的全部影片」 | `buildFilms` 产出的影片节点（含无排期目录片） | 全量列出，按目录既定顺序（不加权排序） |

**排名变化**（▲▼）：可用日账本**反推昨日累计**（`昨日累计 = 当前累计 − 今日新增`）再对比名次 ⇒
是真实推导、不是伪造。**只在 Δ 名次 ≠ 0 时**显示；账本对该届为空时自然全不显示。

**全程不伪造**：不把 `want-counts` 说成「行程人数」，不把排片场次数 / 评分 / 页面访问量当热度。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 用 Vanilla 按需求字面实现 | 否决 | 项目是 React；Vanilla 那份是冻结的 `legacy/`，§5 明令不接新功能 |
| 「最受关注」用 per 场次行程数求和 | 否决 | 同一人排同一部片多场会重复计数，违反需求「不得重复计数」，且会把场次数伪装成人数 |
| 「正在升温」用前端 `localStorage` 存上次看到的累计数做差分 | 否决 | 那只是「你上次访问以来的差」，不是全站真实窗口；服务端账本已经存在，没理由退到本地近似 |
| 「正在升温」先用空态、等以后接接口 | 否决 | 数据支持（`stat_daily` 已有），只是没暴露；一个只读 GET 就能真做，空态等于交半成品 |
| 榜首 + 网格的**布局**用 React Spectrum 组件 | 否决 | S2 没有「编辑式海报墙」这类版式件；硬套会得到后台管理系统观感（需求明确避免）。仅**按钮 / 弹层 / 复选**继续用 Spectrum |
| hover 用 JS 驱动（`mouseenter` + state） | 否决 | 纯 CSS `:hover` + `transition` 更轻、无重渲染、天然跟随 `prefers-reduced-motion`，且不会因 React 重渲染丢状态 |
| 网格「分页」vs「显示更多」 | 采纳**显示更多** | 247 部片逐页翻会打断浏览；逐步 +24 既控首屏成本又保留浏览感 |

## 验收标准

1. 榜首有明显主视觉：桌面左右分栏（海报占 40%–50%、2:3）、移动端纵排；只展示真实存在的字段。
2. 第 2 名起是 4–5 / 3 / 2 列响应式海报墙（桌面 / 平板 / 手机），海报统一 2:3、对齐一致。
3. hover：`scale(1.03)` + 亮度变化 + 底部渐变遮罩 + 信息淡入，200–300ms `ease-out`；
   移出平滑复位；不裁切、不挤压邻格、不挡点击；`prefers-reduced-motion` 下关闭过渡。
4. 移动端**必要信息常驻**（排名 / 片名 / 想看人数不依赖 hover）；点击进入既有影片详情路由。
5. 三个榜单各自真的换数据：最受关注（想看降序）/ 正在升温（今日新增降序，无数据时明确空态）/
   全部影片（目录序，全量）。
6. 名次变化只在日账本反推得出且 Δ≠0 时显示。
7. `npm run typecheck` / `lint` / 单测全绿；受影响 E2E 在 desktop-chromium 上通过。
8. 除本面板外，其它页面与既有业务逻辑零改动（红黑榜、分享图、查票、排片表逐字不动）。

## 修订 2（2026-10-14，用户：热门榜的单元要下拉筛选）

用户原话：

> 热门影片的单元还是没有通过下拉筛选

### 目标

把热门榜刊头的单元筛选从「一排 `aria-pressed` 按钮」换成**真下拉**。

### 现状（动手前的代码事实）

`HotBoardPanel.tsx` 里那块是 `<div className="hb-units" role="group">` + 22 个 `.hb-unit-btn` 按钮，
由 `unitId` / `pickUnit()` 驱动；筛选口径 `rows.filter((row) => row.units.includes(unitId))`。
**它确实不是下拉** —— 在窄屏会折成好几行。

### 范围

**做：** `HotBoardPanel` 的单元控件换成 S2 `Picker`；`hot-board.css` 删掉 `.hb-unit-btn` 那节；
E2E 的断言随 DOM 更新（并补一条「选项只在 `role=listbox` 里出现」的形态断言，防止它退回去）。
**不做：** 不动筛选口径（仍走 `row.units.includes(unitId)`，联映块成员片同属多单元那条照旧）；
不动 `hot-board.ts`；不动分享图弹层里那支同款下拉；不动 `biff.*` 契约；不引新依赖。

### 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 保留按钮带，只让它横向滚动 / 加 `overflow` | 否决 | 用户要的就是下拉；横向滚动在手机上更难用 |
| 原生 `<select>` | 否决 | 全站「互斥选项挑一个」只有 S2 `Picker` 一种写法（`FilterBar` 的「场次类型」、影片库的「单元」、本页分享图弹层）—— 另起一支就是第二份实现（§5） |
| S2 `Picker`，选项文案沿用影片库那条「单元名，N 部」 | 采纳 | 零新依赖；与影片库 / 分享图同形同文案；`unitId`（空串 = 全部）与 `PickerItem` 的 id（**不能为空**）之间做一次 `unitId \|\| "all"` 映射 |
| 选项里继续印**想看合计**（旧按钮上那个数） | 否决 | 另两处单元下拉印的都是**影片数**（「N 部」），同一件事两种数才是真的绕（§5） |
