# PLAN-20260920161837 — 抢票分析模块（需求 → 难度 → 结果 → 口碑）

## 目标

把「票务」这件事从**需求 → 难度 → 结果 → 口碑**四个面量化出来，做成一个独立页面
（`/rush-analysis`），供用户在开票前判断该抢哪几场、哪些场次根本没戏，开票后复盘自己判断得准不准。

用户原话：

> 做一个抢票分析的模块 然后能看到某场抢票人数 然后你看看除了这个抢票人数 抢票难度 有什么好的统计维度 去量化目前整个票务

## 范围

**做：**

1. **抢票人数** —— 每场显示「同场 N 人」（该场出现在多少人的行程里）。**直接复用**已有服务端聚合
   `screening_attendance_stat`（`apps/web/src/screening-counts.ts` → `GET /api/stats/screening-counts`），
   **零新增需求侧采集**。
2. **抢票难度** —— 竞争倍率 = 需求人数 ÷ 影厅座位容量；按倍率分级（极高 / 高 / 中 / 低），
   并同时印出「需求人数 / 容量 / 倍率」三元组让分级可被复核。容量缺失的厅**不估数**，降级为
   「未收录座位数」+ 相对分位排名。
3. **需求面** —— 影片想看人数、需求集中度（Top 10 / Top 20 占比 + 承载全站一半需求所需的场次数）、
   需求时间分布（按日期 + 按开场时段两列）。
4. **结果面（新增上云，全站口径）** —— 把「已抢到 / 没抢到 / 放弃」三态与「转票补入」上报服务端，
   全站统计抢到率 / 落榜率 / 放弃率 / 转票获得数，并**同时给出样本量**。
5. **热度与口碑关联** —— 想看人数 / 抢票人数与红黑榜票数在同一影片行对照，标出「高热度低口碑」反差。
6. 新页面 `/rush-analysis` + 顶部导航新增 tab（紧接现有「抢票」之后）。

**不做：**

- **不抓官网实时余票 / 座位图** —— `biff.kr` 售票页有 WAF（`batch.ts` 文件头已记录；本轮实测
  `theater.asp` 直抓返回 `Browsing Blocked — blocked by a web firewall policy`）。
- **不建「供给面」统计区**（场次总量与批次分布、每日 / 时段场次密度、各影厅场次数、票价分布）——
  用户在维度多选中未勾选。难度榜本身是供需比的自然产物，保留；但不另扩一块供给统计。
- **不建「供需失衡榜」独立统计区**（最挤场次 Top N、时段失衡、场馆供需失衡排行）—— 同上未勾选。
- **不展示任何用户名单 / 明细**，只出聚合数字。
- **不改动现有「抢票」页 `/rush`** 的清单行为（本轮是并列新增，不是替换）。
- **不引入「售罄」这类票务系统内部状态** —— `apps/web/tests/tickets.test.ts:20-34` 已把
  `isTicketState("sold_out") === false` 钉死，本轮是新增「容量」维度，不是恢复该状态。
- **不动 `apps/web/legacy/**`**（只读回退件）。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 抢票人数用新埋点（用户点「我要抢」） | 否决 | 已有 `screening_attendance_stat` 就是「谁把这场排进行程」——再收一份同义数据只会多一条会漂移的口径 |
| 抢票人数复用「同场 N 人」 | **采纳** | 零新增采集、口径已在三处使用（场次卡徽章 / 抢票页 / 讨论），复用即不会漂 |
| 难度用绝对需求人数 | 否决 | 露天场（本届口径 4,000 席）与试写室级小厅量级悬殊，绝对人数不可比 |
| 难度用「需求 ÷ 容量」倍率 | **采纳** | 归一化后可跨厅比较；且容量是可人工查证的客观量 |
| 难度用分位数（不引入容量） | 否决（降级方案） | 只能回答「相对谁更热」，回答不了「这场到底抢不抢得到」 |
| 引入影厅座位容量（人工查证） | **采纳** | 用户明确选择「我提供影厅座位数」；BIFF 官方有公开座位数 |
| 结果面做全站口径（上云） | **采纳** | 用户明确选择；本地三态只回答「我自己」，回答不了「这场整体多难抢」 |
| 结果面用「每人一票不加权」（红黑榜那套） | 否决 | 抢票结果是**一人多场**，不是一人一票 —— 与红黑榜的离散隐喻不同，故沿用 want / screening 的 0.75 / 1.0 权重 |
| 集中度用基尼系数 / 赫芬达尔指数 | 否决 | 数值无法被用户直觉校验，与本站「口径必须能被人话解释」相悖 |
| 集中度用 Top N 占比 + 「承载半数需求所需场次数」 | **采纳** | 两句话就能说清，且可直接指导「盯住哪几场」 |
| 引图表库（recharts 等） | 否决 | 违反「依赖引入前先量化 gzip 增量」；语义化表格 + 既有 CSS 条形足够 |
| 改 `apps/web/src/style.css` 加本页样式 | 否决 | 它命中 TEST-MAP 的 `allOn`，会触发三浏览器全量 E2E（5–9 min）；本页自持 `pages/rush-analysis.css`（与 `pages/rush.css` 同一处置） |
| 容量写进 `tools/scrape_biff_web.py::VENUE_TABLE` | 否决 | 那是「官网抓来的名字映射」，容量是人工查证数据，两者来源性质不同；且改 `VENUE_TABLE` 要动 31 行 |
| 容量单独一张 `VENUE_CAPACITY` 人工表，落盘时并入 | **采纳** | 改动面最小、来源可追溯；重跑抓取不会丢 |

### 已拍板的口径（三轮确认）

- **上报门槛 / 权重**：完全镜像现有 —— 匿名也能上报，权重 **登录 1.0 / 匿名 0.75**，
  登录时必须走同一个 `clearAnonContributions` 去重（否则同一人被算两次）。
- **抢到率**：`已抢到 ÷ (已抢到 + 没抢到 + 放弃)`；**转票单独计数，不进分子也不进分母**
  （转票不等于自己抢到）。
- **读权限**：公开聚合读，与现有 `/api/stats/*` 一致，不返回任何名单。
- **24+ 时制（红线）**：需求时间分布按 `start_time` 的**原始小时**分桶，`≥ 24` 归入明确的「次日」档，
  **任何地方不得 `% 24`**。实测本届 `schedule.json` 795 场 `start_time` 小时域 = **08–23**（无 `≥ 24`），
  `pni.json` = 09–22 —— 故「次日」档是防御性分支（未来换版 / 补录可能出现），单测用**合成样本**覆盖。

## 验收标准

1. `/rush-analysis` 可达，导航里有「抢票分析」且紧接「抢票」之后；空数据 / 少样本时不崩、
   页面内**不出现 `NaN` / `Infinity`**。
2. 每场可见「抢票人数」与「难度」：难度行同时印出需求人数 / 容量 / 倍率；容量缺失行出现
   「未收录座位数」标注而**不是数字**，且降级为相对排名。
3. 需求面三块（影片想看、集中度、时间分布）与结果面（抢到率 / 落榜率 / 放弃率 / 转票获得数 + 样本量）
   可见；样本不足时明示「样本不足（N）」而不给率值。
4. 座位数经用户**逐条核对**后写入 `venues.json`，每条附来源；未查到的厅留空并标「未收录」。
5. 测试：纯逻辑单测全绿（含分级阈值边界、除零、集中度、时段分桶含 `≥24` 合成样本、
   结果面样本不足、口碑最小票数门槛、outcome 映射与白名单解析）；新 E2E spec 登记进
   `scripts/test-map.json` + `docs/TEST-MAP.md`；`npm run verify:quick` 通过。
6. 隐私核查：网络请求体只含 `{edition, entries:[{code, state, via?}]}`，**无备注 / 片单 / 身份**。
7. 登录去重核查：同一浏览器先匿名上报再登录，聚合数字**不翻倍**。

## 修订

### 修订 1（2026-09-20，实施中发现：`VENUE_TABLE` 已与产物漂移）

原方案：把容量表写进 `tools/scrape_biff_web.py::VENUE_CAPACITY`，「重跑抓取不会丢失」。

**实测不成立**：该脚本的 `VENUE_TABLE` 已经与已发货的 `public/venues.json` 漂移 ——
脚本里露天场是 `br`、东西大北咖啡是 `dm`，而产物里是 `bt` / `dk`；且产物含 MEGABOX `m1`–`m4`
（那 4 个厅来自册子，不在抓取表里）。也就是说 `venues.json` 现在**不是**这个脚本产出的。
把容量挂在那张表上，要么得先修漂移（超出本需求），要么一跑就告警。

**改为**：新增独立工具 `tools/build_venue_capacity.py`（人工维护 + 幂等并入 + `--check` 自检），
keyed by venue id，表里没有的厅会删掉产物里的 `capacity` / `capacityNote`。
它对「产物里有、表里没有」和「表里有、产物里没有」两个方向都出提示。
