# PLAN-20260914192552 — 排期数据更新提示（我的场次变了什么 / 我选的片新增了哪些场次）

## 目标

用户原话（逐字保留）：

> 你改了很多排片的信息 能不能给这些用户一些提示 提示自己的哪些片子有更新? 已经同步了哪些新的片子?

背景：`PLAN-20260914184902` 把册子并进产物，**排期 750 → 830 场**（+80 场官网查不到的场次），
另有 6 场片长被册子覆盖、3 场补了联映标记。这些变化对**已经选好片的人**是隐形的 ——
行程里那场可能悄悄变了片长，而新增的 80 场里**有 35 场属于他们早就选过的影片**。

### 现状（代码事实）

- 排期版本只有 `schedule.json::festival.generated_at`，前端**从不读它**（`data.ts::loadCatalog` 只取
  `screenings` / `venues` / `films`）→ 没有任何「数据变了」的信号。
- 用户自己的东西全在 `state.ts::store.picks`（`biff.picks.v2`）；场次 code → 影片 key 的反查索引是
  `store.slotIndex`，全量已排场次是 `allCodes()`。影片身份口径 = `util.ts::filmNodeKey(cat, s)`。
- 新增场次与用户的关系**必须按 `filmNodeKey` 判**，不能按片名字符串 —— 片名匹配会漏掉
  「中文名命中 / 原始片名命中」那两条路（`filmNodeKey` 是这三条路的唯一实现）。

### 实测（本轮数据）

| 关系 | 条数 |
|---|---|
| 新增场次 | 80（MEGABOX 1–4 = 42 / Indieplus = 20 / CGV 7 = 17 / BCM = 1） |
| 其中**属于用户可能已选影片**的 | 35（如 Selvi / Satoko Always / The Day After Sunday… 各新增 1 场） |
| 共有 code 里**影响行程的字段变化** | 9（6 条片长 + 3 条 tags） |

## 范围

**做：**

1. **新增 `tools/build_changelog.py`**：对比「上一个已发布版本」与当前 `schedule.json` → `apps/web/public/changelog.json`。
   - `--base` 默认 `git:HEAD`（读 `git show HEAD:apps/web/public/schedule.json`），也接受文件路径。
   - 只记**用户可见且影响行程**的字段：`date` / `start_time` / `end_time` / `duration_min` /
     `venue_display` / `is_gv` / `rating` / `subs` / `tags`。
     **不记 `venue_id`**（本轮 `br`→`bt` 是内部 id 改名，`venue_display` 没变 → 对用户零影响，
     记进去就是 10 条噪声）、**不记 `page` / `title_kr`**（那是「信息补全」不是「排期变了」）。
   - 输出 `added`（整条场次）+ `changed`（code + 字段级 from→to + 中文标签）。
2. **新增 `apps/web/src/changelog.ts`**：加载产物 + 纯函数 `changelogHighlights(cat, myKeys, myCodes)`，
   分三组返回 —— ① 我的场次有变化 ② 我选过的影片有新增场次 ③ 本次新增概况（按影院分组）。
   文件缺失 / 解析失败**静默降级**（与 `extras.ts` 同口径），绝不阻塞主流程。
3. **新增 `biff.dataver.v1`**：已确认的版本号（= `changelog.schedule_generated_at`）。
   只增不改、不混进 `biff.settings.v1`（与 `biff.ranks.v1` / `biff.gvtalk.v1` 同口径）。
4. **新增 `src/components/ChangelogDialog.tsx`** + `App.tsx` 顶栏按钮「数据更新」：
   - 按钮**只在「有更新且未确认」时出现**，带相关条数徽章；**不自动弹**（项目一贯反对隐性状态与打扰）。
   - 弹层三块：① 你的行程有 N 场信息变化（列出 from → to）② 你选过的影片有 N 场新排期
     （可一键「加入行程」）③ 本次新增 M 场 / K 部影片（按影院分组，可折叠）。
   - 底部「知道了」→ 写 `biff.dataver.v1`。
5. 单测 `tests/changelog.test.ts`（纯函数：命中口径 / 空 changelog / 降级）+ `catalogue-data.test.ts` 补产物断言。
6. 回写 `PLAN.md` §0 与 `docs/CONVENTIONS.md`（新契约 + 新 localStorage 键）。

**不做（与「做」同等重要）：**

- **不做「每场一个红点」** —— 830 场里 9 条变化，逐场标记的噪声远大于信息量；
  入口只落一处（顶栏按钮），与「抢票信息」同构。
- **不做「自动弹窗」** —— 用户可能正在排片；打扰式弹层会打断操作。
- **不动 `legacy/`**（只读回退件；`biff.dataver.v1` 是新键，旧版不读也不会坏）。
- **不改任何既有 `biff.*` 键结构**；不引入新运行时依赖。
- **不改 `schedule.json` / `venues.json` / `films.json` 的既有字段**（changelog 是独立产物）。
- **本轮不推送**（用户 2026-09-14 约定：本地验收后再决定）。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 独立产物 `changelog.json` + 前端读（采纳） | 采纳 | 「上一版」是**历史**信息，前端只持有一版数据，算不出来；产物化还能离线可用（PWA 预缓存） |
| 前端只比 `generated_at`，笼统提示「数据已更新」 | 否决 | 用户要的是「**我的**哪些片子变了」，笼统提示等于没提示 |
| 把 diff 塞进 `schedule.json` | 否决 | 会让「排期契约」混进「版本元数据」；且每版都要重写 830 条 |
| 记 `venue_id` 变化 | 否决 | 本轮 10 条 `br`→`bt` 是内部 id 改名，`venue_display` 未变 → 用户可见面为零，纯噪声 |
| 记 `page` / `title_kr` 补齐 | 否决 | 那是「信息更全」，不是「排期变了」；725 + 35 条会把真正的 9 条淹没 |
| 按片名字符串匹配「我的影片」 | 否决 | 会漏掉中文名 / 原始片名两条命中路径 —— 必须走 `filmNodeKey`（全站唯一身份口径） |
| 自动弹一次 | 否决 | 打断排片操作；顶栏按钮 + 徽章已足够显眼 |

## 验收标准

1. `python tools/build_changelog.py` 输出：`added` 80 条、`changed` 9 条（6 片长 + 3 tags）。
2. `npm run verify` 全绿；`tests/changelog.test.ts` 覆盖：
   - 命中口径与 `filmNodeKey` 一致（中文名 / 原始片名两条路都命中）
   - 无选片时三组均为空但 `added` 概况仍在
   - `changelog.json` 缺失 / 结构不对 → 返回空结果且不抛
   - 版本已确认 → 不再提示
3. 受影响 E2E（含顶栏 `persistent-header` / `desktop`）全绿。
4. 手动验收：删掉 `biff.dataver.v1` → 顶栏出现「数据更新」→ 弹层三块内容正确 → 「知道了」后按钮消失、刷新不回来。
5. 起 dev server 交用户看效果（本地验收，不推送）。
