# PLAN-20260916215100 — 让「点登录 → 跳回首页提示登录未完成」的病因可见（callback 失败分诊）

## 目标

用户原话（逐字保留，不要转述）：

> {"error":"SESSION_NOT_FOUND"} 点击了使用 IFFDAY 登录后 很久都没跳转 最后跳转回主页但时候  显示登录未完成，本机排片没有改动。请重试。

> send 接口是这样的 但是 me 接口还是{"error":"SESSION_NOT_FOUND"}

现象还原成机制：

1. 点「使用 IFFDAY 登录」→ `window.location.assign("/api/auth/login")`（`account.ts:146`）；
2. 走完账号系统后回到 `/api/auth/callback`，callback **失败** → `302 /?account_error=…`
   （`index.ts:173/181/243`）；
3. 前端把 `account_error` 的**具体值丢掉**，只弹一句「登录未完成，本机排片没有改动。请重试。」
   （`account.ts:73-81`）；
4. 首页那一次 `/api/account/me` 回 `{"error":"SESSION_NOT_FOUND"}` —— 含义是确定的：
   **浏览器确实带上了 `__Host-biff.session`，但 D1 里没有对应行**（`oauth.ts:138-140`）。
   也就是 cookie 是**上一次登录留下的死 cookie**，而这次登录**没能建行**。

所以本轮要解决的不是「猜一个修法」，而是**现在这套系统结构上无法区分**病因：
callback 的 7 条失败路径里，6 条都塌成同一个 `account_error=authorization`，
前端又把唯一那个区分度（`expired` / `authorization`）也扔了。

## 现状（代码事实 + 2026-09-16 生产实测，禁止推测）

| 事实 | 位置 |
|---|---|
| callback 的失败出口只有 3 个：`expired`（cookie 缺失 / 临时记录缺失）、`authorization`（try 内一切异常） | `apps/api/src/index.ts:171-244` |
| 前端 `account_error` 只判断**有没有**，不读值；弹完就删参数 | `apps/web/src/account.ts:71-81` |
| `expired` 与 `authorization` 的具体值在重定向后立刻被删，用户抓不到 | `account.ts:75-78` |
| 会话行的 401 分诊（上一轮）已经做得很细，**唯独登录入口没有分诊** | `oauth.ts:28-45` vs `index.ts:241-244` |

**生产实测（本机 curl，2026-09-16 21:4x）**：

| 探针 | 结果 | 结论 |
|---|---|---|
| `GET /api/auth/login`（3 次） | 302，≈2.0–2.9s，`Location` 指向发现文档里的 `authorization_endpoint` | 发现文档（经 `IFFDAY_API` service binding）通；客户端 `biff-scheduler` 已注册 |
| `GET /api/auth/callback?code=fake-code&state=<真 state>` + 真 pending cookie | 302 → `/?account_error=authorization`，≈2.0s | pending 记录存在、`unseal` 通、state 校验通、**走到了换 token 才失败** —— 链条前半段没坏 |
| `GET /api/auth/authorize?client_id=biff-scheduler-nope…`（对照） | `error=invalid_client` | 我们的客户端 id 有效，不是「没注册」 |
| `GET https://account.iff.day/login`（授权页，跟随跳转） | 200，正常渲染登录页 | 账号系统本身可达 |
| JWKS / 发现文档 | `kty=OKP, crv=Ed25519` / 全部 endpoint 都在 `/api/v1/auth/` 下 | `validateApplicationLevelSignature` 与 `customFetch` 的路径白名单口径**都仍然成立** |

→ 因此「很久都没跳转」至少有一部分是**链路本身慢**（登录 2–3s + 授权页 3s + callback 2–6s ≈ 10s 级），
不一定都是故障；而「失败在哪一步」目前**没有任何可观察手段**：
生产 CF 账号本机无权限（上一轮已确认），D1 查不到、日志 tail 不到。

## 范围

**做（把失败步骤变成可区分、用户可见的码）：**

1. **新增 `apps/api/src/auth-callback.ts`**：把 callback 从 `index.ts` 抽出来，按**步骤**赋失败码，
   catch 时用当前步骤作为 `account_error`（不再一律 `authorization`）。
   - 抽出来的理由与上一轮抽 `resolveIdentity` 相同：`index.ts` 里的闭包没法单测。
2. **`apps/api/src/index.ts`**：只留 `app.get("/api/auth/callback", authCallback)`；
   `subjectSchema` 与 `@biff/contracts` 的 `accountUserIdSchema` 是**同一份正则的第二份实现**
   （红线 5），一并删掉改 import 共享契约。
3. **`/api/auth/login` 也补失败出口**：现在发现文档拿不到会直接 500（用户看到的是错误页而不是可读原因），
   改为 `account_error=upstream_unreachable` / `pending_store_failed`。
   （**只影响失败路径**：成功路径的 302 与 cookie 一字不改。）
4. **可区分码的唯一口径放进 `@biff/contracts`**：`loginFailureCodeSchema`（zod enum）。
   - 服务端：类型直接来自契约 → 写出契约外的码会编译不过；
   - 前端：`Record<LoginFailureCode, string>` → 契约新增码而漏写文案会编译不过。
   这是「病因必须一直可见」的机械保证，而不是靠人记得同步。
5. **`apps/web/src/account-errors.ts`（新）**：码 → 中文原因（文案唯一来源）。
6. **`apps/web/src/account.ts`**：toast 带上具体原因；账号面板常驻一行「上次登录失败：…」
   （toast 会消失，面板不会）；`console.warn("account_login_failed", code)` 把**原始码**打出来，
   用户可以直接复制给我们。
7. **测试**：
   - `apps/api/tests/auth-callback.test.ts`：逐条断言失败码（先红后绿）；
   - `apps/web/tests/account-errors.test.ts`：断言每个码都有文案、未知码**保留原始码**；
   - `scripts/test-map.json` 把两个新文件登记进 `account` 规则 + `--write-doc` 同步 `docs/TEST-MAP.md`。

**不做（本轮明确不碰）：**

- **不改任何成功路径行为**：3s 超时、`oauth_pending` 600s 有效期、state/nonce/PKCE、验签、
  cookie 属性、`app_session` 表结构与 D1 迁移 —— 一律不动。
- **不按猜想修**：不扩大 pending 有效期、不做「state 不匹配自动重开登录」、
  不「缺 refresh token 就判登录失败」（沿用上一轮结论：猜错会把「能用」变成「登不上」）。
- **不清掉那条死 cookie**：它是当前**最有价值的证据**（cookie 在、行没了）。
  等病因坐实、决定「缺 RT 会话是否自愈」时再一起处理。
- **不动 `legacy/`**：`legacy/src/account-bridge.ts` 只读 `accountState` 既有字段，
  本轮只在 `accountState` 上**新增**字段 `loginError`，legacy 的文案与逻辑一字不改。
- 不引入新依赖；不动工作树里他人的在途改动。

## 失败码清单（唯一口径：`@biff/contracts/account`）

| 码 | 触发点 | 用户看到的中文 |
|---|---|---|
| `pending_cookie_missing` | 浏览器没带回 `__Host-biff.oauth` | 浏览器没有带回登录临时凭证（换窗口 / 禁用 Cookie / 跨浏览器） |
| `pending_expired` | `oauth_pending` 无行（>10 分钟、或同一浏览器连开两次登录） | 这次登录已超时或重复发起 |
| `pending_unreadable` | `unseal` / `pendingSchema` 失败（多为 `SESSION_SECRET` 变更） | 服务端读不回这次的登录临时记录 |
| `upstream_unreachable` | 发现文档 3s 超时 / 配置不含 PKCE S256 | 账号系统暂时连不上或配置不符 |
| `authorize_denied` | 回调 URL 带 `error=`（上游授权环节直接拒绝） | 账号系统在授权环节拒绝了这个账号 |
| `state_mismatch` | 回调 state ≠ 本次登录 state | 这次登录与开始时的会话对不上（常见于开了两次登录） |
| `token_rejected` | 换 token 被拒（`invalid_grant` 等） | 账号系统拒绝发放登录凭证 |
| `id_token_invalid` | 验签 / nonce / iss / aud 不过 | 登录凭证校验不通过 |
| `subject_invalid` | `sub` 不合 `user_…` 白名单 | 账号标识形态与预期不符 |
| `userinfo_failed` | userinfo 调用 / 解析 / 邮箱缺失 | 读取账号资料失败 |
| `session_store_failed` | 写 `app_session` 失败 | 服务端保存登录状态失败 |
| `pending_store_failed` | 登录时写 `oauth_pending` 失败 | 服务端无法开始这次登录 |
| `authorization` | 兜底：授权应答本身不成形（缺 code / iss 不符）/ 未预期异常 | 登录过程中出现未知错误 |

旧版服务端（2026-09-16 之前）只发过 `expired` / `authorization`：前者作为**遗留码**在前端文案表里保留，
保证老书签 / 缓存页面也能读到像样的中文。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| callback 按步骤分诊 + 前端展示具体原因 | **采纳** | 与 PLAN-20260916104514 同一条路数：生产日志读不到、D1 查不到，就把诊断搬进**用户能看到的东西**里 |
| 失败码放共享契约、前端用 `Record<码, 文案>` | **采纳** | 漏写文案 / 漏登记码直接编译不过，杜绝「新增路径又变成盲区」 |
| 只加 `console.warn` 靠 CF 日志 / `wrangler tail` | 否决 | 本机账号无生产权限（上一轮已确认），日志没人看得到 |
| 让用户去抓地址栏的 `expired` / `authorization` | 否决 | `account.ts:75-78` 立刻删参数，用户抓不到；且 2 个桶太粗 |
| 按最可能的猜想直接改（pending 600s→30min、state 不匹配自动重登） | 否决 | 猜错会把「能登录」变成「登不上」，且掩盖真实信号 |
| 顺手清掉 `SESSION_NOT_FOUND` 的死 cookie | 否决 | 死 cookie 是当前最有价值的证据，清了就把「cookie 在、行没了」这个事实抹掉 |
| 把 callback 留在 `index.ts`，用 `app.request` 测 | 否决 | api 的单测跑在 **node** 环境（`apps/api/vitest.config.ts:10`），为了测一个 handler 拉整个 API 程序不划算；抽出来才能只 mock 上游 |
| 顺手把 `subjectSchema` 与 `accountUserIdSchema` 合成一份 | **采纳** | 正则逐字相同，现在是第二份实现（红线 5） |

## 修订 1（2026-09-16，据用户观察 + 生产实测）

**触发**：用户提出相关性 ——

> 好像每次发版之后就会好 然后每次发版涉及数据库改动之后就会有问题?

**这条相关性能对上一条真实机制**（所以不能否掉）：

`scripts/prepare-cloudflare.mjs:21-33` 把 `db:migrate:remote` 排在**两次 Worker 部署之前**，
且失败即 `process.exit(status)` —— 一旦某个迁移在生产 apply 失败，**整次发布中止**：
站点继续跑旧代码，而库已经是新的。表现正是「涉及数据库改动的那次出问题、下次发版就好」。

**但 2026-09-16 这次不是它**（三条实测，都不是推测）：

| # | 探针 | 结果 | 推论 |
|---|---|---|---|
| ① | `GET /api/stats/film-votes` | `200 {"edition":"biff-2026","votes":{"cat:f001":{"red":1,"black":0}}}` | 最新迁移 `0006` 的表**在生产存在且已有数据** → 迁移没失败、发布没中止 |
| ② | `GET /pni.json`、线上 `main-*.js` 内容 | 200（19 KB）；含 `pni.json` 与讨论区检索文案「没找到这一场」；本轮新增字符串 `account_login_failed` = **0**（阴性对照） | 线上前端产物是**最新提交**（18:22 那版），不是卡在旧代码 |
| ③ | `GET /api/auth/login` → 带返回的 pending cookie 走 callback | callback **走到了换 token** 才失败（≈2.0s） | 拿不到 pending 行就到不了这一步 —— 说明 **D1 写（`oauth_pending` INSERT）与 delete-returning 现在都是通的** |

再补一条**已排除**：`/api/feedback`、`/api/discussions` 里用户自己的帖子（今日 10:43 / 10:56）
`subject` 是 `user_01M2EVF3GTTJ6JC9NTM8NXYNHY`，**符合 `accountUserIdSchema`**
→ `subject_invalid` 不是常态成因（曾列为候选，现排除）。

**「发版之后就会好」也有不需要数据库的解释**：发版会换掉 isolate，并让浏览器拿到新资产
（asset hash 变了，PWA `autoUpdate` 也会换掉旧 bundle），登录失败链上的**一次性状态**
（死 cookie、上一次留下的临时记录、旧 bundle）会被一起冲掉。
所以这条相关性目前只能说明「触发与那一刻的状态有关」，**推不出「是库改动导致的」**。

**顺带发现一条真实隐患**（正是「涉及数据库改动就有问题」的那类）：
`apps/api/migrations/meta/` 里**缺 `0003_snapshot.json` / `0004_snapshot.json`**，
`_journal.json` 的三条 `when`（`1789340000000` / `1789400000000`）是手工编的 ——
历史上每次 `db:generate` 都可能把已存在的 `film_want_*` / `feedback_*` **再生成一遍**，
本地看不出来、**只在生产 apply 时炸**，后果就是修订 1 开头那条「整次发布中止」。
`0005` 的手工裁剪注释记的就是这件事。**现在已拆掉**：`0006_snapshot.json` 是完整基线
（含 12 张表），下一次 `db:generate` 不会再重复建表。

**仍然存在的观测缺口**（下一轮候选，本轮不做）：前端新 ≠ 后端新 —— 前端由 `postbuild` 部署、
API 由随后的 `wrangler deploy` 部署，**API 那一步失败会留下「新前端 + 旧后端」**，
而现在只能用 asset hash 人工比对前端。要让「线上到底是哪一版」一眼可查，需要单独一轮。
