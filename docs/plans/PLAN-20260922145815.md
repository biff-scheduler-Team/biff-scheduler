# PLAN-20260922145815 — 红黑榜：每部影片完整展示全部贴纸（视口渲染 + Canvas）

## 目标

用户 2026-09-22 的两次提问：

> 现在红黑榜单电影数量有上限吗?

> 我也觉得会有性能问题 但是我又想在在一个电影中显示所有贴纸 有什么好的方案吗

**复盘结论**：榜单**影片数量没有上限**（`boardFilms()` 只过滤「有没有场次」，299 部一次全渲染，无分页无虚拟滚动）；
有上限的是**每部影片画布上画几枚「别人的贴纸」** —— `redblack.ts::CROWD_CAP = 16`，超出部分折成一个「+N」角标。
这个上限的成因是**渲染成本**，不是产品意图：`board` 是页面级 state，`visible.map` 又在同一组件里 ——
**每贴一枚，299 张卡全部重跑 `crowdStickers()` 并让 React 重新 diff 全部元素**。

**本期要达成的结果**：每部影片按真实票数**完整画满**所有贴纸（不再有 16 枚上限），
屏幕外的卡片不画（滚动进视野前已补齐），并补一个「放大看全部」的入口。

## 范围

**做:**

1. **渲染预算换单位**：从「每部片画几枚」改成「同时渲染几张卡」——
   `O(卡片数 × 每卡点数)` → `O(视口内卡片数 × 每卡点数)`。
   - 新增 `apps/web/src/use-in-view.ts`（IntersectionObserver，`rootMargin` 预取一屏）
   - 「别人的贴纸」不再进 DOM，改由**每卡一张 `<canvas>`** 绘制，进出视口时分配 / 释放 backing store
2. **分卡 memo**（`RedBlackPage.tsx` 内抽 `RbCard` + `React.memo` + `useCallback` 固定回调）——
   不修这条，光上 canvas 仍会卡（贴一枚仍会重渲 299 张卡）
3. **CSS 隔离**：`.rb-card` 加 `contain: content` + `content-visibility: auto` + `contain-intrinsic-size: auto <近似值>`
4. **贴纸 sprite 预渲染**（`apps/web/src/sticker-sprite.ts`）：离屏把红 / 黑各画一次
   （现有不规则圆片形状 + 细条纹 + 径面高光 + 落影），每枚只做一次 `drawImage`；颜色只读 CSS 的 `--rb-red` / `--rb-black`
5. **重绘守护**（`apps/web/src/sticker-canvas-guard.ts`）：按**值**比较上次绘制的关键参数，
   父级无关 re-render（顶部统计变化等）一律不重画
6. **DPR 观测**（`apps/web/src/use-dpr.ts`）：`matchMedia("(resolution: <dpr>dppx)")`，
   ⚠ 每次变化后用新的 dpr **重挂**监听（跨屏拖窗、Cmd/Ctrl +/- 缩放都不触发 `resize`）
7. **「放大看全部」弹层**（`apps/web/src/components/StickerZoomDialog.tsx`），复用 S2 `Dialog`
8. **测试**：单测 `crowdStickers` 全量语义 + 重绘守护判据；E2E 机读契约从「数 DOM 点」改为读
   `data-rb-crowd` / `-red` / `-black`，并新增滚入补齐、弹层 a11y 断言

**不做:**

- **不动拖拽链路**：「我贴的那一枚」仍是 DOM（唯一可拖元素，绑着 `onPointerDown` 与 ghost 逻辑）。
  Canvas 只承担只读点，`pointer-events: none`
- **不引入任何新依赖**（`react-window` / `will-change` 合成层等一律否决，见方案取舍）
- **不改投票口径与持久化契约**：一人一部一票、`biff.redblack.*` key 只增不改
- **不改 `apps/api`**：服务端仍只返回聚合计数（没有每票坐标），「全部贴纸」是**数量意义**上的全部
- **不做密度降级**（用户明确要求）：单片几百上千枚也一直全量画
- **不动 `style.css`**（它命中 TEST-MAP 的 allOn，会触发三浏览器全量 E2E）；样式只改 `redblack-parity.css`
- **不碰他人在途改动**：`apps/web/src/app/App.tsx`、`e2e/react/share-export.spec.ts`（`PLAN-20260922142922`）

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 保持 16 枚上限 + 「+N」角标 | 否决 | 用户诉求就是「一部片看全部」；16 枚会被读成真实票数 |
| 「我贴的那一枚」也进 canvas | 否决 | 它是唯一可拖元素；canvas 只承担只读点，不动拖拽链路 |
| canvas 与卡片各写一套坐标推导 | 否决 | §5 口径单一来源：都消费 `crowdStickers()` / `spotOf()` / `tiltOf()` |
| canvas 上做 hover 命中检测 | 否决 | 2026-09-22 已拍板「只靠能不能拖区分」；`pointer-events:none` 是拖拽落点命中测试的硬约束 |
| `will-change: transform` 每卡一个合成层 | 否决 | 299 层约上百 MB GPU 显存；`contain` 已解决「不波及全页重绘」，它只买到内存暴涨 |
| SVG `<use>` 批量复用 | 否决 | 每个实例仍是独立 DOM 节点，节点数一个没省 |
| `react-window` 等虚拟列表 | 否决 | 违反 §5「引依赖前先量化 gzip 增量」；2 列变高卡片难以虚拟化 |
| rAF 每帧插 20 个 DOM | 否决 | canvas 方案下无必要，且与 React reconciler 打架 |
| 单片超阈值切热力 / 聚合视图 | 否决（用户拍板） | 偏离「看到每一枚」；先按实测数据说话 |
| `ctx.arc` 画正圆 | 否决（用户拍板） | 贴纸不是正圆（`border-radius: 48% 52% 45% 55% / …` + ±15° 歪斜 + 质感），会明显变样 |
| 每次 render 都 `clearRect` 重画 | 否决 | 滚动时父级无关更新会引发无意义重绘；改按值守护 |
| 手写 `role=dialog` + focus trap | 否决 | 仓库已有 S2 `Dialog`（自带 role / aria-modal / focus trap / Esc / 焦点归还），§5 口径单一来源 |
| **视口渲染 + Canvas + sprite** | **采纳** | 成本与总票数解耦；零新依赖；视觉与现状一致 |

## 验收标准

1. 一部的票数是 100 时，画布上**真的画 100 枚**（`data-rb-crowd="100"`），不再出现「+N」角标。
2. 屏幕外的卡片**不分配 canvas backing store**（`canvas.width === 0`），滚动进入视野前已补齐为全量
   （`rootMargin` 预取一屏，看不到「空画布 → 满贴纸」）。
3. 贴纸外观与现在一致（26px 不规则圆片 / ±15° 歪斜 / 质感 / 落影），高分屏下边缘不模糊；
   跨屏（DPR 变化）后自动重新分配尺寸并重绘。
4. 滚动 / 贴一枚贴纸时，视口内画布**不重画**（重绘守护按值命中即跳过）。
5. 全页 DOM 节点数较改造前显著下降（改造前 299 部 / 20629 票时实测 **8571 节点**，
   其中贴纸点 4008 个）；成本不再随总票数增长。
6. 「放大看全部」弹层：`role=dialog` + Esc 关闭 + 焦点归还原按钮；内容为同一部片的全部贴纸（更大画布）。
7. 回归测试**先红后绿**；收口命令：
   `npm run verify:quick` + `npx playwright test -c playwright.react.config.ts e2e/react/redblack.spec.ts --project=desktop-chromium` 全绿。

## 修订记录

- 2026-09-22 初版。三段递进（视口渲染 → Canvas 只读点 → 放大弹层），口径由用户 2026-09-22 问答拍板：
  范围**三层全做**、Canvas 用**预渲染 sprite**（保持视觉）、票数极大时**不降级**。
- 2026-09-22 修订 1（取消「屏外缩略 + `+N`」这条中间态）：原计划里「屏外卡保留 16 枚缩略 + 角标」
  与「离开视口释放 backing store」**互相矛盾** —— 释放了就没东西可画，不释放就是 299 张 × 约 1MB 的显存。
  且 `useInView` 已预取一屏，屏外卡**根本不会被看到**，角标是零收益的纯成本。
  故：`CROWD_CAP` / `crowdOverflow` 与「+N」角标一并下线，`crowdStickers` 的 `cap` 默认改为 `Infinity`。
- 2026-09-22 修订 2（顺带修掉一个只有放开上限后才看得见的真 bug）：`spotOf` 直接拿 FNV 哈希的**高位**
  当纵坐标，而同一部片的贴纸 id 共享前缀（`cat:f001#crowd-`）—— 高位对末尾那几个字符几乎不敏感，
  于是每部片的点会挤成一条横带（实测个别片 100 枚全落在画布上面 40% 里）。画 16 枚时看不出来，
  画 100 枚时一眼就是「没铺满」。修法：取坐标前过一遍 murmur3 的 `fmix32` 雪崩收尾。
  实测 299 部 × 100 枚：最小纵坐标跨度 **0.78**（修复前个别片只有 0.46）、中位数最大偏移 0.129。
  `tiltOf` 用的是另一套哈希，实测分布正常（±15 铺满），**未改动**。

## 验收结果（2026-09-22）

三段各自一个提交，全部本地验过：

| 阶段 | 提交 | 证据 |
|---|---|---|
| 视口渲染（放开上限 + memo + CSS 隔离） | `perf(redblack): 放开每卡 16 枚上限改按视口渲染…` | 单测 52 passed；E2E 三浏览器 33 passed |
| Canvas 只读点（sprite + 重绘守护 + DPR） | `perf(redblack): 只读贴纸改由 canvas 绘制…` | 单测 530 passed；E2E 36 passed |
| 「放大看全部」弹层 | `feat(redblack): 新增「放大看全部」弹层…` | E2E 含 role=dialog / Esc / 焦点归还 |
| 落点分布修正（修订 2） | `fix(redblack): 贴纸落点的纵坐标挤成一条横带…` | 单测 57 passed；E2E 36 passed |

**本机压测**（dev + 临时 mock：299 部有场次影片 / 20629 票 / 均 80 枚一部 / 最大 160）：

| 项 | 改前（每卡封顶 16） | 改后 |
|---|---|---|
| 全页 DOM 节点 | 8571 | **4955** |
| 贴纸 DOM 节点 | 4008 | **60**（只剩我贴的那几枚） |
| 画布 | — | 299 个，**只有视口内 14 个持有 backing store**（合计 6.6 MPx ≈ 26MB） |
| 实际画出的贴纸 | 4008（被上限截断） | **983**（视口内全量，不再截断） |
| 页面 JS 报错 | — | 0 |

滚动成本（12 步 wheel × 2000px，dpr=2）：canvas 合计 **12714 次 `drawImage` + 188 次 `clearRect` = 13ms**，
占 1743ms 滚动时间的 **1%** —— 瓶颈不在画布；188 次 `clearRect` 说明**只有新进视口的卡在重画**，
重绘守护生效。参考：改前若把 20453 枚点全塞进 DOM，一次性「创建 + 强制布局」实测 22ms + 88ms。

**视觉**：截图核对 —— 1 红 / 100 黑那部画布上仍画得出那枚红；42 红 / 4 黑按真实比例铺满；
弹层里的位置与卡片逐字一致，只是铺得开；sprite 与 `.rb-dot` 的形状 / 质感 / 落影肉眼无差。
