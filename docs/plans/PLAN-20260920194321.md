# PLAN-20260920194321 — hover 高亮块不再遮挡柱子（半透明 + 压到柱子下面）

## 目标

用户原话：

> 分析页面hover 柱子的时候 会出现柱子直接被遮挡 是不是柱子背景色的原因

用户猜的方向对了一半：确实是「背景色」，但不是柱子的 —— 是 **hover 高亮块（ECharts `axisPointer` 的 shadow）** 的。

## 现状（实测证据，不是推测）

在真实浏览器里 hover `[data-chart="facet-year"]` 的一根柱子，对比 hover 前后的 SVG `<path>` 列表：

- hover 前 15 个 path；hover 后 16 个，**新增的那个排在最后**（= 画在最上层）：
  `{"i":15,"fill":"#f7f7f8","d":"M48 155.875 l613.82 0 l0 21.125 l-613.82 0 Z"}`
- 它的 `fill` 正是 `--raised`（浅色 `#f7f7f8`），矩形横跨**整个绘图区** —— 即整行 / 整列
- 被 hover 的柱子 fill 从 `#ce1e36` 变成 `rgb(226,33,59)`（ECharts 自己提亮了），但已被上面那块实色盖住

两个原因叠加：

1. **层级**：ECharts 6 的 `axisPointer` 默认 `z: 50`
   （`node_modules/echarts/lib/component/axisPointer/AxisPointerModel.js:59`），而 bar series 的 `z` 默认是 2。
2. **颜色**：库默认的 shadow 是半透明 `rgba(129,130,136,0.2)`，而我们在三个图表里都把它换成了**完全不透明**的 `tokens.raised`。

三处同样写法：`chart-theme.ts` 的消费点 `components/charts/bars.tsx` 的 `CountBarChart` / `RankBarChart` / `StackedBarChart`。

## 范围

**做：**

- `chart-theme.ts` 新增纯函数 `withAlpha(color, alpha)`：**只给既有 token 加透明度**，不新增色源。
  只认 `#rgb` / `#rrggbb`；读不到或形式不认识时**原值返回**（宁可高亮不透明，也不返回 `undefined` 让 SVG 画出透明图形）。
- `bars.tsx` 把三处 `axisPointer` 抽成一个 `hoverPointer(tokens)`：**`z: 1` + `withAlpha(tokens.line, 0.5)`**。
  - `z: 1`：在网格线（z 更低）与柱子（z=2）**之间** —— 高亮块退到柱子下面。
  - 用 `--line` 派生而不是 `--raised`：`--raised` 是「拉开一层的底」，语义上是面板底色；
    高亮块要的是「比背景深一点的辅助色」，`--line`（网格与坐标轴的色）正是这个语义。
- 单测：`chart-theme.test.ts` 覆盖 `withAlpha` 的正常 / 短写 / 大写 / 非法输入四条分支。
- E2E：新增一条断言钉住修复 —— hover 后高亮块的 `<path>` 出现在**柱子之前**（= 在下层），
  且它的 fill 带透明度（`rgba(...)` 形式，不是纯 token）。

**不做：**

- 不去掉 hover 高亮（用户选的是「半透明 + 压到下面」，保留「高亮这一行 / 列」的反馈）。
- 不改 `emphasis`（柱子自身的提亮是 ECharts 的行为，与本次无关）。
- 不动其它图表的 tooltip / 网格 / 配色。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 直接把 `shadowStyle.color` 写成 `rgba(129,130,136,0.2)`（照抄 ECharts 默认） | 否决 | 等于在图表代码里写死颜色，暗色主题下不会跟随站点 token（红线） |
| 只在 `chart-theme.ts` 里预置一个「高亮色」常量 | 否决 | 那会变成**第二份色源**；派生比新增更安全 |
| 去掉 `shadowStyle` 覆盖、走库默认 | 否决 | 库默认色不跟随主题；且用户在暗色下也需要看得见高亮 |
| 只调 `z`、颜色保持不透明 | 否决 | 柱子出来了，但整行/列仍是实色块，压过网格与坐标轴，视觉更重 |
| 只改半透明、不动 `z` | 否决 | 柱子仍会被蒙上一层灰（颜色被冲淡），不是「完整可见」 |
| **`z: 1` + 从 `--line` 派生半透明** | **采纳** | 高亮语义保留、柱子完整可见、颜色仍全部来自 token |

## 验收标准

1. hover 任一柱子时：柱子**完整可见**（不被色块覆盖），但被 hover 的那一行 / 列仍有淡淡的高亮带。
2. `withAlpha` 的四条分支单测通过（含非法输入原值返回）。
3. E2E 新增断言：hover 后高亮块的 path 索引**小于**柱子 path 的索引；其 fill 为 `rgba(...)`。
4. `npm run typecheck` / `lint` / 单测 / `build -w @biff/web` 通过；`rush-analysis.spec.ts` 全绿。
5. 回写文档：本 PLAN；`PLAN.md` 文档头一行「最后更新」。

## 实施结果（2026-09-20）

**修完之后的实测**（hover `[data-chart="facet-year"]` 的一根柱子，读 SVG 的 `<path>` 列表）：

- hover 前 15 个 path；hover 后 16 个 —— 新增的高亮块落在 **i=7**（`fill="rgb(220,220,225)"` + `fill-opacity`），
  **排在所有柱子（i=8..15）之前**，即画在**下层**；柱子 fill 仍是不被冲淡的 `#ce1e36`。
- 对比修复前：高亮块是**最后一个** path（i=15）、`fill="#f7f7f8"` 且**没有** `fill-opacity`（完全不透明）。

**回归测试先红后绿**（同一台真机浏览器，`-g "hover 柱子"`）：

| 变体 | 结果 | 失败值 |
|---|---|---|
| 完全回到修复前 | **红** | `hover 高亮块没画出来`：`shadowIndex = -1`（不透明填充没有 `fill-opacity`，识别不到） |
| 只修颜色、**不**修层序（`z: 50`） | **红** | `高亮块又跑到柱子上面了`：`Expected < 7, Received 15` |
| 修复后（`z: 1` + 半透明） | **绿** | 10 passed |

也就是说两条断言各自对应 bug 的一个面，任一不修都会红。

**其余验证**：`typecheck` / `lint` 通过；web 单测 **543 passed**（新增 5 条 `withAlpha`）；
`rush-analysis.spec.ts` **10 passed**（desktop-chromium）。
