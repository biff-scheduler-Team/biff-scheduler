## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 手写 SVG 画图（零依赖） | 否决（用户明确选择 recharts） | 用户已知 +100KB 级 gzip 的代价仍选了 recharts；本轮以「实测 + 拆包 + 懒加载」把代价压到首屏之外 |
| **引 recharts** | **采纳** | 用户选择 |
| recharts 进主包 | 否决 | 实测组件子集 **123,524 B gzip**（`main` 基线 84,778 B），首屏会翻倍 |
| **recharts 独立 chunk + 分析页路由级懒加载** | **采纳** | 主包 gzip 反而 **84,778 → 81,723 B（−3.1 KB）**；chart chunk 只在进这一页时下载 |
| 颜色写死在图表里 | 否决 | 暗色下必然不可读；本站现场主要用手机、默认跟随系统 |
| **`chart-theme.ts` 从 token 运行时读色 + 订阅 `data-theme`** | **采纳** | recharts 不认 CSS 变量；不订阅会出现「切暗色图表还是浅色」 |
| 用 recharts 默认外观 | 否决 | 与站点极简清单语言冲突 |
| **tooltip / 图例 / 网格全部走站点 token** | **采纳** | 与站内其它组件天然一致 |
| 图例塞进 `ChartFrame` 的 `children` | 否决（**实测踩到**） | 画布是固定高度的，图例挤进去会和脚注重叠 —— 真实浏览器截图里肉眼可见 |
| **图例走 `legend` prop，渲染在画布之外** | **采纳** | 同上 |
| 需求远低于容量时仍画售罄线 | 否决（**实测踩到**） | 线只能画在原点附近一小截，图例却宣称有它 = 误导；改为「占横轴 <5% 就不画」并写明原因 |
| 无可放点的口碑散点仍挂载图表 | 否决（**实测踩到**） | 只画出一个空坐标系比不画更让人困惑；改为一票都没有时只给提示文案 |
| 把「想看」按钮与「想看 N 人」徽章都叫「想看」 | 否决 | 会被读成「点这里会变成 12」；徽章改为「N 人想看」 |
| 单场片的副作用靠换文案暗示 | 否决 | 改由片信息行的可见说明承担（S2 的 `Button` 不接 `title`，且手机没有悬停） |
| 单场片与多场片各叫一个按钮名 | 否决（用户选择「只统一文案」） | 两者都是「想看」这一个动作 |

## 修订 1（2026-09-20，第 2 轮开工）

### 做了什么

第 1 轮把「需求 / 难度 / 结果 / 口碑」四个面**画出来**了。但需求面只回答「多少人想抢」，
供给面（有多少东西可抢）、个人视角（我排得合不合理）、群体视角（别人怎么想）、
以及最后的「所以接下来做什么」都还是空的。本轮补齐这四组，`/rush-analysis` 由 5 个分组变 7 个：

**A. 供给与排片结构**（`rush-supply.ts` + `RushSupplySection.tsx`）
场次总量 / 覆盖天数 / 用到的影厅数 / 座位供给 / 银幕时间；按**场次**（不是需求）的每日与每时段排片密度；
各影厅场次数与座位供给；票价档位与票面总额；影片放映次数（含「整届只放一场」的影片数）；开票批次结构。

**B. 我的观影画像**（`rush-portrait.ts` + `RushPortraitSection.tsx`）
影片数 / 场次数 / 覆盖天数 / 覆盖影厅 / 时长 / 票面总额 / 平均分 / 单日最密；
按日期与时段的自有场次分布；单元 / 影院品牌 / 制产国偏好；票面总额的口径边界写在页面上。

**C. 群体行为与口碑**（`rush-crowd.ts` + `RushCrowdSection.tsx`）
想看人数榜（+ 中位数基准）、红黑票账（+ 红票占比、Top 红 / Top 黑、「有争议」）、场次讨论榜，
以及**我的选片与全站想看的重合度**。

**D. 行动建议**（`rush-advice.ts` + `RushAdviceSection.tsx`）
五条规则收敛前几组：R1 要盯的场次（难度 ≥ 高，`extreme` 升为 urgent）、R2「整届只放一场」、
R3 已开票但未标结果、R4 下一批开票（带我这批的场次与其中高难度数）、R5 难度数据缺口。
排序固定「要盯 → 留意 → 说明」。

### 本轮的口径决定（都在文件头写了理由）

| 决定 | 理由 |
|---|---|
| 供给密度按**场次**而不是需求 | 与需求面的「按日期需求」是两个问题（「排得最满」≠「最挤」）；已有 `demandByDate` 回答后者 |
| 座位供给只在**已收录容量**的场次上求和，并把缺口单独印出来 | 不写清楚会被读成全站供给；缺口是已知事实，不是 0 |
| 影厅供给 = 场次数 × 座位数 | 露天场 8 场 × 4000 席 = 32,000 座 > 24 场 × 212 席的小厅；只看场次数会看反 |
| 新增 `screening-counts.ts / want-counts.ts / film-votes.ts` 进 TEST-MAP 的 rush-analysis 路径 | 本页消费它们，改它们必须跑本 spec |
| 抽 `buildShowRows(cat, attendance)` 到 `rush-analysis.ts` | 第 2 轮的四个分组都要吃同一份行；各自装配一遍就是「时段怎么算」有两处实现（红线 5） |
| `ShowDemandRow.venueId` 设成**可选** | 设必填会把第 1 轮 35 条单测全部改红 —— 而「既有测试一条不改」正是口径未变的证据 |
| 导出 `medianOf` / `bucketHourOf` / `hourLabel` 供分组复用 | 这三件事在多个分组里都要用；各写一份迟早出现「一处取平均、一处取下侧」 |
| 通用条形图组件 `components/charts/bars.tsx`（竖柱 / 横排 / 堆叠三种） | 第 2 轮四组里大量是「同形状换数据」；给每个图各写一个组件等于把「画一根柱」复制五六遍 |
| 画像**单价注入** `priceOf`、建议**注入** `nowMs`/`opens` | 纯逻辑模块不 import 网络单例（否则单测就得依赖抓取产物、依赖真实时钟） |
| 建议里不新增任何阈值 | 难度分档来自 `capacity.ts`、批次来自 `batch.ts`、开票时刻来自 `extras.ts`：本轮只新增「哪几条规则值得说出口」 |
| 建议里**不重写**冲突检测 | 冲突口径归 `plans.ts` / `util.ts::slackBetween`（已有唯一实现）；本轮不碰，避免第二份 |
| 空数据一律「整组不渲染」而不是「全 0 的组」 | 「0 部片 / ₩0 / 0 条建议」不是信息，是让人以为站点坏了的形态 |

## 修订 3（2026-09-20，用户反馈：太多字了，尽量都图表化）

### 触发

第 2、3 轮把八个分组都做出来了，但**表达方式**没跟上：我用大量 `ra-hint` 段落写口径说明，
难度榜每行还挂一句人话判据。用户直接反馈「太多字了，最好尽量都图表化」。

### 先量，再改（不然只是猜）

写了一个临时探针（`zz-probe.spec.ts`，出报告后已删）统计每个分组的**文字量 / 图表数 / 高度**：

| 分组 | 改前文字 | 改前图 | 改前高度 |
|---|---|---|---|
| **抢票难度榜** | **3068 字** | 1 | **64,208 px** |
| 供给与排片结构 | 1113 | 4 | 981 |
| 我的观影画像 | 624 | 4 | 679 |
| 群体行为与口碑 | 541 | 2 | 587 |
| 行动建议 | 423 | **0** | 364 |
| 其余四组 | ~1300 | 4 | ~330 起 |
| **全页** | **7,237 字** | 19 | **70,485 px** |

★ 结论：**全页 91% 的高度是难度榜那一条 795 行的文字清单**，而它 3,068 字里大半是
每行重复的那句「需求 N 人 > 座位 N 席，想抢的人坐不下」——同一句话抄了 795 遍。

### 改了什么

| 改动 | 做法 |
|---|---|
| **难度榜列表折叠** | 默认只列前 20 行（`LIST_LIMIT`），其余靠「展开其余 N 场」按钮；**搜索时不受限**（那时就是在找特定一场） |
| **难度榜行内压缩** | 删掉每行的人话判据（移进 `title` 悬停可得）；数字压成 `需求/容量 · 分位`（每行省约 13 字） |
| **难度条** | 新增 `.ra-ratio`：宽度 = 倍率，色按难度分档 —— 「这一行多难」本来就是可画的量 |
| **批次结构** | 两张文字卡（含判据条目）→ 一张**堆叠条**（每批一格、按判据分段），批次数字压成一行 chip |
| **制产国** | 一行拼接文字 → 横排条形图 |
| **「有争议」** | 十行清单 → 一行 chip（它是红黑图的子集，列十行是重复表达） |
| **讨论榜** | 十行文字清单 → 横排条形图 |
| **行动建议** | 0 图 → 新增「我行程里要盯的场次」横排图（开票当天照着抢的那张） |
| **热度与口碑清单** | 17 行 → 前 12 行 + 一行「另有 N 部」 |
| **全部口径说明** | 可见文案压到一句话以内，完整解释移进 `title`（悬停/读屏仍可得，**信息没删，只是不占版面**） |

## 修订 5（2026-09-20，用户反馈：卡片不铺满 + 明细只要 TOP10 + 重新排版）

### 用户原话

> 为什么卡片不会填满? 请你参考项目其他地方的填充逻辑 影片明细（只需要 TOP 10） 请你重新排版样式

### 根因：不是卡片的问题，是**页面元素作为 flex 子项没有宽度**

`.workspace` 是 `display:flex`（`style.css:215`），页面元素是它的 flex 子项 ——
`flex-basis:auto` 取**内容宽度**，于是 `.ra-page` 只铺开约 620px，右侧整片空。

**修法照既有三个整页的写法**（`style.css:1489`：`.library-page` / `.agenda-page` /
`.feedback-page` 都是 `width:100%; min-width:0;`），把 `.ra-page` 加进同一份名单 ——
不新写一套规则。⚠ `style.css` 命中 TEST-MAP 的 **allOn**，这次改动按约定要跑三浏览器全量 E2E。

### 重新排版（都是「原来没铺满 / 原来挤在一起」的具体形态）

| 处 | 改动 | 依据 |
|---|---|---|
| 数字条 | flex → **grid 等分**，每个数字一张浅底卡 | flex 在宽屏把六个数字挤在左边，右半边空着 |
| 筛选条 | flex → grid 等分，上限 860px | 三个控件挤在左侧；但铺到 1500px 是三个巨型控件，故设上限 |
| 明细表数字列 | 固定 72px → **百分比宽度** | 宽屏下四列数字均匀铺开，而不是全挤在右端 |
| 图表网格 | `auto-fit`（已是）| 空轨道会折叠，两张图各占一半而不是缩在左半边 |
| **影片明细** | 24 行 → **TOP 10** | 用户明确要求；它本来就是「按想看降序」的第 11~N 名，不是抽样 |
| **红黑票图** | 竖堆叠 → **横堆叠**（类目上 Y 轴） | 竖放的横轴放 10 个中文片名会被 ECharts 抽稀成只剩一条可见（实测只剩「The Sorry Generation」），等于把「哪条是谁」整个丢掉 |
| **环形图图例** | 右侧竖排 → **底部横向滚动** | 面板宽 ~460px 时竖排图例（右对齐、宽度由最长分类名决定）直接压在扇区上（截图实测：单元那张环被盖住） |
| **年份榜** | 28 个年份全列 → **只列影片数最多的前 8 个**（其余合计写在图注） | 全列是一条「根根皆针」的纵轴，占满整列高度而信息量接近 0 |
| 影片分析分组 | 5 张图挤一个 grid（4+1，第二行空三格）→ **拆成 3 环一行 + 2 榜一行** | grid 的行不会自动跨列铺满 |
| 红/黑票配色 | 红票=语义绿、黑票=语义红 → **红票=品牌红、黑票=正文色** | 语义色里 `--selected-line` 是**绿**，拿它画红票等于把「好看」画成绿色，与「红黑榜」这套叫法冲突 |

### 顺带逮到的一个真 bug

环形图圆心那个「合计」数字**一直没画出来**，而 ECharts 既不报错也不警告 ——
原因是按需注册时**漏了 `TitleComponent`**（圆心文案是用 `title` 画的）。
探针证据：修前 SVG 的 `<text>` 只有 7 个图例名，修后多出 `"327"`。
**教训**：ECharts 的按需注册是静默降级，`data-points` 这类契约断言也发现不了它 ——
只有把「SVG 里到底有哪些文字」读出来才看得见。
