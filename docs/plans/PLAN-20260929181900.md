## 目标

看得到「有多少人贴」,看不到「为什么」。用户 2026-09-29 要把它变成可读的。最初的原话是:

> 悬停浮层(Popover / Tooltip)的结构与视觉:当用户将鼠标悬停(Hover)在展板上的某个红点或黑点上时,
> 弹出一个精致的轻量卡片……用户头像与昵称……贴纸类型与评价(如:🔴 红榜 |「拉片细节绝了,今年最佳!」)
> ……密集/重叠场景的操作处理……扩展响应热区(Hit Area)……层级置顶(Z-Index)……重叠聚拢(Cluster / Group)
> ……移动端(Touch Device)适配……单击触发……Bottom Sheet……按需获取……
> 💡 互动扩展建议:增加「回应」或「同感」

> ⚠ **这段初版设想当天就被用户自己改口了**(见下方「已定口径」第 4 条):
> 「评语我觉得单独做一个模块吧,不要放在贴纸上,不然很乱」。
> 所以**悬停浮层 / 热区 / 层级置顶 / Bottom Sheet 这一整套都不做** —— 本 PLAN 只保留

## 现状(代码事实,非推测)

1. **投票早就是匿名的,不需要新身份模型。**
   `apps/api/src/db/schema.ts:145-154` 的 `film_vote_contribution` 以
   `(edition, film_key, contributor)` 为主键,`contributor` 是**身份串**:登录时是账号 `subject`,
   匿名时是 `anon:<SHA-256(匿名 cookie)>`(`film-vote-store.ts:172` 的 `ANON_PREFIX`)。
   ⇒ 口径 1 不引入任何新东西,**直接沿用**。

2. **⚠ `contributor` 有一条硬约束:绝不能回给公开接口。**
   `film-vote-store.ts:212-214` 原话:
   > 自查接口回给浏览器的一行。⚠ **刻意不含 `contributor`** —— subject 是账号标识,回出去就是
   > 「谁投了什么」的名单;匿名 hash 虽不可反查,但它能当跨表 / 跨接口比对的抓手。
   全站唯一回它原文的地方是 `VoteAdminRow`(`:269-271`,门禁在 `/api/admin/*`)。
   ⇒ 这条约束与本需求的字面表述(「显示是**哪位用户**贴的」)是**直接冲突**的,必须先解耦(见下)。

3. **当前只有聚合计数,没有明细。**
   公开读接口 `GET /api/stats/film-votes` 按 `edition` 回 `Record<filmKey, {red, black}>`
   (`apps/web/src/film-votes.ts:17`);写入是 `POST /api/stats/film-votes-ping`,
   **整份替换**语义(`film-vote-store.ts:32-40`),前端载荷只有 `{ key, vote }`
   (`film-votes.ts:150`)。

4. **前端贴纸里没有评语字段。** `apps/web/src/redblack.ts:19-24` 的 `Sticker` 只有
   `{ id, type, posX, posY }` —— 评语在这个需求里是**全新维度**,不是「补个浮层」。

5. **群点位置是纯确定性的。** `redblack.ts::crowdStickers` 由 `(filmKey, index)` 推导,
   三处共用(卡片画布 / 「看全部」弹层 / 分享图)。2026-09-29 落点已改成
   **「中间密、四周疏的矩形」**(`softSpot`)—— 不再铺满四角,也没有可见的边界。
   ⇒ 中心那片的重叠度更高,「要求精准点中那一枚 8px 的点」这条路不通(见取舍表)。

6. **线上票量级很小。** `film-vote-store.ts:179` 注释:「线上目前是个位数票」——
   全量拉明细今天完全可行,但接口形状**不能按今天的数据量设计**(见取舍表)。

## 关键矛盾与解法(本 PLAN 的核心)

**矛盾:** 用户要「显示是谁贴的」,而既有安全口径规定 `contributor` 不得出公开接口。

**解法:把「身份标识」与「对外展示名」拆成两个字段,只公开后者。**

| 字段 | 内容 | 公开? |
|---|---|---|
| `contributor`(已有) | 登录 `subject` / 匿名 `anon:<hash>` | ❌ 绝不 —— 维持现约束,不新增任何出口 |
| `display_name`(新增,可空) | **写入时快照**的账号昵称;匿名 / 未登录时为 `null` | ✅ 是 |
| `comment`(新增,可空) | 用户写的评语正文 | ✅ 是 |

- `display_name` 用**快照**而不是 join 账号表:① 账号昵称会变,评语读的是「当时那句话是谁说的」;
  ② 公开接口不必去碰账号库,不新增一条跨库读取路径。
- 匿名用户的 `display_name` 是 `null` → 前端显示「匿名观众」。
  ✅ **口径已定(2026-09-29):匿名评语也公开** —— 读到的只有「一个匿名观众说」+ 正文,
  **读不到是谁**(`contributor` 那一层仍然不出公开接口,两者是解耦的)。
  这与「不登录也能贴纸」是同一条口径的延伸:能贴就能说,不额外要求登录。

## 范围

**做:**

1. **数据层(D1 迁移)**:`film_vote_contribution` 加 `comment`(text, nullable)、
   `display_name`(text, nullable);不需要改 `film_vote_stat`(评语不进聚合)。
   新迁移文件按既有编号顺延。
2. **写路径**:`POST /api/stats/film-votes-ping` 的载荷由 `{key, vote}` 扩到
   `{key, vote, comment?}`;**整份替换语义不变**(撤票 / 改色时评语一起走,不留孤儿)。
   服务端校验:长度上限(暂定 **140 字**,按 Unicode 码点算)、去掉首尾空白、空串归一成 `null`。
3. **读路径(新接口,跨片)**:`GET /api/stats/film-comments?edition=&cursor=&limit=`
   —— 按 `updated_at` 倒序回**全局**最近的评语,形状与分页口径见末尾「已定:评语区落点」。
   ⚠ **不含 `contributor`**(游标在内,任何一处都不许夹带)、**不 join 账号库与影片库**。
   ⚠ 只回**有评语**的行。
   ⚠ 需要新索引 `(edition, updated_at)`:现有索引是 `(edition, contributor)`(按人查「我的票」),
     跨片按时间拉取走不上它。
4. **前端 —— 评语走「榜单下方的页面级模块」,不许挂在贴纸上**(用户 2026-09-29:
   「评语我觉得单独做一个模块吧 不要放在贴纸上 不然很乱」)。
   - 新增 `apps/web/src/film-comments.ts`:`loadFilmComments({ cursor })` + 按页缓存,
     失败静默降级(与 `film-votes.ts` 同一条「接口没上线也能用」原则);
     模块外框复用既有卡片样式,不新造一套骨架;
   - **贴纸回到纯视觉**:红黑点仍然只是一枚枚贴纸,不挂 Popover、不做悬停命中计算;
   - 一行的组成:**片名**(由 `filmKey` 走目录反查)+ 昵称(匿名 →「匿名观众」)+ 正文;
   - 写入口也在模块里(没写过的人在那儿写、写过的人在那儿改),复用同一条写路径;
     ⚠ 写之前必须**已有这一部片的票**(一人一片一票一评)—— 没贴过的人要先在卡片上
     标记「看过」再贴;这条要在 UI 上说清,否则用户会以为「模块里能给任意片写评语」;
   - 翻页用「加载更多」按钮(走游标),**不做无限滚动**:它落在页面最底部,
     滚动触底在窄屏上不稳定(观感与性能都不好)。
5. **测试**:服务端纯函数单测(校验 / 截断 / 归一)、写路径回归(撤票时评语一起消失)、
   E2E 一条(评语区能读能写;且**贴纸上没有任何浮层**)。

**不做(以及理由):**

- **不改投票身份模型**(不引入登录要求)—— 口径 1 已定,且现有 `anon:` 机制本就支持。
- **不在公开接口暴露 `contributor`** —— 见「关键矛盾」;这条**不给任何例外**。
- **不做「+1 / 同感」** —— 它是第二张表 + 第二个写接口 + 第二套限流,
  与「先让评语读得出来」是两件事。**本轮不排期**,等评语上线看真实使用率再说
  (用户原话也是「互动扩展**建议**」)。
- **不做头像** —— 账号系统当前不回 avatar 字段(需先确认 `apps/account` 是否提供);
  先用「昵称首字 + 品牌色圆底」的占位,不阻塞本轮。
- **不做按片的评语弹层**(候选 A)—— 用户选了页面级模块;两套入口会让「评语在哪」有两个答案。
- **不做评语的点赞 / 热度排序** —— 一条直线按时间倒序;要「点赞最高的」得再加一套计数与索引,
  与「先让评语读得出来」不是一件事。
- **不做「自动散开 / 磁吸」** —— 见取舍表。
- **不动分享图**:分享图是静态出图,浮层交互在图上没有意义(评语将来若要进分享图,另开)。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 公开接口直接回 `contributor`,前端自己查昵称 | 否决 | 打破 `film-vote-store.ts:212` 的既有硬约束,且把「谁投了什么」的名单发出去 |
| 新增 `display_name` 快照 + `comment`,只公开这两个 | **采纳** | 展示需求与身份标识解耦;公开接口不碰账号库,不新增跨库读取 |
| 明细分**全量**(跟着聚合接口一起回) | 否决 | 今天票是个位数所以「看起来还行」,但评语是长文本 —— 全量响应体会随票数线性膨胀,而用户一次只看得到一两张卡 |
| 明细**按片按需拉**(新接口）+ 前端缓存 | **采纳** | 与 `loadFilmVotes` 同一套「点了才拉」;卡片数量近 300,预取等于把整榜评语拖下来 |
| 评语并入 `film_vote_stat` 聚合表 | 否决 | 聚合表是 `(edition, film_key)` 粒度,装不下「一条一条的评语」 |
| 独立一张 `film_vote_comment` 表 | 否决 | 评语与票是**一对一**的(一人一片一票一评),拆表后「撤票时评语怎么办」要两处协调 —— 同一口径两份实现(红线 5) |
| 沿用 `film_vote_contribution` 加两列 | **采纳** | 撤票 / 改色走同一个 `replaceContributorVotes`,评语自动跟着走,不会留孤儿 |
| 悬停红点弹 Popover 看评语(用户**初版**设想) | **否决**(用户当天自己改口) | 「评语我觉得单独做一个模块吧,不要放在贴纸上,不然很乱」。而且它还要连带解决「重叠时点不中」与「移动端没有 hover」—— 两件事互相牵制 |
| 评语**独立成一个区域**,贴纸保持纯视觉 | **采纳** | 贴纸回到「只是贴纸」,评语回到「只是列表」;画布上不再需要任何命中计算,「点不中重叠的点」这个问题随之消失 |
| 重叠时**自动散开 / 磁吸**(悬停方案的配套) | 否决 | 会与「点位置由 `(filmKey, index)` 确定性推导」冲突 —— 位置一动,`crowdStickers` 的三处消费者(卡片 / 放大弹层 / 分享图)就得各写一份「临时位置」 |
| 匿名评语也公开 | **采纳**(2026-09-29 用户拍板) | 与「不登录也能贴纸」同源:能贴就能说。读到的只有「一个匿名观众说」+ 正文,`contributor` 那一层仍然不出公开接口 |
| 评语长度不设限 | 否决 | 公开字段 + 无上限 = 一块免费的公告板;定 **140 字** |

## 验收标准

## 已定:评语区落在**榜单下方的页面级模块**(用户 2026-09-29 拍板)

用户选了 **B** —— 「榜单下方一个页面级『大家说』模块」:独立区块,列最近的评语(带片名)。

**为什么可以接受它的代价**:`film_vote_stat` 那套按片聚合确实用不上,要另建按时间排序的索引;
但评语总量本来就小(线上票是个位数),而「一眼看到全场在说什么」正是用户要的。

**读接口因此是跨片的**:

- `GET /api/stats/film-comments?edition=<id>&cursor=<opaque>&limit=<n>`
- 回 `{ items: [{ filmKey, vote, comment, displayName }], nextCursor: string | null }`
- **只回写了评语的行**(没评语的行回来也没有内容可展示);
- 排序:`updated_at` **倒序**(最新在前);
- 分页:`(updated_at, film_key)` 复合游标,**服务端编码成不透明串**再回 ——
  ⚠ 游标是公开响应体的一部分,**不许夹带 `contributor`**(与「不回身份」是同一条约束);
  ⚠ 已知边界:同一毫秒内同一位用户给同一部片改两次,游标会跳过其中一条 ——
  概率极低、刷新即恢复,不值得为它上「三元组游标」那点复杂度;
- `limit` 由服务端夹在 `1..50`,默认 20;
- **不 join 账号库**(`display_name` 是写入时的快照)、**也不 join 影片库** ——
  前端本来就有完整目录(`useCatalog`),拿 `filmKey` 反查片名即可。
