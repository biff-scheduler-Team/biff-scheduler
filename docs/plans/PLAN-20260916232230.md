# PLAN-20260916232230 — 新增「吃喝」页：把《BIFF吃喝》表格搬进系统，接 Google 信息并支持用户提交店铺

## 目标

用户原话：

> https://docs.qq.com/sheet/DRWpTTmpsc1dmRERy 我把这个也放系统里吧 看能不能多获得一些 google 上的一些信息?
> 然后能够支持一键跳转到 google maps 然后提供一个入口让用户提供自己的心仪的店铺

拆成四件事：

1. 把《BIFF吃喝》这份釜山（海云台 / Centum）餐厅表变成站内可浏览的页面；
2. 每条店铺支持**一键跳转 Google Maps**（移动端直接唤起 App）；
3. 通过 **Google Places API** 补充评分 / 营业状态 / 照片；
4. 给用户一个**提交自己心仪店铺**的入口，默认只存本地，登录 IFFDAY 后同步到**自己那份**。

### 现状事实（已核实，非推测）

- 表格是腾讯文档**只读分享**（`can_export: 1`），仅一个工作表「餐厅」。
- 表头 12 列：`序号 | 韩文名 | 英文名 | 中文名 | 营业时间 | 菜单 | 人均（人民币） | 韩文地址 | 英文地址 | 备注 | 链接 | 赶场`。
- 该页是 **canvas 渲染**，DOM 取不到单元格；数据走 `docs.qq.com/dop-api/opendoc` 的 protobuf 载荷
  （`clientVars.collab_client_vars.initialAttributedText.text[0].related_sheet`，zlib 压缩的 protobuf：
  `1.5.19.5` = 字符串池，`1.5.19.6` = 单元格 `(row, col, textIndex)`）。**仓库里不引入这个解码器**（见「方案取舍」）。
- `apps/web/src/legend.ts:246` 已有 `mapsUrl(place)`（`google.com/maps/search/?api=1&query=`），
  现有场地卡片的「在 Google 地图打开 ↗」走它 —— 这是**唯一口径**，新页面复用而不是另写。
- 「用户贡献数据」既有链路：`workspace-storage.ts` 写 `biff.*` → 派发 `iffday:workspace-change`
  → `account-sync.ts` 防抖上传。`sync-data.ts:105` 把任何 `biff.*` 键**原样**装进 `local:biff.<key>`，
  `writeWorkspace:130` 再原样还原；服务端白名单 `apps/api/src/index.ts:75-93` 的正则
  `/^(pick:|plan:|local:biff\.|raw:biff\.)/` **已放行**新键。
  → **新增 `biff.eats.v1` 不需要改同步层、不需要改 D1 schema。**
- `apps/api` 走 Hono；`worker.ts:7` 只把 `/api/*` 交给 app，其余转发给 web Worker。
  全局同源校验在 `index.ts:113-123`（**无 CORS 头、无 OPTIONS 预检**）。
- **仓库内没有任何「代理公网第三方 + 缓存」的先例**（唯一外呼是 `IFFDAY_API` service binding）；
  也没有 KV / `caches.default` 使用痕迹。
- 密钥惯例：`wrangler secret put`，**不进仓库**（`docs/plans/PLAN-20260914164050.md:140`）。

## 范围

**做：**

1. 离线管线 `tools/build_eats.py`：读**导出的 xlsx/csv**（或本地快照），规范化后产出并检入
   `apps/web/public/eats.json`（含 `id` slug 与 `district` 归一）。
2. 新增 `/eats` 页面 `apps/web/src/pages/EatsPage.tsx`：搜索 + 分区筛选 + 品类筛选 + 卡片列表，
   每张卡一条「在 Google 地图打开 ↗」（复用 `legend.ts` 口径）。
3. Worker 代理 `GET /api/eats/places`：按 `id` 批量取 Google 评分 / 营业状态 / 照片，
   **带边缘缓存**；未配置 `GOOGLE_MAPS_API_KEY` 时返回 `503 GOOGLE_DISABLED`，前端**静默降级**为只显示跳转链接。
4. 用户提交店铺上下两端，存 `biff.eats.v1`（本地优先，登录后经既有链路同步到自己那份）。
5. 单测 + E2E：`tools/build_eats.py` 的归一化逻辑、`biff.eats.v1` 读写、Google 代理的降级分支、
   `/eats` 页面的渲染与筛选。

**不做（同等重要）：**

- **不把腾讯文档的 protobuf 解码器写进仓库** —— 一次性的取证手段，进仓库就是长期维护一个未公开私有格式。
- 不做 OAuth/账号体系改动；不改 D1 schema；不改 `sync-data.ts` 的合并规则。
- 不做「多人可见的公共店铺库」：用户提交的店铺**只在自己账号内**，不写任何共享位置（红线 7）。
- 不做店内的营业时间倒推「现在是否营业」的本地算法 —— 该信息只信 Google（`openNow`），无 Key 就不显示，
  不自己算一份（避免与 Google 口径冲突）。
- 本期不接 Google 照片以外的 Places 字段（不做路线规划、不做实时拥挤度）。
- 不改 `legacy/`（该目录是只读回退件，本次不是 P0 修复）。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 构建时实抓腾讯文档 | **否决** | 依赖第三方私有接口，构建不稳定；与项目「离线管线产物检入」惯例冲突 |
| 仓库内实现 protobuf 解码器 | **否决** | 私有格式无契约，一变更就红；一次性取证用过即弃 |
| 读导出的 xlsx/csv → 检入 JSON | **采纳** | 产物可 review、可 diff、不依赖外部可用性；导出是 1 次点击 |
| 新增独立页 `/eats` | **采纳**（用户选定） | 与「影片库 / 讨论区」同级，改动最小、后续好扩展 |
| 只做 Maps 深链、不接 API | 否决（用户选 API） | 但**保留降级路径**：无 Key 时页面必须仍然完全可用 |
| Google 数据由前端直连 | **否决** | 会把 API Key 暴露到浏览器；必须 Worker 代理 |
| 边缘缓存用 KV | 否决 | 要新增 binding 与配置；`caches.default` 零配置即可 |
| 用户店铺存 `biff.eats.v1`（数组整键合并） | **采纳** | 与 `biff.filters.v1` 等同级；`pick:` 那套逐条合并是给需要跨设备独立增删的片单选片用的，店铺列表不需要 |
| 用户店铺另建 D1 表 / 公共端点 | **否决** | 红线 7；且要动 schema 与迁移，收益不匹配 |

## 验收标准

1. `/eats` 能列出 `eats.json` 里的全部店铺；搜索（三语名 / 地址 / 菜单）与分区、品类筛选生效；
   空结果有明确空态。
2. 每张卡片的「在 Google 地图打开 ↗」用 `name + address` 拼 query，`target=_blank rel="noopener noreferrer"`。
3. **未配置 `GOOGLE_MAPS_API_KEY` 时**：`/api/eats/places` 返回 503，页面不报错、不显示空壳评分块，
   跳转链接照常可用（这是本轮的默认路径，Key 到位后才点亮）。
4. 配置 Key 后：卡片显示评分 / 评分人数 / 营业中·已打烊 / 照片；同一店铺二次访问命中边缘缓存
   （响应头或上游调用次数可证）。
5. 用户提交店铺：未登录时写入本地并立即出现在列表；刷新后仍在；登录后出现在自己账号的云端副本里，
   **另一个账号看不到**。
6. 命令：`npm run verify:quick` 全绿；`npx playwright test -c playwright.react.config.ts e2e/react/eats.spec.ts --project=desktop-chromium` 全绿。

## 修订 1（2026-09-16，触发原因：用户改口「先降级」，并要求补 Naver / Kakao）

**决策变更 —— 本轮不接任何第三方 API，改为「三站跳转」。**

原方案第 3/4 条（Google Places 评分 / 营业中 / 照片）**本轮不实现**，整段推迟；页面改为同时提供
**Google / Naver / Kakao 三个地图跳转**。三条链接都是普通 URL，**零密钥、零配额、零成本**：

| 服务 | 模板 | 备注 |
|---|---|---|
| Google Maps | `google.com/maps/search/?api=1&query=<q>` | 已抽成 `legend.ts::mapsUrlForQuery()` |
| Naver 地图 | `map.naver.com/p/search/<q>` | 韩国店命中率最高；表里有韩文名，用它当 query |
| Kakao 地图 | `map.kakao.com/link/search/<q>` | |

**为什么先降级**：Google Places 的 `places.rating` / `userRatingCount` / `regularOpeningHours`
属于 **Text Search Enterprise** SKU，免费额度只有 **1,000 次/月**（不是 Essentials 的 10,000），
且需要绑定境外可用的结算账号。而跳转路径完全不依赖这些，先把功能做完整更划算。

**二期候选数据源（记下来，本轮不做）**：韩国店其实更适合本土数据源，且都不需要绑卡 ——
Naver 地域搜索 `openapi.naver.com/v1/search/local.json` **25,000 次/天**；
Kakao 关键词地点搜索 `dapi.kakao.com/v2/local/search/keyword.json` **100,000 次/天**
（坑：Kakao 免费地图配额只给账号下**第一个激活的应用**）。

**新发现的限制（影响数据完整性）**：原表「链接」列有 6 条人工整理的链接（小红书 1、naver.me 2、
instagram 2 等），**腾讯文档导出 CSV 会丢失超链接**（单元格文本是「链接」二字，URL 不在文本里）。
已尝试直接从文档数据载荷里恢复：能取到 URL，但**无法可靠对应到行**（7 个链接单元格 vs 5 个 URL，
索引对不上）。故：

- 本轮 `eats.json` **不含 `link` 内容**，页面统一用自动生成的搜索链接；
- 若用户后续补 **xlsx 导出**（保留超链接），再由管线写入 `link` 并优先展示。

### 修订 1 补充：密钥填入口（2026-09-16，用户要求「留一个密钥填入口」）

跳转是零成本的骨架；**数据源查询的代码路径已经写好并留了开关**，密钥一填就生效：

| 位置 | 内容 |
|---|---|
| `apps/api/src/place-lookup.ts` | Naver / Kakao 两家的适配（归一化与网络调用分开，纯函数可测） |

npx wrangler secret put KAKAO_REST_API_KEY -c apps/api/wrangler.jsonc

### 修订 1 补充：怎么注册这两个数据源

**Naver 地域搜索（25,000 次/天，不用绑卡）**

1. 打开 `developers.naver.com` → 登录 Naver 账号 → **Application → 애플리케이션 등록**。
2. 使用 API 里勾 **「검색」**（地域搜索属于 Search API，不勾会返回 `403`）。
3. 환경 选 **WEB**，등록할 서비스 URL 填站点域名（本地调试填 `http://localhost:31028` 即可，该字段不参与鉴权）。
4. 注册完成 → **내 애플리케이션 → 개요** 里拿到 **Client ID** 与 **Client Secret**
   → 分别填给 `NAVER_CLIENT_ID` / `NAVER_CLIENT_SECRET`。
5. 调用形态：`GET https://openapi.naver.com/v1/search/local.json?query=<名称 地址>&display=5`，
   两个密钥走 **请求头**（不进 URL）。返回 `title`（含 `<b>` 高亮，需去标签）、`link`（精确店铺页）、
   `roadAddress`、`mapx`/`mapy`（**1e7 放大的 WGS84 整数**）。

**Kakao 关键词地点搜索（100,000 次/天，不用绑卡）**

1. 打开 `developers.kakao.com` → 로그인 → **내 애플리케이션 → 애플리케이션 추가하기**。
2. 建好应用后 → **앱 키** 页拿 **REST API 키** → 填给 `KAKAO_REST_API_KEY`。
3. **必须再开权限**：해당 앱 → **카카오맵**（或 제품 설정 → 카카오맵）→ 「사용 설정」打开，
   「키워드로 장소 검색」勾上；否则调用回 `403`。
4. ⚠ **免费地图配额只给开发者账号下「第一个激活的应用」** —— 之后再建的应用没有免费额度。
   别为了测试随手多建应用，否则配额算到第一个上去。
5. 调用形态：`GET https://dapi.kakao.com/v2/local/search/keyword.json?query=<名称 地址>&size=5`，
   密钥走 **`Authorization: KakaoAK <REST API 키>`**。返回 `place_name` / `place_url`（精确店铺页）/
   `road_address_name` / `phone` / `x`（经度）/ `y`（纬度），**已经是十进制度**。

### 修订 3（2026-09-16，触发原因：Kakao 密钥到位后实测命中率）

**实测数字（38 家店，走生产同一份 `lookupKakao`）：命中 27/38 = 71%**，且命中项逐条对得上
（`스타벅스 센텀KNN점` → 精确到 `센텀서로 30`；`오설록` → `티하우스 해운대점` 并带电话）。

**探针跑出两个必须写进代码的结论**（都已落成注释与测试）：

1. **检索串不能是「店名 + 整条地址」** —— Kakao 关键词搜索对长串**直接返回 0 条**，
   第一版探针因此 40 家全灭。
2. **只用店名会全国排名** —— `CU` 的第一名在济州、`오설록` 的第一名是济州博物馆。
   名称闸门（互相包含）**挡不住这类错误**，因为它只比名字、不看城市。

于是改成 **检索串 = `店名 + 区名`**（区名从韩文地址里取 `…구/…군`），并追加**行政区校验**
（命中地址必须含该区名）。**推不出区名就放弃查询** —— 宁可没有精确链接，也不挂一个错店的链接。

**11 家查不到**（保持三个搜索链接，功能不受影响）：`甜甜圈`、`新世界/乐天地下一层美食街`、
`Angelsinus`、`60年传统奶奶汤饭`、`芝麻糖饼`、`密阳血肠猪肉汤饭`、`부산미가되지국밥`、
`긴자료코 부산센텀점`、`와 센텀트럼프 월드점`、`커피프론트`。
其中 `60년전통할매국밥` 在 Kakao 上的登记名是 **`70년전통 할매국밥`**（60/70 之差），
`커피프론트` 是 **`프론트커피`**（词序）—— 都属于**表里的名字与地图登记名不一致**，
不是策略问题。要捞回来得做模糊匹配，代价是可能挂错店，**本轮不做**。

**顺带修掉一个真实缺陷**：表里第 22、23 行**没有任何店名**（只有时间/菜单/地址）。
原管线会给它们生成同一个哈希 id 并渲染出**空白卡片** —— 现已改为在管线里**直接跳过**并打印告警。
所以店铺数是 **40 → 38**。

**两家共同的注意事项**

- 这两个接口**都不返回评分** —— 页面不会出现任何评分 UI（只有 Google 有评分，但那是 Enterprise SKU、
  免费仅 1,000 次/月，本项目不接）。所以卡片上补出来的是**精确店铺页 + 道路名地址 + 电话**。
- 上游第一条结果未必是目标店（小馆子重名多）→ 适配层用「名称能互相包含」当闸门，
  对不上就返回 `null`，卡片**退回搜索链接**而不是挂一个错店的精确链接。
- 超时 4 秒、失败一律当「没查到」；服务端按 「provider + query」缓存 30 天（isolate 内存）。

### 修订 2（2026-09-16，触发原因：用户直接粘贴了表格原文）

**数据来源改为「用户提供的表格原文」，解码器退为取证手段。** 后续如果再补数据，
直接编辑 `data/_cache/biff-eats.csv`（与表格同表头）后重跑 `tools/build_eats.py`，不必碰文档载荷。

**为什么必须换**：原表「人均（人民币）」是**数值单元格**，与字符串单元格不是同一套编码 ——
字符串解码只能拿到上一行的串行残留（整段地址 / 菜名）。所以第一版 `eats.json` 里那一列 40 家全空。

| 项 | 修订 1 的状态 | 修订 2 的结果 |
|---|---|---|
| 店铺数 | 40（含 2 行解码伪行） | **40**（与原文逐行核对） |
| `人均` 有值 | 0 家 | **35 家**（另 5 家在表里就是 `-`，按「未知」处理成空） |
| `链接` 有值 | 0 家 | **5 家**（对应表里 5 个链接单元格） |
