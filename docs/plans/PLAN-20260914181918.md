# PLAN-20260914181918 — 修复 token 刷新把健康会话打成 401 的链路

## 目标

线上 `/api/account/me` 先返回 `503 {"error":"SERVICE_UNAVAILABLE"}`，紧接着变成
`401 {"error":"UNAUTHENTICATED"}`，用户被踢出登录。要把这条「一次瞬时刷新失败 → 会话被误删」
的链路掐掉。

用户原话（不要转述）：

> https://biff.lcandy.co/api/account/me 503 Service Unavailable
> {"error":"SERVICE_UNAVAILABLE"} 分析下问题

> 又有了 {error: "UNAUTHENTICATED"}

> 建议的修复方向 1-7 写一个 PLAN 然后开始执行

### 现状（代码事实，含行号）

`{"error":"SERVICE_UNAVAILABLE"}` 只有一个来源：`apps/api/src/index.ts:730-735` 的 `app.onError`
处理 `HTTPException(503)`；全仓库只有两处抛它，都在 `apps/api/src/oauth.ts::sessionFor()`：

- `oauth.ts:121` — 刷新抛了**非 `invalid_grant`** 的异常（上游 5xx / 超时 / `invalid_client` / 验签失败）
- `oauth.ts:124` — 12 × 200ms ≈ **2.4s** 的租约等待耗尽

`401 UNAUTHENTICATED` 对 `/api/account/me` 只有两条路径：`index.ts:242`（`sessionFor` 返回 null）
与 `index.ts:248-255`（上游 profile 返回 401 → 删会话）。结合「先 503 后 401」，
且 503 的两条分支**都不删会话**（`oauth.ts:120` 只把 `refresh_until` 归零），
可判定 401 来自 `sessionFor` 返回 null，最可能是 `oauth.ts:116-118` 的 `invalid_grant` 删除。

### 根因（4 个具体缺陷）

| # | 位置 | 缺陷 |
|---|---|---|
| ① | `oauth.ts:115-122` | 刷新失败时上游**可能已消费掉 refresh token**（轮换非原子：请求已到上游、RT1 已换 RT2，但响应 5xx / 丢失 / `validateApplicationLevelSignature` 失败）→ 本地仍留已死的 RT1 → 下次必然 `invalid_grant` |
| ② | `oauth.ts:116-118` | `invalid_grant` 时**无条件按 `token_hash` 删行**，不校验 payload 版本。并发刷新的「败者」会删掉「胜者」刚写入的健康会话 → cookie 还在、行没了 → 401 |
| ③ | `oauth.ts:120` | `refresh_until` 重置**无条件**（只有 `where token_hash`），会踩掉别人刚拿到的租约 → 放大并发 |
| ④ | `oauth.ts:112-114` | 持久化新 token 时**不读 `changes`**，`where` 里的 `eq(payload, row.payload)` 命中 0 行时静默当成功 → 新 RT2 丢失 |

放大器：上游（better-auth）开启 refresh token 轮换 + 重用检测，一次误判会撤销**整个 token family**，
所以这条链路**不可自愈**，只能重新登录。

## 范围

**做（对应建议的 1-7）：**

1. `invalid_grant` 的删除改成**条件删除**（带 payload 版本校验）；命中 0 行说明别人已写入新 token，
   回到循环重读并返回胜者的会话，而不是删行 + 返回 null。
2. `refresh_until` 的重置改成**条件更新**（只有自己仍持有那次租约时才归零）。
3. 持久化新 token 时**检查 `changes`**；为 0 时丢弃本次结果、重读并采用胜者的 token。
4. 给 service binding 的 `fetch` 加**硬超时**（`AbortSignal.timeout`），避免上游挂死拖到 isolate
   被回收、留下未被重置的租约。
5. **对齐租约窗口与等待窗口**：把「租约 / 等待 / 单次上游超时」三个口径提成显式常量并锁成不变量
   （`REFRESH_WAIT_MS >= REFRESH_LEASE_MS >= 2 × IDENTITY_TIMEOUT_MS`，且等待窗口小于前端 12s 的 abort），
   不再用写死在循环里的 12 × 200ms。
6. **补日志**：两条失败分支分别打点，记录 oauth error code / 上游 status（**不打 token 本身**）。
7. **回归测试**（先红后绿）：覆盖缺陷 ①②③④ 与等待窗口。

**不做：**

- **不改 `apps/api/src/index.ts`**（另一个在途任务已改它 159 行）—— 日志打在 `oauth.ts` 的抛出点，
  那里信息更精确，也避免与在途改动重叠。
- **不改前端 `apps/web/src/account-sync.ts`**：503 已按可重试处理（`initAccountSync` 落 `offline`、
  `syncAccount` 20s 轮询重试），不是本次故障的必要条件。
- 不重构 `sessionFor` 的整体结构，不引入依赖，不动 D1 schema / 迁移。
- 不实现「refresh token 家族级重试」（上游行为，不在本仓库可控范围）。

### ⚠ 对建议第 5 条的后半句提出反驳（请复核）

原建议是「等不到锁时**降级为 401（提示重新登录）**而不是 503」。**这一条我建议不做**，理由：

- `503` 在这里的语义是「**可重试的临时故障**」，前端已经按可重试处理并会自动恢复；
- 改成 `401` 会让前端 `identify()` 返回 null → 提示「登录已过期，请重新登录」，
  **为一次几秒的瞬时故障强制用户重新登录**，是严格更差的行为；
- 更要紧的是：本次故障的现象恰恰**就是 401**。把等待超时也改成 401，等于把刚修掉的症状再引回来。

所以第 5 条只做**前半句**（对齐窗口），等待耗尽**保持 503**；配合缺陷 ④ 的超时后，
租约持有时间变成有界，这条分支会变得极罕见。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 修 `sessionFor` 的 4 个缺陷（条件删除 / 条件释放 / 检查 changes / 超时） | **采纳** | 直接切断「瞬时失败 → 会话被误删」链路，改动集中在一个文件 |
| `invalid_grant` 一律删会话（现状） | 否决 | 并发时败者删掉胜者的健康会话（缺陷 ②），是 401 的直接成因 |
| 等待耗尽降级为 401 | 否决 | 见上，会把刚修掉的症状引回来 |
| 把刷新逻辑抽成纯函数以便测试 | 否决 | 会改动 `sessionFor` 结构、扩大回归面；用 D1 替身 + mock `oauth4webapi` 已足够覆盖 |
| 用隔离 worktree | 否决 | 本次改动与在途改动**零文件重叠**（只动 `oauth.ts` + 新增测试），且用户要在本工作树看效果 |
| 依赖真实 miniflare D1 跑单测 | 否决 | 单测要快且无网络；用 `node:sqlite`（Node 24 内置）做 D1 替身，跑的是**真实 SQL** |

## 修订

### 修订 1（2026-09-14，执行中发现）

**1. 顺带修掉一条既有 flake（`apps/api/tests/crypto.test.ts`）。**
`npm run verify` 第一次跑时挂在「密文被篡改则解不开」上。定位结论：**与本需求无关的既有缺陷**，
但会卡住门禁，必须修。

- 成因：原用例把 base64url 密文的**末位字符** `'A'` 改成 `'B'`。去掉 `=` 填充后末位字符仍含 2 个
  填充位，末位是 `'A'`（index 0）时改成 `'B'`（index 1）**解出完全相同的字节** —— 等于没篡改。
- 量化：一次性探针跑 2000 次，**115 次（5.8%）**「篡改后字节完全相同」，与末位为 `'A'` 的占比一致。
- 修法：改成翻转**解码后密文的第一个字节**，再重新编码。探针复验 5000 次，**0 次**未改变字节。
- 归属：应作为**独立提交**（`test(crypto): …`），不混进本次修复。

**2. 缺陷 ④ 的测试是守卫，不是先红后绿。**
原以为「持久化不读 `changes`」会丢 token，实测发现：写入命中 0 行后代码会走到循环末尾、重新读行，
因此**旧实现也能拿到胜者的 token** —— 该用例修复前后都是绿的。仍保留（把意图写死），
但**不声称**它是回归测试。真正先红后绿的是缺陷 ②（并发败者删会话）与缺陷 ③（踩租约），
外加两条窗口口径不变量。

**3. `PLAN.md` 存在并发编辑。**
另一个在途任务（同场观影 & 场次讨论）正在改 `PLAN.md` §0 同一区域。本次只做**纯插入**一条 bullet，
提交时需按 hunk 拆分，避免把对方改动搭车提交。

**4. 上游真的消费掉 refresh token 的那条链路不可自愈**（见「不做」）。修复只能消除**可避免**的
误删与并发放大；真实失效时仍应删会话 + 401（强制重新登录是正确的）。这一点已在代码注释与
`PLAN.md` 中写明，避免日后被误当成 bug 再「修」。
