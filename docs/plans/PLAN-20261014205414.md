# PLAN-20261014205414 — 红黑榜：手机端排版 / 左右指引 / 撤回条 / 扫码投票二维码

## 目标

用户在微信群里问来的两条反馈（截图对话 + 原话）：

> 不知道左右哪个是喜欢
>
> 需要指引和反悔机制？
>
> 嗯 搞个手机端，生成一个带二维码的图直接扫码投？

> 手机端指引不够我觉得可能是移动端海报太大了 然后像他说的 需要撤回 、指引 、优化手机端排版
> 然后把这个红黑榜链接做成一个二维码吧

四件事，按用户拍板的取舍落地：

1. **手机端排版**：卡片尺寸要受**视口高度**约束 —— 现在只按宽度算，手机竖屏里海报顶满一屏；
2. **左右指引**：不拖动时卡片上看不出「左 = 不喜欢 / 右 = 喜欢」，要有**常驻**的方向说明；
3. **撤回强化**：撤回能力已经有了，但入口是一枚灰弱按钮、投完也没有回执 —— 改成「已投红榜 · 撤回」的状态条；
   ⚠ 用户明确选了**只强化现有撤销、不改投票语义**（同色再点仍是幂等，不新增「取消票」）；
4. **扫码投票二维码**：页面上加一枚按钮，弹出**可保存**的二维码图片，用于分享给朋友扫码进入快速投票。
   用户原话：「二维码是你直接在页面上嵌入一个按钮弹出可保存的二维码 用于分享」。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 卡片尺寸只按宽度（现状 `min(78vw, 320px)`） | 否决 | 手机竖屏里高度 = 宽度 × 1.5，**宽度定死了高度**，而屏幕的瓶颈恰恰是高度 |
| 卡片尺寸加 `vh` 上限 | **采纳** | 一行 `min()` 就把「矮屏不顶满」这件事表达完；桌面端仍受 `320px` 约束，零影响 |
| 窄屏隐藏简介 | **采纳** | 简介是卡片里唯一「整段话」，也是最长的一段；手机上认片靠海报 + 片名 + 场次 |
| 指引做成一次性引导蒙层（首访才出现） | 否决 | 用户朋友的问题是「**每次**都想不起来左右是什么」，而不是「第一次不知道」；且蒙层要新状态、要记住「看过了」 |
| 指引做成常驻方向图例 | **采纳** | 无状态、无记忆、每次都看得见；与跟手的 `.qv-mark` 分工明确（左给「是什么」、右给「会投成什么」） |
| 按钮文案保留「投黑榜 / 投红榜」 | 否决 | 「黑 / 红」是榜单术语，新用户读不出方向；用户朋友的问句就是证据 |
| 按钮文案改「← 不喜欢 / 喜欢 →」 | **采纳** | 方向 + 语义一次说完；「黑 / 红」仍在卡片的跟手标记与榜单里，术语没丢 |
| 撤回做成 Toast（飘一条「已投红榜」+ 撤回） | 否决 | Toast 会盖住卡片、有超时、且与「连续撤回」的诉求错位；卡片里本来就有撤销位，就地升级更省 |
| 撤回做成卡片内的常驻状态条 | **采纳** | 位置不变（用户的手已经在那一带）、无超时、空态也能说明「可以撤回」；`undo()` 逻辑不动 |
| 撤回再加「取消票」（同色再点 = 收回） | 否决（用户拍板） | 会改 `setFilmVote` 的幂等口径与服务端差分语义，本轮不做 |
| 二维码用外部图片服务（`api.qrserver.com` 一类） | 否决 | 现场扫码要**离线可用 / 不依赖第三方**；出图链路一旦第三方抽风，现场就是白屏 |
| 自写 QR 编码器 | 否决（用户拍板） | byte 模式 + RS 纠错 + 掩码评分约 400-600 行，正确性风险高；`qrcode-generator` 4KB gz 且懒加载 |
| 引 `qrcode-generator`（懒加载） | **采纳** | 无 runtime 依赖、MIT、API 极薄（`addData` / `make` / `isDark`）；只在弹层里 import，首屏零成本 |
| 二维码同时画进分享长图 | 否决 | 用户选的是「页面上按钮弹二维码用于分享」；长图的用途是**展示结果**，扫码者的目的是**投票**，两件事 |
| 二维码里编码「首页 / 红黑榜」而不是「红榜 + vote=1」 | 否决 | 扫码的人目的就是投票，多一次点击 = 多一次流失；落地自动弹卡片是既有能力（`BoardPage` 落地逻辑） |

## 修订 3（2026-10-14，实现时按实测收紧）

**触发**：写完第一版（卡片 `min(78vw, 320px, 38vh)` + 矮屏隐藏说明行）后，加了一条 E2E 去量
「390 × 667 里那几行够不够得着」，结果是**差 7px**（`lowest = 674.3 > 667`）—— 最后一行仍要滚。
把卡片改到 `36vh` 后桌面档过了，但**移动端两档还是差 32~34px**
（`lowest = 698.9 / 701.0`：移动端的字体行高更高）。

**最终形态（三处，缺一不可）**

1. 主规则 `width: min(78vw, 320px, 36vh)` —— `982px` 高的桌面上 `36vh = 353px > 320px`，
   所以桌面卡片仍只受 `320px` 约束（**逐像素不变**）；
2. `@media (max-height: 700px)`：卡片再收到 `32vh` + 隐藏说明行 `.qv-help`
   （键盘快捷键在手机上没意义，而它讲的那三件事常驻图例已经逐字说了）；
3. 窄屏 `@media (max-width: 560px)`：不渲染简介 `.qv-intro`（caption 是 `overflow: hidden`，
   被裁掉的正是底部的「红 N · 黑 N」）。

**为什么系数不能直接写小**：低于 `33vh` 时 `982 × 0.33 = 324 > 320` 这条就破了，桌面卡片会跟着缩水 ——
所以矮屏那一档必须用 media query 单独收，否则「桌面零影响」当场失守。

**断言的写法**：用 `getBoundingClientRect().bottom ≤ window.innerHeight`，**不用** `toBeInViewport()` ——
后者走 IntersectionObserver，会把祖先的裁剪算进去，这个弹层里报出来是 `ratio 0`（元素明明在窗口里）；
视口高度也取 `innerHeight` 而不是写死的 `667`（移动端模拟里参与布局的高度与桌面档不同，写死会把差异判成失败）。

**实测**：`390 × 667` 下 `stage = 320`、`lowest = 659 < 667`；
desktop-chromium / mobile-chromium / mobile-webkit 三档该用例全绿，全量 spec 三档各
**41 passed / 1 skipped**。
