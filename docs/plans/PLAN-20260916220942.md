# PLAN-20260916220942 — 把「换 token 被拒」的上游错误码与耗时带到用户眼前（并纠正「超时太短」这一假设）

## 目标

上一轮（`PLAN-20260916215100`，已上线）把 callback 的失败**步骤**变成可见的码。用户重试后拿到：

> 登录未完成，本机排片没有改动。原因：账号系统拒绝发放登录凭证。请重新登录；如果反复出现，请把这句话发给我们。

→ 码是 **`token_rejected`**。用户的追问（原话）：

> 是不是超时时间太短了?

**两个问题必须回答：**
1. 3 秒这个上限是不是把这次登录掐断了？
2. 如果不是，账号系统到底回了什么？

**问题 2 现在答不了**，因为 `describeError(error)` 只进 `console.warn` ——
那是 **Worker 侧**的日志，只有 Cloudflare 控制台能看（本机账号无生产权限，用户也读不到），
所以「上游错误码」这条最关键的证据**仍然是黑的**。这一轮就是把它搬到用户能看见的地方。

## 现状（代码事实 + 2026-09-16 22:0x 实测）

| 事实 | 位置 |
|---|---|
| 每次上游调用套 `AbortSignal.timeout(IDENTITY_TIMEOUT_MS = 3_000)`，注释称其为「硬上限」 | `apps/api/src/oauth.ts:59-64, 96-100` |
| 失败细节只经 `console.warn` 落到 Worker 日志，不进任何回传给浏览器的通道 | `auth-callback.ts:145-157` |
| `token_rejected` 一个码同时盖住三件完全不同的事 | `auth-callback.ts:84-97` |

**实测（本机 curl，22:0x）**：

| 探针 | 结果 |
|---|---|
| `GET /api/auth/login` ×10（内部只调一次发现文档） | 1.81 / 1.95 / 2.04 / 2.11 / 2.26 / 2.34 / 2.47 / 2.70 / 2.70 / **4.39** 秒，**全部成功跳转到账号系统** |
| callback + 真 pending cookie + 假 code（不带 `iss`） | `account_error=authorization`，2.19–3.65s |
| 同上但补上 `iss`（RFC 9207 的 issuer 参数） | **`account_error=token_rejected`**，3.20 / 3.26 / 3.54s —— 走到了换 token 那一步 |
| 直连 `account.iff.day` 的发现文档 | 2.4s（**上游本身就这么慢**） |

**关于「超时太短」的结论**：那 10 次里有一次 **4.39 秒仍然成功**。若 3 秒上限真的生效，
它应该在第 3 秒被中断、并回 `upstream_unreachable` —— 但它成功跳转了。
⚠ **但这**不足以**断言「上限失效**」：`/api/auth/login` 的 4.39 秒里还包含一次 D1 批量写
（2 删 1 插），两段没有分开计时，所以**必须**先把它分开测，再决定要不要动上限。
→ 本轮**不改任何超时数值**（改也是猜），改为把「失败那一步自己耗时多少」变成可见的数字。

**「很久都没跳转」另有解释**：登录 + 回调串行调用上游 **4 次**（发现文档 → 换 token → JWKS → userinfo），
每次 2–4 秒 → 十几秒是正常的。上游慢是独立问题（账号系统本身响应 2–4 秒）。

## 范围

**做：**

1. **契约加取值形态的拼/拆**（口径唯一来源，`packages/contracts/src/account.ts`）：
   - `loginFailureDetailSchema`：上游细节码白名单 `^[a-z_]{1,32}$`（**上游给的东西绝不原样进 URL / DOM**）；
   - `loginFailureParam(code, detail?)`：服务端拼 `token_rejected:invalid_grant`；
   - `parseLoginFailure(value)`：前端拆（未知码原样返回，未知/非法细节丢弃但不影响基础码）。
2. **`apps/api/src/auth-callback.ts` 回传两样东西**：
   - `account_error=<步骤码>[:<上游细节>]`；
   - `account_ms=<失败那一步自己的耗时>`（**这一步**，不是整轮 —— 它就是回答「是不是超时太短」的判据）。
   细节分类：`ResponseBodyError`/`AuthorizationResponseError` → 上游的 `error` 码（如 `invalid_grant`）；
   `TimeoutError` → `network_timeout`；`AbortError` → `network_aborted`；`TypeError` → `network_error`；
   `OperationProcessingError` → `unexpected_response`；其余 → `unexpected_error`。
   **下游只允许白名单值**：不回显任意错误名/消息（异常里可能裹着含 token 的响应体）。
3. **每一步上游调用单独计时**（闭包内的 `stepMs`，**不用模块级变量** —— 同 isolate 并发会串扰，
   上一轮已经因为同样的理由否掉过模块级方案），日志里打一张分步耗时表。
4. **前端展示**：`account-errors.ts` 显示「上游原因：授权码已经被用过或已过期」这类人话
   （没登记过的细节码原样显示），并把耗时拼进 toast / 账号面板 / 控制台三处。
5. **纠正 `oauth.ts` 的注释口径**：把「硬上限」改写成实测事实（**未观察到它中断过慢请求**，
   但 4.39s 那次混了 D1，尚未坐实），并写明「要动这个值必须先分开计时」。
6. 测试：api（分类 + 白名单 + 耗时参数 + 成功路径不变）与 web（解析 + 展示 + 未知细节原样显示）。

**不做：**

- **不改超时数值**（`IDENTITY_TIMEOUT_MS` / `REFRESH_LEASE_MS` / `REFRESH_WAIT_MS` 一个都不动）——
  改动必须等「失败那一步耗时」这个数字出来；`REFRESH_LEASE_MS ≥ 2 × IDENTITY_TIMEOUT_MS`
  这条刷新链路的租约不变量绑着它。
- 不改成功路径（`/?account=connected` 与 cookie 一字不改）。
- 不动上游账号系统（慢与拒绝都可能有它的一半，但不在本仓库）。
- 不动 `legacy/`；不引依赖。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 把上游 `error` 码 + 本步耗时回传浏览器（本轮） | **采纳** | Worker 日志没人看得到；这是唯一能让「拒绝 vs 超时」当场分清的通道 |
| 只把耗时打进日志 | 否决 | 与本轮要解决的问题同因：日志读不到 |
| 直接把上游 `error_description` / 异常消息带出来 | 否决 | 上游响应体可能含 token / 用户数据；只带白名单化的 error 码 |
| 猜着把 3 秒调大 | 否决 | 4.39s 那次混了 D1 耗时，两段没分开；先测再改 |
| 顺手把上游超时改成真正可中断（Promise.race / 换掉 binding） | 否决 | 会动到刷新链路的租约不变量，且本轮目标是**先把数字拿到** |
| 把每步耗时都塞进 URL | 否决 | URL 只带一个数（失败那一步）；完整分步表进日志，够用且不脏 |

   `account_error=token_rejected:invalid_grant` + `account_ms=<数字>`；非法细节码不得进 URL；

2. `apps/web/tests/account-errors.test.ts`：`token_rejected:invalid_grant` 显示人话；
   未登记的细节码原样显示；非法细节被丢弃但不影响基础码文案；耗时拼进整句。
3. `npm run verify:quick` 全绿（web / api / 根单测 + typecheck + lint + check:repo + check:test-map）。
4. 部署后用户重试一次：toast / 面板 / 控制台三处都能读出 **步骤码 + 上游错误码 + 本步耗时**，
   据此**当场判定**「是上游明确拒绝（会给出 `invalid_grant` 之类）还是我们等上游超时
   （会给出 `network_timeout` 且耗时 ≈ 上限）」。
5. 本轮不以「已修复」结案；结案条件是**「拒绝 vs 超时」已当场分清**，并据此决定下一轮是改超时、
   还是去改上游客户端注册 / 授权参数。

## 修订 1（2026-09-16，用户要求把超时加到 10 秒）

用户原话：

> 顺便把超时时间加到10s

**先反驳「直接把 `IDENTITY_TIMEOUT_MS` 改成 10_000」这种读法。** 那个常量被刷新链路的窗口不变量绑着
（`REFRESH_LEASE_MS ≥ 2 × IDENTITY_TIMEOUT_MS`、`REFRESH_WAIT_MS ≥ REFRESH_LEASE_MS`、
`REFRESH_WAIT_MS < 前端 12s abort`，见 `oauth.ts:74-89` 的注释）：持有者要顺序跑完
discovery + refresh 两次调用，若单次上限变 10 秒而租约仍是 8 秒，别的请求会在持有者跑完之前接管租约、
**用同一个 refresh token 再换一次** —— 上游的重用检测会撤销整个 token family。
本条已**写成断言**（`apps/api/tests/oauth-session.test.ts` 的「刷新链路的窗口不变量」）：
把常量改成 10_000 会立刻红 **3 条**（含原有的「★ 上游调用必须有硬超时,且租约能覆盖两次调用」），
实测 `3 failed | 24 passed`，随后已还原。

**采纳的做法（本修订实现的部分）：**

1. 新增 `oauth.ts::AUTH_FLOW_TIMEOUT_MS = 10_000`，**只给登录流程**（`/api/auth/login` +
   `/api/auth/callback`）—— 它没有租约、也不在 `sessionFor` 的请求路径上。
2. `provider(env, clientIp, origin, budget: { timeoutMs?, deadline? })`：单次上限可覆盖，并支持
   **整条流程的总 deadline**；回调共享同一个 10 秒 deadline —— 否则「4 步 × 10 秒」会把用户晾 40 秒。
3. `IDENTITY_TIMEOUT_MS` 保持 3_000，**刷新 / 会话路径一个字节不变**（前端 `api()` 的 12 秒 abort
   也要求它别变大：变大只会让用户看到网络错误，而不是可重试的 503）。
4. 配套测试：4 条不变量断言 + 「deadline 真的会被拼进请求信号并在到点时中断」的机制测试。

**不做**：不动 `REFRESH_LEASE_MS` / `REFRESH_WAIT_MS` / `REFRESH_POLL_MS`；不给会话路径放宽；
不把 10 秒做成「每一步都能耗 10 秒」（总 deadline 才是给用户的承诺）。
