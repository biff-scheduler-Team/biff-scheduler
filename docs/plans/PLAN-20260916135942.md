# PLAN-20260916135942 — 导出弹层加「当前行程」范围（与 /rush 同源）

## 目标

> 「分享图片/文案的批次还是有误 请你看看 参考 https://biff.lcandy.co/rush」
> 「两处的第一批数量明显不一样」
> → 用户选定 **方案 A**：「导出弹层的『导出方案』下拉里加一项『当前行程（与 /rush 同源）』并默认选中 ——
> 内容、顺位、批次三样都和 /rush 完全同源；已保存方案仍可显式选。」

**排查结论（两条根因，第二条是本轮要修的）**：

1. **批次判据没有错，也不缺**：`/rush`（`batch.ts::groupCodesByBatch`）与分享
   （`share.ts::shareUnits` → `batch.ts::ticketBatchOf`）是同一份判据；真实数据实测第 1 批 = 61 场，
   与官网第 1 批品类逐条吻合（开闭幕 2 / 露天 `bt` 8 / Midnight Passion 3 / Actors' House 6 / Community BIFF 901–942 = 42）。
   用户截图的分享图里 `003`（露天、第 1 批）被嵌在 `007`（第 2 批）下面、只印「备选②」——
   这是**修复前**（`6c63051` 之前）的排版；修复版对跨批次备选一律印「007 的备选②」并归第 1 批。
   线上产物 `/assets/main-BLh0yGwX.js` 与本地 HEAD 构建同名同 hash（`altOf` 各 14 处），
   即**线上代码已是修复版**，用户看到旧排版是 PWA 预缓存未刷新（`registerSW.js` 只注册，无「接管后刷新」）。
2. **导出把两个状态混用**：场次取自**已保存方案（快照）**，而顺位 / 备选取自**当前行程**
   （`plans.rankOf` + `groupMatesOf(plans.groups)`）。方案一旦过期（用户拖过顺位或之后又加了场次），
   就会出现「方案里的 `222` 印成主选行 + 它的备选 `805` 印成『222 的主选』」，而 `/rush` 里是
   「`805` 主选 / `222` 备选②」——**顺位措辞与批次内容都与用户预期对不上**。本 PLAN 修的就是这条。

## 范围

**做：**

- `components/ExportDialog.tsx`：`导出方案` 下拉最前面加一项 **「当前行程」**（伪方案 id `current`）**并默认选中**；
  选中它时场次 = `agenda-model.ts::topPlanCodes(plans)`（当前行程「每组第一顺位 + 共同场次」），
  顺位 / 备选 / 批次继续走同一份 `shareOptions`（`plans.rankOf` / `groupMatesOf(plans.groups)` / `ticketBatchOf`）
  ⇒ **内容、顺位、批次三样与 `/rush` 同源**（顺位勾选时分享集合 = 行程全部场次 = `/rush` 的集合）。
- 已保存方案仍可显式选，行为**逐字不变**（快照语义、`planOutline` 概要、空方案回落逻辑都保留）。
- `.ics` 与分享文案 / 分享图片**同用一个 `rows`** ⇒ 选「当前行程」时三者口径一致（不另开一套）。
- 空态收口：`savedPlans` 为空时不再挡在「先保存一个方案」，改为按当前行程继续导出；
  当前选择确实没有可用场次时给一行提示（按钮本就按 `!rows.length` 禁用）。
- 回归测试（E2E，组件层没有 node 单测环境）：`rush.spec.ts` 补「默认按当前行程导出、批次与 /rush 逐条一致」；
  同步修正被本改动影响的 `parity-dialogs.spec.ts`（「默认选最新方案」）与
  `review-state-export.spec.ts`（删方案后的回落 / 全删后的空态）。
- 回写文档：`docs/CONVENTIONS.md` 的「三个出口」小节加范围口径；`PLAN.md` 文档头一行「最后更新」。

**不做：**

- **不动** `batch.ts`（判据已正确）、`share.ts::shareUnits` / `poster.ts` 的排版（备选抬节逻辑已上线）。
- **不动**已保存方案的快照语义与 `savePlan` / `topPlanCodes` 的定义。
- **不动** `.ics` 的字段、`PlanShowsDialog`（方案「查看场次」弹层仍按方案快照，不传 `ShareOptions`）。
- **不动** `legacy/`（只读回退件，且有自己的一份 `export-panel.ts`）。
- 不顺手改 PWA 更新链路（「新版接管后自动刷新」是独立议题，用户未点头，另开 PLAN）。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 下拉加「当前行程」伪方案并默认选中（本 PLAN） | 采纳 | 用户明确选定；分享 = 当前行程的抢票清单，与 `/rush` 完全同源；方案仍可显式选 |
| 导出改为**只能**按当前行程 | 否决 | 已保存方案「导出这一套」是既有语义（`.ics` / 分享都按所选方案），砍掉是功能倒退 |
| 保留纯方案导出，只在方案与行程不一致时提示 | 否决（用户选了 A） | 提示仍要用户手动「按当前行程」；默认就对才是目的 |
| 让 `shareUnits` 自己按当前行程重算（不经过 UI 选择） | 否决 | 会悄悄改掉「导出所选方案」的语义；范围必须由用户在弹层里显式选 |
| 顺带把导出面板的顺位标记改成「方案内自洽」 | 否决 | 与「顺位取当前行程」的既有口径冲突（`PLAN-20260915234414`），本轮不引入第二套口径 |

## 验收标准

1. 打开「导出与分享」：`导出方案` 下拉默认显示 **当前行程**（概要 = N 场 / 日期区间），下拉里「当前行程」在最前，
   已保存方案紧随其后；选任一方案后输出与该方案的场次集合一致（与改动前逐字相同）。
2. 行程与方案不一致时（例如方案里有 `222`、当前组内第一顺位已是 `805`）：默认「当前行程」下
   - 分享文案 / 分享图片里 `805` 出现在 **【第 1 批】** 节并印「主选」，`222` 落在第 2 批并印「备选②」；
   - 勾「带上顺位 + 带上开票批次」后，各批次节的场次**逐条等于 `/rush` 的两节**（8 / 21）。
3. `.ics` / 分享文案 / 分享图片三者在同一范围下集合一致；空行程 + 无方案时给提示而非空下载。
4. `npm run verify:quick` 全绿；受影响 spec 全绿：`rush`、`parity-dialogs`、`review-state-export`
   （`--project=desktop-chromium`），并在 CI 上三浏览器跑一遍。
