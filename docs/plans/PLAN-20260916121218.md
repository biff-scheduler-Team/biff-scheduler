# PLAN-20260916121218 — 修刷新链路的 5 处缺陷（含「上游一次 401 就永久登出」）

## 目标

用户原话：

> 从代码逻辑上看 重新获取 token 的逻辑有没有什么问题

> 请你修复一下

上一轮（`PLAN-20260916104514`）只是把病因变成可观察的：`/api/account/me` 返回
`renewable` 与可区分的 401 原因码。本轮把代码审查中确认的 5 处缺陷修掉。
其中第 1 条是整条链路里**唯一把「可恢复」升级成「不可恢复」**的地方，
与用户现象（cookie 还在、会话行没了、不再刷新、只能重新登录）形态一致。

## 现状（代码事实，含行号）

| # | 位置 | 缺陷 |
|---|---|---|
| ① | `apps/api/src/index.ts:262-263` | 上游 `/api/v1/profile` 回 401 就**删掉整个会话行**。上游 401 的成因不止「失效」：本地 `token_expires_at` 是按「收到响应那一刻 + `expires_in`」算的（比上游签发时刻晚一个网络往返），边界上会拿着刚过期的 token 过去；瞬时故障、限流也会回 401 |
| ② | `apps/api/src/index.ts:256-260` | 该调用**没有硬超时**、也**没转发 `cf-connecting-ip`**；而同文件的 `provider().customFetch`（`oauth.ts:64-73`）两样都有，注释还写明「没有它,上游挂死会把请求拖到 isolate 被回收」 |
| ③ | `apps/api/src/oauth.ts:178` | `result.refresh_token ?? tokens.refreshToken` —— `??` 挡不住空串。上游回 `refresh_token: ""` 时空串入会话，下次刷新 `oauth.ts:138` 的 `!tokens.refreshToken` 成立 → 删行踢人，且错误码误报为「登录时没给 RT」 |
| ④ | `apps/api/src/oauth.ts:136` + `188-194` | 刷新成功后不 `return`，靠「回到循环重读」收尾；若上游 `expires_in` < 30 秒，会在**同一请求内连环刷新**（最多 52 次），每次都拿刚得到的 RT 再换一次 —— 上游开了轮换 + 重用检测时极易判定异常 |
| ⑤ | `apps/api/src/oauth.ts:207-208` | `invalid_grant` 的 `continue` 绕过了 `150-152` 的 deadline 检查，极端时序下会空转到 `maxAttempts`（52 次） |

**已确认正确、本轮不改**：`saved.meta.changes === 0` 不当作成功、`invalid_grant` 的条件删除、
租约条件释放、刷新带 `resource`（RFC 8707）、窗口不变量（租约 ≥ 2×超时、等待 ≥ 租约）。

## 范围

**做：**

1. 把「验证会话身份」从 `requireIdentity` 里抽成 `oauth.ts::resolveIdentity`，行为改为
   **上游 401 先强制刷新一次换 token 重试，只有新 token 依然被拒才删会话**（修 ①）。
   - 真失效时判定权回到刷新路径，用户拿到的仍是可读的 `IDENTITY_REJECTED`（401）；
   - 瞬时故障 / token 边界过期 → 自动自愈，用户无感。
2. 该调用补 `AbortSignal.timeout(IDENTITY_TIMEOUT_MS)` 并转发 `cf-connecting-ip`（修 ②）。
3. `sessionFor` 新增可选 `{ force }`（只对第一次读到的行生效，等待者路径不再强制），
   供上一步的「换一份 token 重试」使用。
4. 空串 refresh token 不得覆盖已有的（修 ③）。
5. 刷新成功后**直接返回**刚写入的会话；只有写入未命中（被并发取代）才回循环重读（修 ④）。
6. 循环顶部统一检查 deadline（`attempt > 0` 时），覆盖所有 `continue` 路径（修 ⑤）。

**不做：**

- **不做会话滑动续期**（`expires_at` / cookie 仍是登录 + 7 天）—— 与本轮无关，单开一轮；
- **不做**「登录时强制校验 refresh token」（`6ab51d7` 的另一半，被回退过；本轮只做 401 的处置）；
- 不改上游账号系统、不改 D1 schema / 迁移、不引依赖；
- 不碰工作树里他人的在途改动（`App.tsx` / `share.ts` / `PLAN.md` 等）。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 上游 401 → 强制刷新重试一次，仍 401 才删会话 | **采纳** | 把「是否真失效」交给**刷新这个权威判定**：刷新成功即自愈，`invalid_grant` 才是真失效 |
| 上游 401 一律不删会话（只记日志） | 否决 | 真失效时用户会一直看到「账号暂时无法连接」，且不会去重新登录，比现状更难自助 |
| 上游 401 → 把 `token_expires_at` 归零，让下次请求去刷 | 否决 | 上游持续 401 时会变成每 20 秒一次无用刷新；且用户要等一个轮询周期才有结论 |
| 401 计数达到 N 次才删会话 | 否决 | 需要新的持久化状态（D1 加列 + 迁移），收益不抵成本 |
| 抽出 `resolveIdentity` 让「删会话」的判定可单测 | **采纳** | 现在这段逻辑埋在 Hono 中间件里，没有任何单测能覆盖它 |

## 验收标准

1. `apps/api/tests/oauth-session.test.ts` 新增覆盖，且**先红后绿**（红的那次要贴失败值）：
   - 上游 401 → 换新 token 后成功 → **会话行必须还在**（回归 ①）；
   - 换新 token 后仍 401 → 删会话并给出 `IDENTITY_REJECTED`（守门）；
   - 上游 `expires_in` 很小 → **同一请求内只允许刷新一次**（回归 ④）；
   - 上游回空串 RT → 会话里保留原 RT，不得被空串覆盖（回归 ③）。
2. `npm test -w @biff/api` / `npm run typecheck` / `npm run lint` / `check:test-map` 全绿。
3. 本地跑通后交用户验收，**用户明确说「可以推」再 push**（AGENTS.md §1 第 4 步）。
