## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 本机 Python 脚本,凭证走环境变量 | **采纳** | 与仓库既有 `tools/*.py` 离线管线口径一致;凭证不落盘 |

## 修订 4(2026-09-17,首次真实端到端跑通;修掉三个实跑才暴露的 bug)

用真实 cookie 跑 `--codes 803` 与全量扫描,拿到第一批真数据,同时暴露三个 bug:

### bug 1:`patDate` 是空参(成本模型错了一个数量级)

原判断是「一天一条请求,10 条覆盖全影展」。实测**证伪**:

```
patDate=2026-10-06 → 61 条,日期横跨 10.06–10.15
patDate=2026-10-15 → 61 条,同一批 sdCode
完全不传 patDate   → 61 条,同一批 sdCode
```

三次响应的 `sdCode` 集合**完全一致**,逐字段比对只有 5 个 `sdCode` 的 `remainSeat` 不同,
且是实时抖动(`325: 921→922`、`644: 2080→2079`)。结论:**参数被服务端忽略,一条请求即全量**。

处理:首条响应一旦跨多个日期,就判定参数无效、跳过其余日期查询。10 条 → 1 条,省 90% 请求量。

### bug 2:行没去重,产出被放大 10 倍

`row_key()` 早就写好、`watch()` 也在用,但 `fetch_rows()` 从没调用它 —— 10 条查询各自
`rows.extend(...)` 同一批数据。首跑输出「共 610 场」(= 61×10),可买数同样 ×10。

处理:`fetch_rows()` 按 `row_key`(=`prodSeq`)去重,保留首次出现。

### bug 3:`--json` 的 stdout 被诊断行污染

`[info] patDate 不生效…` 这类 `print()` 与 JSON 混在 stdout,下游
`python3 … --json | jq .` 会直接解析失败。

处理:新增 `warn()`,所有 `[warn]/[info]/[error]` 一律走 stderr;stdout 只留 JSON 一个文档。

### 附带:`--dates` 原本是个空转 flag

服务端既然不按日期裁,`--dates` 只影响"发哪几条无用请求",不影响结果。
现改为**客户端筛选**(`date_key()` 把 `2026.10.06 (Tue)` 归一成 `2026-10-06`,
只做分隔符与星期后缀处理,**不解析时间**),并改掉 `--help` 与文档里"10 天 = 10 条请求"的说法。

### 修复后实测口径

```
$ python3 tools/biff-ticket-watch.py --json
stderr: [info] 单条响应已跨 10 个日期 —— patDate 不生效,跳过其余 9 条日期查询。
stdout: {"total": 61, "bookableCount": 14, ...}
```

`--codes 803` → 1 场(`2026.10.08 18:00` Actors' House: KIM Minha),`remainSeat=0`、`SALE`,不可买。

## 修订 5(2026-09-17,盯盘模式做成长跑可用;三处缺口)

用户目标:常开监控 `001 / 003 / 803`,出现余票就推企微。

现有 `--interval` 循环能跑,但真开一整天有三个缺口,逐个补:

| 缺口 | 后果 | 处理 |
|---|---|---|
| 首轮已有可买场次不推 | 通知只在 `不可买 → 可买` 的**跳变**上触发;若开盯时就有票,人守一天也收不到 | 首轮快照里若有可买场次,立刻推一次「开盯就有票 N 场」 |
| 取不到数据只打日志 | 凭证失效后进程还在,但已经"瞎"了,人不知道 | 连续空轮并配了 webhook 时推**一次**告警;恢复后自动复位(`alerted`) |
| 空轮无退避 | 拿着废凭证继续按原间隔空转 | 连续空轮 ≥3 起按 2/3/4 倍退避,封顶 `WATCH_BACKOFF_CAP = 4` |

**新增参数:**

- `--jitter`(默认 `0.25`,取值 0–0.9):每轮间隔在 `interval ± jitter` 内随机抽;仍受 30 秒硬底约束。
- `--rounds N`:跑满 N 轮自动退出,给调参/验证用(`0` = 一直跑)。
- 心跳行带轮次与可买数(`14:55:01 #2 无变化(3 场,可买 1)`),长跑时能确认进程活着。

**关于"随机数 / 不被检测"的边界(明确记录):**

做:间隔随机抖动、每轮单请求、请求头照搬页面 XHR。
不做:UA 轮换、伪造 Referer、代理 IP 轮换、多会话切换、任何针对 `sctTabSessionCheck` 的规避。

理由:流量不像人的根因是**高频 + 并发**,不是缺随机数;本工具 1 请求/轮(≈0.67 次/分钟)
低于站点自身背景噪音一个数量级,加"反检测特征"反而更异常,且与本 PLAN 修订 3 已划的线冲突。
真正的长跑上限是 **cookie 24 小时失效**,不是检测 —— 所以补的是失效告警,不是伪装。

**实测:**`--codes 001,003,803 --interval 30 --rounds 2` → 首轮快照 3 场/可买 1(001 剩 1),
次轮心跳无变化,跑满 2 轮退出。

## 修订 6(2026-09-17,新增 wecom-cli 推送出口;澄清「API配置」不是 webhook)

用户问「API配置里的 Bot ID / Secret 能不能用」——**不能当 webhook 用**,这是两套东西:

| | 群机器人 webhook | 智能机器人 Bot ID / Secret |
|---|---|---|
| 形态 | 一条 `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=…` 地址 | 一对 ID/Secret,用于 SDK 长连接 |
| 本脚本怎么用 | 环境变量 `BIFF_WECOM_WEBHOOK`,脚本自己 POST | **填了也没用**;由 `wecom-cli auth init` 自动落盘 |

所以新增第二条出口 `--push-cli`:spawn 已授权的 `wecom-cli message aibot send`,
把消息发给**授权人自己**。用户已经扫过码,因此这条**零额外配置** —— 不需要 webhook,
也不需要手填 Bot ID / Secret。

**实现要点:**

- `cli_chat_id()`:`chat_id` 由 `wecom-cli identity whoami` 解析一次,进程内缓存(仅内存)。
  踩坑:`whoami` 只返回一段**自然语言**上下文,ID 埋在「授权真人用户身份」下方两行,
  且 JSON 里的换行是**转义**的 —— 必须先 `json.loads` 再正则,直接对原始 stdout 匹配必然失败(已实测踩过)。
- `cli_error_hint()`:把失败回包压成一行(errcode + errmsg + 处置建议),853004 → 重扫码,
  850002 → 缺消息权限。不回显任何 ID / 密钥。
- `make_pusher(webhook, cli_push)` 返回一个「给我几行 markdown」的闭包,`watch()` 不再关心出口怎么接;
  两个出口都开就都发。
- 启动时打印一行 `推送出口:…` 或 `推送出口:无(只在终端打印)`,避免"以为在推其实没推"。

**实测:**`--codes 001,003,803 --interval 30 --rounds 1 --push-cli` → 首轮触发
「BIFF 开盯就有票 1 场」并投递成功(`success = true`);另跑一条自检消息确认通路。

## 修订 7(2026-09-17,证伪:「接口只认登录 cookie」是错的)

在测空数据分支时偶然发现:拿一个**假 cookie**(`invalid-cookie-for-test`)跑,照样返回 61 条与
`resultCode=0000`。于是做了对照实验:

| 请求头 | resultCode | 条数 | 803 余量 |
|---|---|---|---|
| 不带 cookie | `0000` | 61 | 0 |
| 假 cookie `invalid-cookie-for-test` | `0000` | 61 | 0 |
| 无关 cookie `foo=bar` | `0000` | 61 | 0 |
| 真 cookie | `0000` | 61 | 0 |

**四者完全一致 ⇒ `prodList` 根本不校验 cookie。**

原判断错在哪:PLAN 开头写的「认证**只靠 cookie**」,证据是"用户贴的浏览器请求头里有 cookie、没有
`Authorization`"。那是**浏览器会带**,不是**服务端要求**——把观测当成了约束。修订 1–6 全都建立在这个
误判之上,连带 §五 的第 1 条理由(「技术上跑不久:cookie 24 小时失效」)**作废**。

据此的改动:

- `load_cookie()` 不再缺失即 `SystemExit`,改为**返回空串 + 提示继续**;`http_get_json()` 只在
  cookie 非空时带 `cookie` 头。凭证从"硬门槛"降级为"接口哪天收紧时的备胎"。
- 校验改由 `check_result_code()` 兜底(非 `0000` 会明确报警),不会静默出错。
- 文档 §一 改为「凭证(可选,可以完全不设)」,§五 第 1 条标注作废,§六 排障、§七 契约同步更正。

注意:**这不动摇 §五 第 2 条**(性质上不做无人值守流水线)——那条与凭证无关,依然成立。

**实测:**`env -u BIFF_COOKIE python3 tools/biff-ticket-watch.py --codes 803,001,002` → 正常拿到
3 场(001 剩 3、803 剩 0、002 剩 3);无 cookie 的 `--interval 30 --rounds 1 --push-cli` 亦正常推送。

## 修订 8(2026-09-17,`wecom-cli` 在用户 shell 里找不到)

用户在自己的 Terminal 跑 `--push-cli`,报:

```
[warn] 取授权身份失败:FileNotFoundError(wecom-cli 装了吗?)
```

两个原因叠在一起:

1. **`wecom-cli` 不是 brew 包**,用户先试了 `brew install wecom-cli`(失败,brew 建议 `code-cli`)。
   它其实是 npm 包 `@wecom/cli`。
2. **本机根本没缺这个包** —— WorkBuddy 连接器已经装在
   `~/.workbuddy/binaries/node/cli-connector-packages/bin/wecom-cli`(v1.3.0),
   但这个目录**只注入到 WorkBuddy 自己的子进程 PATH**,用户在 Terminal 里手跑时不在 PATH 上。
   (这个坑我在 `which` 时没复现,因为我的 shell 恰好带着它。)

改动:

- `wecom_cli_path()` 三级查找:`WECOM_CLI_BIN` 环境变量 → `shutil.which("wecom-cli")` → 兜底固定路径
  `WECOM_CLI_FALLBACKS`。找不到时给出可执行指引(npm 包名 + 可用 `WECOM_CLI_BIN` 覆盖)。
- `cli_output()`:失败时 stdout 为空则退回 **stderr**。踩过:`wecom-cli` 的 shebang 是 `env node`,
  PATH 里没有 node 时错误只在 stderr,原来只看 stdout 会打印一句毫无信息量的「返回不是 JSON」。
- `cli_error_hint()` 对非 JSON 输出改为回显**首行**(截断 200 字符),不再笼统说"格式变了"。

**实测:**`PATH=/usr/local/bin:/opt/homebrew/bin:/usr/bin:/bin`(有 node、无 `wecom-cli`)下,
`--interval 30 --rounds 1 --push-cli` 走兜底路径推送成功,无告警。
