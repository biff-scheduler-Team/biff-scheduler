# PLAN-20261005182415 — 红黑榜上报不再丢票：客户端重试落盘 + 服务端原子/重算 + 增量协议

> 用户原话：
> 「我是在服务端发现的 是不是贴纸的上报机制有问题? 有什么好办法能解决吗?」
> 「三件事都做 分层，按 ROI 排序」

## 目标

让「贴纸贴了、榜上没有」的每一种成因都被兜住：

1. **客户端不丢** —— 上报不再只活在内存里一个 1200ms 定时器上：关页 / 切后台 / 崩溃都留在盘上，
   下次开页面补发；失败自动退避重试。
2. **服务端不半截** —— 一票的 `contribution + stat + daily` 三条语句不可能被批次边界劈开；
   已经发生的漂移可以用一条幂等的 `recount` 修好。
3. **协议不靠碰巧** —— 把「发全量 + 失败不重试 + 靠下次签名变化碰巧自愈」换成带
   `seq` / `operationId` 的可重放增量。

## 范围

**做：**

- **A. 客户端**（`apps/web/src/film-votes.ts`；`RedBlackPage.tsx` 只改提示文案与接重试）
  1. **待发队列落盘**：键 `iffday.workspace.redblackpending.v1`（见「修订 1」：**不是** `biff.*`），
     存 `{ seq, votes }` —— 由 `film-votes.ts` 自己管。
  2. **`pagehide` / `visibilitychange(hidden)` → `flushFilmVotesPing()`**，用 `fetch(..., { keepalive: true })`。
  3. **失败退避重试**：1s → 2s → 4s → 8s → …（上限 30s）；**4xx 不重试**。
  4. **`seq` 守卫**：`seq` 只在**客户端**递增（见「修订 1」），响应回来时落后者丢弃
     （不 `adoptSyncedVotes`、不 `applyVotes`）。
  5. 页面载入发现有 pending → **立刻补发**（不走 1200ms 防抖）。
- **B. 服务端**（`apps/api/src/stat-batch.ts` / `film-vote-store.ts` / `index.ts`）
  6. `chunkStatements` 改**按写组切块**：同一票的几条语句同组、不可拆。
  7. **`recount(edition)`**：按贡献表重算 `film_vote_stat` / `film_vote_skin_stat`，并清理零票残行；
     挂 `POST /api/admin/recount`（该路径已有两层门禁）。
- **C. 协议**（`packages/contracts` + web + api + 迁移 `0015_*`）
  8. **增量 op 载荷** + `film_vote_sync(edition, contributor, last_seq)` 幂等守卫；
     **旧 `votes[]` 载荷继续可用**（部署期新旧客户端并存，见「提交边界」）。

**不做：**

- 不动红黑总数口径、不动卡片与画布的视觉、不引入任何新依赖。
- **日桶（趋势）不重算** —— 它记的是「当天变了多少」，没有历史可依。这条要写进 `recount` 的
  docstring 与响应体，否则运维会以为它修全了。
- 另外四个 ping（want / screening / ticket / telemetry）**本轮不动**：同一套病，但改一处就动四条链路，
  按「一次提交只做一件事」留给后续轮次（在本文档登记为已知同类）。
- 不做 Cloudflare 控制台的 WAF / Rate Limiting Rules（仓库里配不了，`rate-limit.ts` 文件头已留痕）。

## 方案取舍

| 备选 | 结论 | 理由 |
|---|---|---|
| 只加退避重试、不做待发队列 | 否决 | 「切后台 / 关页」正是移动端最先丢的那一下：定时器被挂起、标签页被回收。重试得先活到能重试 |
| 待发队列只放内存 | 否决 | 崩溃 / 被系统回收就没了 —— 而那正是要覆盖的场景 |
| keepalive 发**截断的**载荷 | 否决 | 整份替换语义下截断是**破坏性**的（会把服务端其余的票删掉）。超 64KB 干脆不发，留 pending 下次补 |
| `sendBeacon` 代替 `fetch(keepalive)` | 否决 | 同样是 64KB 上限，且**拿不到响应**：既确认不了成功，也拿不到 `seq`，pending 清不掉 |
| 4xx 一律不重试 | **采纳（按用户口径）** | 载荷 / 版本问题重试无意义。⚠ 已知代价见下「已知取舍」 |
| 429 单独重试 | 待定 | 限流是临时状态，重试几乎必然成功；但与用户口径相左。实现把它收成一个纯函数 `shouldRetry()`，将来改它是一行 |
| 把整份上报塞进**一个** `batch()` | 否决 | 最坏 500 票 × ~4 条 ≈ 2000 条语句，SQL 文本与绑定参数一起膨胀（`stat-batch.ts:14-16` 已说明为何分块） |
| 按**写组**切块 | **采纳** | 一票的语句同生共死；最坏退化成「整票都没写」，不会再有「贡献行落了、聚合没落」 |
| `recount` 只修 `film_vote_stat` | 否决 | 按款表的桶同样会漂，而群点直接读它（多出的一枚就是这么来的） |
| `recount` 顺手重算日桶 | 否决 | 无历史可依；只能修「当前累计」 |
| C：新表 + `last_seq` 幂等 | **采纳** | 幂等、可重放、载荷小到能用 beacon、部分载荷不再有破坏性 |
| C：每次上报都由服务端从贡献表整份重算 | 否决 | 那是 `recount` 的常驻版，成本不可接受 |

### 已知取舍（必须在代码注释里留痕）

- **429 会被当成「不可重试」**：按用户口径「4xx 不重试」。后果是场馆 NAT 下被限流的那一票要等
  下一次票签名变化才可能补上（A 的 pending 队列能兜住「最终会补」，但不是「立刻」）。

## 提交边界（一次提交只做一件事）

1. `fix(web): 红黑榜上报不丢票——待发队列落盘 + pagehide 补发 + 退避重试 + seq 守卫`（A）
2. `fix(api): 红黑榜聚合不再半截——按写组切块 + admin recount 兜底`（B）
3. `feat(redblack): 上报改增量协议（operationId + last_seq 幂等）`（C）

⚠ A / B / C 各自跑一遍对应的 workspace 单测并贴计数；三段都完成后本地起 dev server 交用户验收，
**经用户确认才 push**（本机约定）。

## 验收标准

1. **A**：`apps/web` 单测新增并全绿 ——
   「`pagehide` 后有 pending 就会发（且带 keepalive）」「载荷 > 64KB 时**不发**」
   「失败按 1s/2s/4s 重试且 payload 逐字不变」「4xx 不重试」「`seq` 更小的响应被丢弃」
   「载入时有 pending 立刻补发」「成功后 pending 清空」。
2. **B**：`apps/api` 单测新增并全绿 ——
   「第 k 个 batch 抛错时不会留下「贡献行有、聚合没有」的半截状态」
   「`recount` 幂等（连跑两次结果一致）且能把 gap 抹平」「零票残行被清掉」。
3. **C**：`apps/api` 契约单测 —— 旧 `votes[]` 载荷仍 200；新 op 载荷重复投递同一 `seq` 只生效一次；
   乱序 `seq` 被丢弃；老客户端与新客户端**同时**写同一部片时结果符合「op 到达序即生效序」。
4. **运维**：`POST /api/admin/recount?edition=biff-2026` 之后，那条对账 SQL（见下方附录）的 `gap` 全为 0。
5. 全量：`npm run verify:quick`（本地可选）；云端 Cloudflare 构建 + GitHub CI 绿。

## 附录：对账 SQL（`recount` 的判据）

```sql
SELECT c.film_key,
       SUM(CASE WHEN c.vote = 'red'   THEN 1 ELSE 0 END) - COALESCE(s.red_count, 0)   AS red_gap,
       SUM(CASE WHEN c.vote = 'black' THEN 1 ELSE 0 END) - COALESCE(s.black_count, 0) AS black_gap
FROM film_vote_contribution AS c
LEFT JOIN film_vote_stat AS s ON s.edition = c.edition AND s.film_key = c.film_key
WHERE c.edition = 'biff-2026'
GROUP BY c.film_key, s.red_count, s.black_count
HAVING red_gap <> 0 OR black_gap <> 0;
```

## 修订 1（2026-10-05，A 实现中）—— 两处比原方案更安全的选择

**① 待发队列的键改落 `iffday.workspace.*`（原写 `biff.redblack.pending.v1`）**

理由（实现时才查实，不是偏好）：`sync-data.ts::readWorkspace` 会把**所有** `biff.*` 键收进账号文档
（`local:biff.*`）、参与跨设备合并（异值会进 `SyncConflict` → 弹「同步冲突」），`backup.ts` 的备份
快照也按 `biff.` 前缀全量收。而这一份是**本浏览器、本身份**的临时待发状态 —— 不是用户数据：
跨设备合并没有意义，反而会把别的设备那一份当成自己的意图发上去。
`iffday.workspace.*` 是既有的「本地专属、只写盘不上报」命名空间（`state.ts` 里那条说明）。

**② `seq` 只在客户端递增，不上线（A 不需要任何服务端改动）**

理由：服务端的 `filmVotePingSchema` 是 `.strict()` —— 多带一个 `seq` 键会让**整份载荷 422**
（正是 2026-09-30 那次事故的同一类坑）。而 `seq` 守卫要回答的问题（「这条响应对应的是哪一份载荷」）
在客户端本来就答得出来：响应回调里闭包捕获着 `job.seq`。
⇒ A 因此**可以独立发布**，不必与服务端同时上线。线级的 `seq` + 响应回显归 **C**（那时服务端
本来就要存 `last_seq`）。

**③ 顺带记：「回到前台补一次」的边界（实现中补上的，不在原方案里）**

原方案只写了 `pagehide` / `visibilitychange(hidden)` 那一发。实现时发现一个**真实缺口**：
「贴完立刻切后台」时，切后台会把 1200ms 的防抖定时器一起挂起 —— 那一份**根本没发出去过**，
而 hidden 那一发是 keepalive、拿不到可靠响应（可能也没成功）。所以 `visibilitychange` 的
**visible** 那一侧也补一次，判据是「没有人在等这次发送」（`retryTimer` 为空）——
有退避计时器正等着时**不插队**，否则每次前后台来回都把退避白白抵消。

## 修订 2（2026-10-05，A 实现完成后）—— 退避重试与 `AbortSignal` 兜底的相互作用

A 把「失败不重试」改成了「退避重试到成功为止（间隔封顶 30s）」，于是它**放大**了本文档
§A 那条已知风险（旧 Safari / 内嵌 WebView 没有 `AbortSignal.timeout`）：

- 那种环境下 `film-votes.ts` 的每一发都会在 `fetch` 调用前抛 `TypeError`，被归成 `offline`；
- 改前：失败一次就算（提示一次）；
- 改后：**每 30s 无限重试一次**，而它**永远不会成功** —— 提示还会说「正在自动重试」。

代价很小（一次请求 / 30s，提示只弹一次），但**口径上是一种谎**。这里显式记下来：
它该与「目标浏览器矩阵」一起处理 —— 矩阵确认没有旧机型就什么都不用做；
一旦确认有，**兜底与重试策略要一起改**（例如「环境不支持超时」这一类失败直接不重试）。
⚠ 不要为了它单独加一条 `error instanceof TypeError` 的判据：Chrome 的网络失败**也是**
`TypeError: Failed to fetch`，两者分不开。

## 修订 3（2026-10-05，用户拍板）—— 兜底**做掉了**，而且只做一处

用户 2026-10-05 决定支持旧机型（也就是回答了修订 2 里那个前置问题），于是：

- 新增 `apps/web/src/net.ts::timeoutSignal(ms)`：能用原生 `AbortSignal.timeout` 就用，
  否则退到 `AbortController` + `setTimeout`（两条路语义一致：到点 abort）。
- 全站 **11 处** `signal: AbortSignal.timeout(12_000)` 全部换成它（want / screening / ticket /
  telemetry / film-votes / film-comments / account-sync）。
- ⚠ 为什么收成一个函数而不是各写一份兼容代码：AGENTS §5「口径单一来源」。也正因为如此，
  这条改动**跨 7 个模块**，属于一次「口径收口」，不是给红黑榜打的补丁。
- 读侧仍然**静默降级**（`loadFilmVotes` 失败 → 空表）——这是刻意的：榜本来就是「大家的票」，
  读失败退化成空表比整页报错好。但有了兜底之后，那类失败不再会由「环境缺 API」造成。

## 修订 4（2026-10-05，C 实现完成，在分支 `feat/film-vote-incremental` 上）

三个口径**定稿**（用户 2026-10-05 把 ①③ 说成硬要求，② 由实现方拍板并把代价写明）：

1. **`seq` 按设备记** ✓ —— 新表主键 `(edition, contributor, client_id)`；`client_id` 客户端生成、
   落 `iffday.workspace.redblackpending.v2`。少这一维两台设备会互相把对方的批次当成重放跳过。
2. **冲突口径 = 按到达序（LWW）**，**不带**客户端时间戳：每个 op 的语义是「把这部片设成某状态」，
   服务端按到达序整条覆盖。理由：设备时钟不可信（`updated_at` 本来就由服务端记），而「到达序」
   与既有的整份替换语义一致。
   ⚠ **已知代价**：两台设备**同时**改**同一部片**时后到的赢 —— 先改的那次会被覆盖掉。这是
   「本地即意图」口径下的必然结果，写在这里备查（要改就得引入向量时钟那一档复杂度）。
3. **向后兼容** ✓ —— `votes`（整份替换）那条路径**保留**，与 `ops` **二选一**（都带 / 带 ops 却缺
   `clientId`/`seq` → 422）。老 bundle 被 SW 预缓存留很久，这一条不能急着删。

### ⚠ 部署顺序会有一个分钟级窗口（上线那次必须知道）

`scripts/prepare-cloudflare.mjs` 的顺序是 `db:migrate:remote → deploy web → deploy api`（web 先、api 后）。
于是 C 上线那一次，**新前端会先于新 API 生效** —— 窗口里 `ops` 载荷打到老 API 会被 `.strict()` 判成
422，前端显示一次「服务端拒绝了这次上报」并停止自动重试（4xx 口径），但**待发队列留在盘上**：
API 上线后用户再动一次手（或刷新页面）就会补上。两条可选加固 → **已按第一支做掉**（见修订 5）。

### ⚠ `drizzle-kit generate` 当前是坏的（本轮之前就坏）

`migrations/meta/0013_snapshot.json` 是 `0012` 的**字节副本**（`id` / `prevId` 完全相同），
`0014` 甚至没有 snapshot —— 于是 `npm run db:generate -w @biff/api` 直接报
「pointing to a parent snapshot … which is a collision」。本轮迁移 `0015` 因此是**手写**的
（表结构只有一条 `CREATE TABLE`，风险可控）。⚠ 建议单独一轮修快照链：不修的话，以后每次加表都得
手写，而且将来某次 `generate` 会基于一份错位的快照算出**错误的 diff**。

## 修订 5（2026-10-05，部署窗口的加固）—— 两处入口都改成「迁移 → api → web」

窗口是真的，而且**有两个入口**（修订 4 只点了第一个）：

| 入口 | 原顺序 | 现在 |
|---|---|---|
| CI `scripts/prepare-cloudflare.mjs`（`WORKERS_CI_BRANCH=main`） | 迁移 → web（api 留给构建结束那条 `npx wrangler deploy`） | 迁移 → **api** → web |
| 手动兜底 `npm run deploy`（根 `package.json`） | build → 迁移 → web → api | build → 迁移 → **api** → web |

**为什么选「改顺序」而不是「客户端 422 后降级回发 `votes`」**：降级那支要多一条**常驻**兼容分支 +
一份「这台服务端只认旧载荷」的粘性状态，而顺序修好之后那条路**永远走不到** —— 那就是一段没人能测到的
死代码（仓库对「有实现但永远选不出来」的态度见 `sticker-material.ts` 那条守卫）。反向方向本来就安全：
新 API 保留整份替换路径（修订 4 的第 3 条），所以「旧前端 + 新 API」不会有事。

⚠ 副作用（写在 AGENTS §6 里备查）：构建结束那条 `npx wrangler deploy` 会**再部署一次 API** —— 同一份
代码、幂等；保留它是为了不动 CI 侧那条既有命令（它同时是「构建产物确实能上线」的兜底）。

验证：`node --check scripts/prepare-cloudflare.mjs` ✓；本地 `npm run verify`（不带 `WORKERS_CI` ⇒ 那段
`if` 整块跳过，**不会**迁移也不会部署）✓；`npm run build` 里的 `postbuild` 走的就是这条路径 ✓。
