# PLAN 2026-09-11 22:30 — 拖动顺位 = N 套方案 + 删除「档位」

> 需求(用户原话):
> ①「冲突的时间我看你用红框圈起来了 那这样 可以拖动红框内的冲突的场次 然后标记顺位 只要在不同顺位下不冲突
>    那么这个方案就可以 例如 一月一号 我生成一个顺位的 和一月二号另一个顺位的不冲突 即使再甘特图上是冲突的
>    也没关系 然后可以生成对应的 N 个方案(根据顺位不同的拖动顺序)」
> ②「那这样选片就不需要标记优先级吧 必看想看随缘」

## 1. 概念重构

| | 旧 | 新 |
|---|---|---|
| 冲突决策 | ★ 档位(必看 / 备选 / 随缘,影片级,3 档) | **拖动顺位**(场次级,组内 N 档) |
| 多方案 | A/B 两个方案(已于 `PLAN-20260911190000` 删除) | **顺位 = 方案编号**,冲突组自然展开出 N 套 |
| 档位 | 8 处消费,选片时被要求回答「多想看」 | **整体删除** |

**顺位 = 偏好次序;方案 = 所有无冲突组合**(`plans.ts`,**以「二改」为准**,见 §6):

```
冲突组 = conflict.ts::conflictGroups() 的连通分量(同一时间带互相重叠的几场)
顺位   = 组内位置 1..n,用户在「我的行程」的顺位卡里**拖动**决定 —— 只表达「多想保哪场」
方案   = 「每个冲突组各取一场」的**所有组合**(∪ 不属于任何冲突组的共同场次)
排序   = 顺位成本 = Σ(各组所选场次在组内的顺位),越小越优先
```

* **顺位不决定分组** —— 它只给方案排序(都取首选的那套排最前);
* **每一套方案都无冲突** —— 冲突组是连通分量,组与组之间按定义没有冲突边,一套方案从每组各取一场,
  取出来的任意两场必然分属不同组 ⇒ 不重叠。`plans.ts` 仍**逐套跑一遍校验**,异常组合直接剔除;
* 2 个冲突组各有 2 场 → **4 套方案**(`005+071` / `005+089` / `027+071` / `027+089`)。

## 2. 关键决策

### D1. 顺位**场次级**,不再是影片级

旧档位在影片级(「同片多场同步」),但方案编号必须落在**具体场次**上 ——
「9/17 的 001」和「9/18 的 001」是两个不同的备选。故新增 `state.ts::rankOf: Map<code, number>`。

### D2. 顺位只存**相对次序**,不存绝对值

每次拖完由 `setRanks(codes)` 把**该组整组**归一成 1..n。这样「删掉组内一场」不会留下空洞,
组员变动(新增一场把两个组合并)也不会因为旧序号撞车而产出怪顺序。

### D3. 拖动用**指针事件**,不用 HTML5 DnD

* 移动端不支持 HTML5 DnD,而顺位恰恰是手机上也要能改的;
* drag image / dragover 频率在各浏览器差异大,自己移动 DOM 更可控(行跟着指针走,所见即所得)。

拖动中**直接改 DOM 顺序**,松手才 `setRanks` 落盘 + 广播。

### D4. 拖动入口只在「我的行程」的择一卡里

甘特图的卡片位置由**时间**决定,拖动没有语义(而且容器本身已被「按住平移」占用)。
入口 = 卡片头第 1 列的 `⠿`(那个 12px 的箭头占位列 —— 行程卡本来就没有箭头,正好用上;
有把手时列宽放宽到 18px,触屏才抓得住)。

### D5. 档位(必看 / 备选 / 随缘)**整体删除**

它原本的定位就是「冲突组内的顺位」(`PLAN-20260911190000` D3 已把它从「选片时必填」降级为
「仅冲突时显示」)—— 现在这个位置被真正的顺位接管,档位在非冲突场景里只剩排序噪声。
**两套排序机制并存只会互相打架**,故一并下线:

| 位置 | 处理 |
|---|---|
| `src/pick.ts` | **整文件删除**(档位语义层:文案 / 色类 / ★ 控件 / 弹出菜单) |
| `types.ts::Priority` / `PickEntry.priority` | 删除;旧数据字段读取时忽略(**零迁移**) |
| `state.ts::setWish` / `priorityOfCode` / `setPriorityOfCode` | 删除 |
| `grid.ts` | 冲突卡标题行前的 ★ 删除(连 `wishOf` / `PRI_VOCAB` / `applyStar` 一起) |
| `agenda.ts` | 行程冲突行的 ★ 删除,换成**顺位徽章** |
| `library.ts` | 影片库卡片的 ★ 删除;「我的选片」的档位筛选 chips 与档位排序删除 |
| `modal.ts` | 资料弹层的「我的选片 ★」整行删除 |
| `ics.ts` / `share.ts` | DESCRIPTION / 影院行里的档位标签删除 |
| `score.ts` | 档位权重删除 → `分 = 场次数 + GV − 紧转场`(「排了就算数」) |
| `style.css` | `--pri-*` 与 `--color-pri-*` token(含暗色覆盖)删除 |
| `index.html` | 图例的 ★ 档位条 → 「① ② ③ 顺位 = 方案」 |

**唯一真实损失**:「我的选片」不再能按「多想看」排序 / 筛选,改为沿用影片库的目录顺序。
这是删除档位的必然结果(排序键没了),不是遗漏。

### D6. 方案对比 = **只列差异场次**

共同场次(不属于任何冲突组)每一套都有,列 N 遍是纯噪声 —— 折成每张卡底部一行计数。
这是「并列展示对比」最省读的一版:一屏就能看出「方案 1 保哪几场、方案 2 换成哪几场」。

### D7. `.ics` / 分享文案**不分方案**

仍导出**全部已选场次**(与旧行为逐字一致)。理由:导出是「把已选的全部带去现场」,
冲突双方在日历里同时存在是**用户明知**的状态(抢票时抢到哪个去哪个);
按方案拆分导出属于新需求,本轮不做(方案对比区已经能看清 N 套的差别)。

## 4. 验收

* `npm run build`(typecheck + lint + test + vite build)全绿:**98 项单测通过**。
* 人工路径:
  1. 网格里点选 4 场(两组各 2 场时间重叠)→ 行程里出现两张**绿框顺位卡**,每行带 `顺位 N` 与 `⠿` 把手;
  2. 顶部「方案对比」列出 **4 套**方案,按顺位成本 2 / 3 / 3 / 4 排列,第一套盖「最优先」章;
  3. 拖动某组第二行到第一行上方 → 该组顺位互换,「方案对比」**整体重排**(集合不变、顺序变);
  4. 把三场拖成 A~B~C 链式重叠 → 一张卡三行、方案对比出现 3 套;
  5. 移出组内一场 → 顺位自动归一,不残留空号;
  6. 「我的选片」不再有档位 chips / ★,列表顺序与影片库一致。

### 迭代(同日):拖动要有「移动感」

用户反馈「拖拽的时候要有一个明显的动画 就是我在拖拽它移动到另一个位置的感觉」。首版只是
`opacity-40` + 瞬时换位,读起来像「跳」而不是「拖」。改成两段动效:

1. **被拿起的那一行** —— `@utility rank-lift`(抬高 + 强投影 + 品牌色描边 + `cursor: grabbing`)
   + `scale(1.02)`,并用**逐帧跟手**的内联 `transform: translateY(...)` 平移。
2. **其余行 FLIP 让位** —— 换位前记录各行的 `offsetTop`,换位后算 delta → 先瞬移回旧位置
   (`transition:none` + `translateY(d)`),强制回流后放行 `transform 170ms cubic-bezier(.2,.8,.2,1)` 归零。

两处坑(已在代码里写明):

* **行留在文档流里**(不改成 `position: fixed`)—— 抽屉是 `overflow-hidden`,脱离文档流还要处理裁剪与滚动。
  代价是换位会改它自己的布局位置 → 必须做**位移补偿** `offset -= row.offsetTop - selfBefore`,
  否则行会在换位瞬间跳一格。
* FLIP 一律用 **`offsetTop`(布局位置)而不是 `getBoundingClientRect().top`** —— 后者含 transform,
  换位后读到的仍是「补偿前」的视觉位置,算出的 delta 恒为 0,动画根本不会播。
* 拖动期间置 `document.body.dataset.rankDragging`,让 `main.ts::onHoverLinkMove` 跳过 hover 联动
  (否则同冲突组每一行都被 `hl-row` 描边,盖掉「拿起」的投影);按下时顺手摘掉残留的 `hl-*` 类。

### 迭代(同日):冲突组「去警报化」—— 红框 → 绿框 OK

用户反馈(附截图)「我觉得这样是不是需要表示这样的顺位下是 OK 的??」——**问题比「缺一个 OK 标记」更根本**:

> 旧档位模型里「两场重叠」= 你必须做决定 = 待办,所以红框红底是对的。
> 顺位接手之后,重叠会自动展开成 N 套**各自可行**的方案 —— 红色只剩「这两场不能都看」这个事实,
> 不再是「有问题」。可整块还在用警报配色(红框 + 淡红底 + 红字标题 + 红色行卡片),读起来像报错。

**改动**(范围 = 只改「我的行程」的顺位卡;甘特图红卡与顶栏「冲突 N」刻意不动 ——
它们表达的是「同一时间轴上不能同时看两场」,选片时是有用的事实标记,不是错误计数):

| 位置 | 旧 | 新 |
|---|---|---|
| 组框 | `border-2 border-conf`(红) | `border-2 border-ok`(绿) |
| 组标题 | `text-conf` + 「N 场时间重叠」 | `text-ink` + 「N 场重叠」+ 绿章 **`✓ 顺位已排`** |
| 组内行卡片 | `CARD_SHELL_CONF_CLS`(红框 + 淡红底) | `CARD_SHELL_CLS`(普通白卡) |
| 顺位徽章 | `border-biff-line bg-biff-soft text-biff-ink` | `border-ok` + ok 浅底 + `text-ok` |
| 红色 | 常态 | **只留给真异常** `plans.invalid` 非空(同一顺位内仍重叠,理论不会发生)→ 红框 + 「顺位内仍重叠」 |

**顺带清掉的死代码**:`CARD_SHELL_CONF_CLS`、`agenda.ts::buildConf` + `confCodeChip`
(「与 [042] [098] 时间重叠」追加行)—— 冲突场次**必然**落在某个冲突组里(`conflictGroups()` 的
连通分量覆盖 `codeSet` 全体),组外的冲突行不可能存在,那条追加行早已不可达。

**顺位未拖过时**:一律显示 `✓ 顺位已排`(不区分「用户排的」还是「工具按开始时间兜底排的」)——
只要组内顺位互不相同,每套方案就能跑,就是 OK。

### 二改(同日):顺位 = 偏好次序,方案 = 枚举所有组合

用户澄清(两次):

> 「不是顺位已排序 而是在某一顺位下 比如第一顺位 这个可以生成多个无冲突的方案」
> 「不行 太多了 我想的比如说就是峡湾冲突了 然后我换了一个顺序 就 ok 了 那其实就应该是一套方案 + 其他的换完之后也不冲突的方案的总方案」

**一改错在哪**:把顺位当成「方案编号」(方案 k = 各组第 k 场),于是只产出 `max|组|` 套 ——
顺位被赋予了「决定分组」的语义,而用户只想要它表达**偏好次序**。

**二改后的模型**:

| | 一改 | 二改(现行) |
|---|---|---|
| 顺位含义 | 方案编号 | **偏好次序**(只回答「先保哪一场」) |
| 方案 | 各组第 k 场 | **「每个冲突组各取一场」的所有组合** |
| 套数 | `max|组|` | `∏|组|` |
| 顺位的作用 | 决定分组 | **只给方案排序**(成本 = Σ 各组所选顺位) |
| 组框徽章 | `✓ 顺位已排` | `✓ 已排偏好次序` |

**枚举实现**(`plans.ts::buildPlanSet`):按**成本分层**枚举 —— 成本从「组数」一路加到「各组大小之和」,
每层做一次精确用尽成本的 DFS。于是产出**天然按优先度排序**,不需要事后 sort;
撞到 `MAX_OPTIONS`(240)就停,留下的必然是最优先的那一批(`truncated` 置位)。
展示侧**全部并列**(横向滚动),不做默认折叠 —— 实际场景就是 4~9 套,加折叠反而是多余的机制。

**逐套校验**:不依赖「连通分量 ⇒ 任意组合无冲突」这条性质去**断言**,而是真的跑一遍冲突校验
(`firstOverlap`)—— 性质是论证,校验是证据。将来冲突口径变了(例如补上跨午夜的相邻两日),
不可行的组合会被自动筛掉、其场次进 `broken`(UI 标红),而不是静默产出撞车的方案。

**新增单测**:`tests/plans.test.ts` 13 项 —— 覆盖「2 组 × 2 场 → 4 套且按 2/3/3/4 排序」、
「换顺位 → 顺序整体改变但集合不变」、「3 组 → 8 套」、「超上限 → 截断并置 `truncated`」。

## 5. 已知边界(继承既有口径,本轮未动)

* **跨午夜的相邻两日之间不成冲突组**:`conflict.ts` 按 `s.date` 分桶判定,
  故「10/8 的 29:35 散场」与「10/9 的 01:00 开场」不会被判为冲突,也就不会进同一个择一卡。
  这是既有实现口径(与网格红标、`.ics` 一致),本轮不在此处另行修正。
